Operating Systems

An operating system exists to tell three convincing lies: that your program has the computer to itself, that it has unlimited contiguous memory, and that data written to a file is safely stored. Each lie is useful, each one is leaky, and the leaks are where all the interesting behaviour lives.

The single idea. An OS is a resource multiplexer with a security boundary. Every concept below is either a way of sharing something finite (CPU, memory, disk, network) among parties who do not trust each other, or a way of hiding that the sharing is happening.
#processes #virtual-memory #durability #syscalls #isolation

00 Why this domain exists

Everything mysterious about a running program is explained here.

Why does a program that works alone break when two copies run? Why does memory usage report two different numbers? Why did a file exist but contain nothing after a power cut? Why is starting a container fast and starting a VM slow? None of these are answerable from inside your program — they are answerable only one layer down.

01 The environment

One practical note, because it determines whether any of the hands-on work is possible.

You are on Windows. Most of this domain's instrumentation — /proc, strace, fork, cgroups, namespaces — is Linux. Install WSL2 and do everything in this domain there. It is a genuine Linux kernel, the tools behave normally, and it costs one command.

wsl --install
# then, inside the Linux shell:
sudo apt update && sudo apt install strace ltrace sysstat htop
Why not learn the Windows kernel instead You could — but every resource, every server you will ever operate, and every layer above this domain in the Atlas assumes Unix semantics. Learn the model the rest of the stack was built against.

N1 Processes and threads

What a running program actually is, as an object the kernel owns.

WHAT IT IS. A process is the kernel's record of a running program: an address space, a set of open file descriptors, credentials, and one or more threads of execution. A thread is a schedulable flow of control that shares the address space with its siblings.

WHY IT EXISTS. Because a machine must run code from parties that do not trust one another, and because a crashed program must not take the machine with it. The process is the unit of both isolation and accounting.

DEPENDENCIES. Computing N5 (stack and heap) · Software Engineering N6 (concurrency).

SUBTOPICS. The process control block · fork and copy-on-write · exec · parent/child trees and orphans · zombies · signals · threads and shared address space · why a thread crash kills the process but a process crash does not kill its parent.

PRIMARY RESOURCE
Type: Free online textbook · Title: Operating Systems: Three Easy Pieces (OSTEP), Virtualisation chapters 4–6 · Creator: Arpaci-Dusseau
Why this one: completely free, and it is the rare systems text organised around questions rather than components. Each chapter opens with the crux of the problem before naming any mechanism.

DEEPER (optional) — the fork(2), execve(2) and signal(7) man pages, which are the actual specification.
HANDS-ON · One program becomes two mid-sentence Write a program that prints its PID, calls fork(), and then both branches print again. You will see one program produce two different PIDs from a single line of code — and the return value of the same call differs between them.

Then find the memory question: set a variable before the fork and change it in the child. The parent does not see the change. Now check how much memory was actually copied — with copy-on-write, almost none, until you write. Verify by forking a process holding a large array and watching RSS.

Finally, create a zombie: fork, let the child exit, and have the parent sleep without calling wait(). Look at it in ps. The child is dead but still occupying a slot, because the kernel must keep the exit status until someone asks for it.

The realisation to reach: a process is not the program. It is a data structure the kernel maintains about the program — and things like zombies exist because that structure has its own lifecycle, independent of the code.

CONNECTS TO. Software Engineering N6 (threads) · Infrastructure (containers are processes with restricted views) · Distributed Systems (a crashed process is the simplest failure model).

N2 Scheduling

How one CPU convinces many programs that each of them owns it.

WHAT IT IS. The policy and mechanism by which the kernel decides which runnable thread gets a core, and for how long.

WHY IT EXISTS. Because there are always more runnable things than cores. Every scheduler is a compromise between throughput, latency and fairness, and you cannot maximise all three.

DEPENDENCIES. N1 · Computing N3 (the timer interrupt).

SUBTOPICS. Preemption and the timer interrupt · time slices · context switch cost · run queues · priorities and nice · starvation · CPU-bound versus I/O-bound processes and why the scheduler favours the latter · load average and what it actually measures.

PRIMARY RESOURCE
Type: Free online textbook · Title: OSTEP, scheduling chapters 7–10
Why this one: it develops the scheduler by repeatedly breaking a simpler one — FIFO fails, so shortest-job-first, which fails, so round-robin, and so on. The final design feels earned rather than announced.
HANDS-ON · Make context switching visible and expensive Run one CPU-bound loop and time it. Now run two, four, eight, sixteen copies simultaneously on a machine with a known core count, and plot total completion time against process count. Up to the core count it stays roughly flat; beyond it, it rises linearly — that bend is the moment the illusion of parallelism stops being free.

Then measure the switch itself: two processes that ping-pong a single byte through a pipe, as fast as possible, for a million rounds. Divide total time by rounds. You have measured your machine's context switch cost — typically a few microseconds. Compare that to the cost of a function call from Computing N7, and note the ratio is roughly a thousand.

Finally, run a CPU-bound and an I/O-bound process together and watch which one the scheduler favours with htop. Ask why the answer is the opposite of "fair".

The realisation to reach: concurrency is not free, and the scheduler is not fair on purpose — it optimises for keeping the CPU busy, which means rewarding processes that give it up voluntarily.

CONNECTS TO. Probability N6 (this is queueing theory with a policy) · Distributed Systems (load balancing is scheduling across machines) · Infrastructure (CPU limits and throttling).

N3 Virtual memory

Every process believes it owns a vast, empty, contiguous address space. None of that is true.

WHAT IT IS. A translation layer between the addresses your program uses and the physical locations that hold the data, implemented jointly by the kernel and a hardware unit in the CPU.

WHY IT EXISTS. Three reasons at once: isolation (you cannot name another process's memory), convenience (contiguity without fragmentation), and overcommitment (promising more than exists, because most promises are never fully claimed).

DEPENDENCIES. N1 · Computing N4 (the hierarchy).

SUBTOPICS. Pages and page tables · the TLB · minor and major page faults · demand paging · swap · overcommit and the OOM killer · virtual size versus resident size · mmap · shared memory · why memory-mapped files blur the file/memory distinction.

PRIMARY RESOURCE
Type: Free online textbook · Title: OSTEP, virtual memory chapters 13–22
Why this one: the single best free treatment of the subject, and it does not assume you have a hardware background.
HANDS-ON · Allocate a terabyte on a laptop Write a program that allocates far more memory than the machine has — say 100 GB — and does not touch it. On Linux with default settings, this succeeds. Check ps: virtual size is enormous, resident size is nearly nothing.

Now start touching one byte per page and watch RSS climb in page-sized steps while VSZ stays fixed. You are watching demand paging happen, one page fault at a time. Count the faults with /usr/bin/time -v.

Then keep going until the machine cannot cope, and meet the OOM killer — a kernel component that chooses a process to destroy because the system wrote cheques it cannot honour. Read its reasoning in dmesg.

The realisation to reach: allocation is a promise, not a delivery. This single fact explains why memory monitoring is confusing, why containers get killed mysteriously, and why "how much memory does my program use" has at least four different correct answers.

CONNECTS TO. Software Engineering N5 (a leak is now measurable in two different units) · Databases (the buffer pool competes with the page cache) · Infrastructure (container memory limits and OOM events) · Computing N4.

N4 Filesystems and the write path

The illusion of durability — and the exact point at which it becomes real.

WHAT IT IS. The structures that turn a flat block device into named, nested, growable files, and the caching layers that sit between your write() call and the physical medium.

WHY IT EXISTS. Because disks are slow and programs are impatient, so writes are buffered — and because a machine can lose power between the buffer and the platter, every serious system needs a way to say "no, actually store it now".

DEPENDENCIES. N3 (the page cache is virtual memory) · N5.

SUBTOPICS. Inodes, directory entries, hard and soft links · the page cache · write-back caching · write vs fflush vs fsync · journaling · atomic rename as a durability idiom · torn writes · what a filesystem guarantees and what it merely usually does.

PRIMARY RESOURCE
Type: Free online textbook · Title: OSTEP, persistence chapters 39–42
Why this one: chapter 42 on crash consistency is the clearest free explanation of why journaling exists, and it will retroactively explain everything you observed in p3-crash-survival.

DEEPER (optional) — "Files are hard" (Dan Luu, free) and the PostgreSQL fsync incident write-ups, for how badly this goes wrong in production systems written by experts.
HANDS-ON · The rename that is safer than the write You have already killed a process mid-write and found a file that exists and is empty. Now solve it properly and measure the cost of each level: write and exit; write and flush; write, flush and fsync. Three throughput numbers, orders of magnitude apart.

Then discover the idiom that real systems use. Write the new content to a temporary file, fsync it, then rename() it over the original. Kill the process at a hundred random points during this sequence and verify that the destination is always either the complete old version or the complete new one — never a mixture.

Then find the trap: does the directory entry itself need an fsync? Test it. The answer surprises most engineers and is the source of a well-known class of data loss bugs.

The realisation to reach: atomicity is not something the filesystem gives you; it is something you construct out of one operation that happens to be atomic. Rename is that operation, and nearly every durable system is built on it.

CONNECTS TO. Databases (the WAL is this node, formalised) · Distributed Systems (durability before acknowledgement) · Data Engineering (atomic publish of a dataset) · your own write-path notes.

N5 Syscalls and I/O

The boundary between your code and the machine's authority.

WHAT IT IS. The controlled doorway through which unprivileged code requests privileged operations, and the models — blocking, non-blocking, event-driven — for waiting on slow devices.

WHY IT EXISTS. Because a program must be able to touch hardware without being allowed to touch hardware. The syscall is that compromise: a deliberate, checked transition into a more privileged mode.

DEPENDENCIES. N1, N3.

SUBTOPICS. User and kernel mode · the syscall instruction and its cost · file descriptors as a universal handle · blocking vs non-blocking · select, poll, epoll · interrupts and DMA · why async I/O exists and what it actually buys.

PRIMARY RESOURCE
Type: Free tool used as a laboratory · Title: strace, with the syscalls(2) man page as reference
Why this one: this node becomes obvious the moment you watch a real program's syscalls scroll past, and stays abstract for as long as you only read about it.

DEEPER (optional) — "The C10K problem" (Dan Kegel, free) for why event-driven I/O was invented, then Beej's Guide to Network Programming for the practice.
HANDS-ON · Count the cost of printing "hello" Run strace ./hello on a trivial C program and read every line. A program with one visible statement performs dozens of syscalls before it reaches your code — loading the dynamic linker, mapping libraries, setting up. Count them.

Now the measurement that matters: write a program that writes one million lines to a file, one write() syscall per line. Time it. Then buffer in user space and issue one syscall per 8 KB. Time it again. The gap is the cost of crossing the boundary, and it is enormous.

Then use strace -c on something real — a Python interpreter starting up, or git status in a large repository — and find which syscall dominates. In most slow programs, the answer is a surprise and immediately suggests the fix.

The realisation to reach: buffering exists because crossing the user/kernel boundary costs roughly a thousand times more than a function call. Every buffered writer, every batch API, and every "why is this slow" investigation traces back to this number.

CONNECTS TO. Networking (sockets are file descriptors) · Software Engineering N7 (buffering and framing) · Infrastructure (seccomp restricts exactly this boundary) · Databases (I/O patterns).

N6 Isolation

Sharing one machine among parties who must not see each other.

WHAT IT IS. Two families of mechanism. Containers restrict what a process can see and use by manipulating kernel features. Virtual machines emulate an entire machine so a second kernel can run inside the first.

WHY IT EXISTS. Because hardware is expensive and workloads are bursty, so one machine must serve many tenants — and because "many tenants" immediately becomes a security and fairness problem.

DEPENDENCIES. N1, N3, N5.

SUBTOPICS. Namespaces — PID, network, mount, user · cgroups for resource limits · the union filesystem and image layers · what a container image actually contains · hypervisors, type 1 and 2 · the container-versus-VM security boundary · why a container shares the host kernel and what follows from that.

PRIMARY RESOURCE
Type: Free talk and accompanying code · Title: "Containers From Scratch" (Liz Rice) — build a container in ~100 lines with no Docker
Why this one: containers are usually taught as a product with commands to memorise. Building one from namespaces and cgroups reveals that there is no such thing as a container — only a process with a restricted view, which is a far more useful mental model.
HANDS-ON · Become PID 1, then escape Use unshare to run a shell in a new PID namespace. Run ps — your shell is PID 1 and the host's hundreds of processes are invisible. Nothing was virtualised; the kernel simply declined to show them to you.

Now add a memory cgroup limit of 100 MB and run a program that allocates 200 MB. It is killed, and dmesg shows exactly the same OOM machinery from N3 — but scoped.

Then the instructive comparison: run uname -r inside a container and on the host. Same kernel. Do it inside a VM. Different kernel. That one difference is the entire security argument between the two technologies, and it explains why multi-tenant clouds run VMs underneath their containers.

The realisation to reach: a container is not a lightweight VM. It is a normal process that has been lied to about what exists — and every container escape in history is a hole in one of those lies.

CONNECTS TO. Infrastructure & Cloud (orchestration schedules these) · Distributed Systems (the unit of deployment) · Business (the economics of multi-tenancy) · Security.
