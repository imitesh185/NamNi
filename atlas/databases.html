Databases

A database is what you get when you take every hard problem in this Atlas — the memory hierarchy, durability, concurrency, data structures — and solve all of them at once, correctly, for hostile concurrent users, without losing anything. It is the most concentrated engineering artefact you will study.

The single idea. A database exists to let you say what you want without saying how to get it, while guaranteeing that concurrent users and sudden power loss cannot corrupt the result. Everything below is either part of the "how" it works out for you, or part of the machinery that keeps those guarantees true.

00 Why this domain exists

Every serious system eventually contains a database, or accidentally rewrites one badly.

You could keep data in files. People did. The database was invented because files force every application to solve the same six problems independently — finding records quickly, changing several things atomically, letting many users write at once, surviving crashes, evolving the format, and answering questions nobody anticipated.

N1 The relational model and SQL

A sixty-year-old mathematical idea that refuses to be replaced.

WHAT IT IS. Data as sets of tuples, with operations — selection, projection, join, union — that take relations and produce relations. SQL is a language that approximates this algebra.

WHY IT EXISTS. Because before it, programs navigated data structures by hand, and every schema change broke every program. Codd's insight was that if you describe what you want, the system is free to change how it gets it — which is the same decoupling argument as design, applied to data access.

DEPENDENCIES. Mathematics (sets and relations) · Software Engineering N1 (keys are identity).

SUBTOPICS. Relations, tuples, attributes · primary and foreign keys · relational algebra · inner, outer, cross joins · aggregation and grouping · NULL and three-valued logic · declarative versus imperative thinking.

PRIMARY RESOURCE
Type: Free course · Title: CMU 15-445 Database Systems (Andy Pavlo), lectures 1–2 — full lecture videos and notes are free online
Why this one: it is the best free database course in existence, taught by someone who builds them, and it treats the relational model as an engineering decision with alternatives rather than as the natural order of things.

DEEPER (optional) — Codd's 1970 paper "A Relational Model of Data for Large Shared Data Banks", free and remarkably readable.
HANDS-ON · Ask a question nobody designed for Load a genuinely large real dataset into SQLite — Indian census data, a government open-data release, or your own browser history file, which is already SQLite. Do not design anything; just load it.

Now answer five questions that the original creators never anticipated, using only SQL. Then try to answer the same five questions by writing Python that reads the raw file. Count the lines of code and the time taken for each.

Then find the NULL trap on purpose: write a query with WHERE column != 'x' on a column containing NULLs, and notice that rows you expected are missing. Work out why from three-valued logic. NULL is not a value; it is the absence of one, and it propagates through comparisons in a way that surprises everyone exactly once.

The realisation to reach: the power is not the syntax. It is that you described a result and something else decided the algorithm — and that this is why the query still works after the data grows a thousandfold.

CONNECTS TO. Mathematics (set theory, logic) · Data Engineering (SQL is the lingua franca) · Software Engineering N9 (declarative interfaces).

N2 Storage and indexes depth

This node is Computing N4 played out at disk scale, and it is the heart of the domain.

WHAT IT IS. How rows are laid out in fixed-size pages, and the auxiliary structures that let the system find a specific row without reading every page.

WHY IT EXISTS. Because a full scan of a large table costs a number of disk reads proportional to its size, and disks are the slowest tier of the hierarchy. An index trades write cost and space for read cost — and that trade is the single most consequential decision in database performance.

DEPENDENCIES. Computing N4 · OS N3–N4 · Software Engineering N3 (trees).

SUBTOPICS. Pages and the buffer pool · row-oriented layout · B+ trees and why they are wide and shallow · clustered versus secondary indexes · covering indexes · LSM trees, memtables and compaction · write amplification · columnar layout and why analytics uses it · index selectivity.

PRIMARY RESOURCE
Type: Free online book · Title: Use The Index, Luke! (Markus Winand), free at use-the-index-luke.com
Why this one: free, and it is organised around the question you will actually have — "why is this query slow?" — rather than around index theory. It teaches you to read execution plans, which is the transferable skill.

DEEPER (optional) — CMU 15-445 lectures on storage and tree indexes, and the SQLite file format documentation, which is one of the clearest specifications of a real on-disk format available for free.
HANDS-ON · Find the index that makes things slower Take a table with a million rows. Time a query filtering on an unindexed column. Add the index. Time it again — orders of magnitude faster, exactly as promised.

Now break the promise, three ways. First: filter on a low-selectivity column, such as a boolean where half the rows match. Add an index and watch the planner refuse to use it — because reading half the table via random index lookups is slower than reading all of it sequentially. Find the selectivity threshold where the planner changes its mind.

Second: time a bulk insert of 100,000 rows with no indexes, then with five indexes. Every index must be updated on every write, and the cost is very visible. An index is a read optimisation paid for on every write, forever.

Third: build a multi-column index and discover that column order decides which queries it can serve. An index on (a, b) helps a query filtering on a, and does nothing for one filtering only on b. Work out why from the tree structure.

The realisation to reach: sequential access beats random access by so much that reading everything is often faster than looking things up — which is exactly the stride-cliff result from Computing N4, one storage tier further down.

CONNECTS TO. Computing N4 · Data Engineering (Parquet is columnar storage, and this node explains why it wins) · Distributed Systems (LSM trees underpin most distributed stores) · your own storage-engine work.

N3 Query planning

Automated algorithm selection — and why it sometimes chooses catastrophically.

WHAT IT IS. The component that turns a declarative query into an execution plan by estimating the cost of alternatives using statistics about the data.

WHY IT EXISTS. It is the price of N1's promise. If you do not say how, something must decide — and the decision depends on data the developer cannot know at write time.

DEPENDENCIES. N1, N2.

SUBTOPICS. Parse, rewrite, plan, execute · cardinality estimation · histograms and statistics · nested loop, hash and merge joins · join ordering as a search problem · why estimation errors compound through a plan · reading an EXPLAIN output.

PRIMARY RESOURCE
Type: Free documentation used as a tool · Title: PostgreSQL's EXPLAIN ANALYZE documentation, plus SQLite's EXPLAIN QUERY PLAN
Why this one: the plan of a query you wrote thirty seconds ago teaches more than any general account of optimisation. This is the single most valuable database skill to hold.
HANDS-ON · Make the planner guess wrong Write a three-table join and run EXPLAIN ANALYZE. Compare the estimated row count at each step with the actual one. On a healthy query they are close.

Now break it deliberately. Load a table, run a query, then insert a million rows without updating statistics. Run the query again. The planner is now reasoning about a table that no longer exists, and may choose a nested loop join over a hash join — turning milliseconds into minutes. Then run ANALYZE and watch it recover instantly.

Then create correlated columns — say, city and postcode — and filter on both. The planner assumes independence and multiplies the selectivities, so it estimates far fewer rows than exist. The error compounds at every join above it in the plan.

The realisation to reach: the optimiser is a predictive model of your data, and like every model it fails when its assumptions are violated. Most inexplicable production slowdowns are this — a plan that changed because the statistics did.

CONNECTS TO. Probability (cardinality estimation is statistical inference) · Computing N7 (this is automated complexity analysis) · Data Engineering (query engines do the same thing at scale).

N4 Transactions

All-or-nothing, in the presence of a power cut.

WHAT IT IS. A grouping of operations that either all take effect or none do, survives a crash once acknowledged, and leaves the database internally consistent.

WHY IT EXISTS. Because a transfer between two accounts is two writes, and a machine can die between them. Without transactions, every application must implement its own crash recovery — and every one of them will get it wrong.

DEPENDENCIES. OS N4 (fsync, the write path, atomic rename) · N2.

SUBTOPICS. Atomicity, consistency, isolation, durability — each meaning something specific · write-ahead logging · why the log is written before the data · checkpoints · crash recovery, redo and undo · group commit · the cost of durability.

PRIMARY RESOURCE
Type: Free course · Title: CMU 15-445, logging and recovery lectures
Why this one: free, and it derives write-ahead logging from the crash-consistency problem you already met in OS N4 and in your own crash-survival project — so it lands as a solution to something you have personally suffered.
HANDS-ON · Kill the database mid-transfer Write a script that transfers money between two rows inside a transaction, with a deliberate pause between the debit and the credit. Run it, and kill the database process during the pause — hard, with SIGKILL, not a clean shutdown.

Restart and check the balances. The money is not missing and it has not been duplicated. Now remove the transaction wrapper and repeat. Money vanishes. You have demonstrated atomicity by destroying it.

Then measure what it costs. Insert 10,000 rows one transaction per row, then all in a single transaction. The difference is enormous, and the reason is one fsync per commit — the same number you measured in OS N4. Then look at the WAL file directly and watch it grow, then checkpoint and watch it truncate.

The realisation to reach: durability costs one disk sync, and everything about database performance tuning is an attempt to amortise that sync across more work. Group commit, batching and async commit are all the same idea.

CONNECTS TO. OS N4 · Distributed Systems (two-phase commit, and why it is unsatisfying) · Data Engineering (exactly-once processing) · Finance (why ledgers are append-only).

N5 Concurrency and isolation depth

Many writers, one truth — and the four ways it goes wrong.

WHAT IT IS. The mechanisms and the spectrum of guarantees governing what one transaction can observe of another's incomplete work.

WHY IT EXISTS. Perfect isolation — behaving exactly as if transactions ran one at a time — is achievable but slow. Every database therefore offers weaker levels that are faster and permit specific anomalies. Almost every database ships with a default that is not fully isolated, and most developers do not know which one they are using.

DEPENDENCIES. N4 · Software Engineering N6 (races and locks).

SUBTOPICS. Dirty read, non-repeatable read, phantom read, lost update · read uncommitted, read committed, repeatable read, serializable · two-phase locking · multiversion concurrency control · snapshot isolation and write skew · deadlock detection · optimistic versus pessimistic control.

PRIMARY RESOURCE
Type: Free paper · Title: "A Critique of ANSI SQL Isolation Levels" (Berenson et al., free from Microsoft Research)
Why this one: it demonstrates that the standard's definitions are ambiguous and that real databases interpret them differently — which is the fact that actually matters in production, and is omitted from almost every tutorial.

DEEPER (optional) — CMU 15-445 concurrency control lectures for the mechanisms, and the Jepsen analyses (free at jepsen.io) for what real systems actually deliver versus what they claim.
HANDS-ON · Reproduce all four anomalies deliberately Open two PostgreSQL sessions side by side. This exercise only works with two real terminals, and that is the point — concurrency is invisible in a single session.

Set isolation to READ COMMITTED. In session A, begin a transaction and read a row. In session B, update and commit that row. Read it again in A — the value changed inside a single transaction. That is a non-repeatable read, at the default isolation level of most databases in production.

Now reproduce the lost update: both sessions read a counter, both increment it in application code, both write it back. One increment silently disappears — the identical failure to the two-thread counter in Software Engineering N6, now across processes and machines. Fix it with SELECT FOR UPDATE, then again with an atomic UPDATE ... SET x = x + 1, and compare.

Then the subtle one that catches experienced engineers: write skew under snapshot isolation. Two doctors are on call; a rule says at least one must remain. Both check the rule simultaneously, both see two doctors on call, both sign off. Neither transaction conflicts on any row, both commit, and the invariant is now violated with no error anywhere.

The realisation to reach: your database's default isolation level permits anomalies your application logic assumes cannot happen. Write skew in particular cannot be prevented by careful application code — it requires either serializable isolation or an explicit lock, and knowing that distinction is genuinely rare.

CONNECTS TO. Software Engineering N6 · Distributed Systems (consistency models are this node spread across machines) · Human Behavior (coordination failures) · Finance (double-spend).

N6 Modelling

Deciding the shape of the truth — the decision that is hardest to reverse.

WHAT IT IS. Choosing tables, columns, keys and relationships to represent a domain, and deciding deliberately where to duplicate data.

WHY IT EXISTS. Because the schema outlives the application. Code is rewritten every few years; data structures persist for decades, and every consumer downstream depends on them.

DEPENDENCIES. N1 · genuine experience of N2–N5.

SUBTOPICS. Functional dependencies · normal forms and what each eliminates · denormalisation as a read optimisation · star and snowflake schemas · slowly changing dimensions · surrogate versus natural keys · schema evolution and migrations · soft deletes and their consequences.

PRIMARY RESOURCE
Type: Free course lectures · Title: CMU 15-445 on the relational model, combined with the freely available chapters and articles from Kimball's dimensional modelling work for the analytics side
Why this one: the operational and analytical traditions disagree productively, and seeing both prevents you from applying warehouse patterns to transactional systems or the reverse.
HANDS-ON · Model it badly on purpose, then change the requirement Model something you know well — a cricket league, a family tree, or your own bookshelf. Deliberately build the naive version first: one wide table, repeated values, no foreign keys.

Now apply four requirement changes, one at a time, and count what each costs. A team renames itself. A player transfers mid-season and history must remain correct. A match is replayed and the old result must be preserved. You must report on a date that has since changed.

The first change alone will force an update across thousands of rows and reveal an inconsistency where one row was missed. That inconsistency is the argument for normalisation, discovered rather than asserted. The third and fourth push you into temporal modelling and slowly changing dimensions, which is where most real schemas are wrong.

Then redesign properly and re-run the same four changes to see which became free.

The realisation to reach: normalisation is not tidiness, it is the elimination of any fact stored in more than one place — because two copies of a fact will eventually disagree, and then no query can tell you which is true.

CONNECTS TO. Data Engineering (dimensional modelling, data contracts) · Software Engineering N9 (coupling) · Accounting (a ledger is an append-only schema, chosen deliberately).

N7 The NoSQL families

Not alternatives to SQL. Different things given up, for different reasons.

WHAT IT IS. A set of storage systems that relax one or more relational guarantees — joins, schema, or strong consistency — in exchange for scale, flexibility or write throughput.

WHY IT EXISTS. Because some workloads genuinely do not need what a relational database provides, and the guarantees are not free. The failure mode of this node is adopting a system for fashion rather than for the specific guarantee you are willing to lose.

DEPENDENCIES. N1–N6. This node is only comprehensible after you know what is being given up.

SUBTOPICS. Key-value stores · document stores and embedded aggregates · wide-column stores · graph databases and when traversal beats joins · search indexes · time-series stores · the aggregate-boundary idea · why "schemaless" means the schema lives in your application instead.

PRIMARY RESOURCE
Type: Free paper · Title: Amazon's Dynamo paper (2007), freely available
Why this one: it is the origin of most of this family, and it states its trade-offs with unusual honesty — what was abandoned, why, and what the application must then handle itself.

DEEPER (optional) — the Bigtable paper for wide-column, and Jepsen's analyses for what these systems actually guarantee under partition.
HANDS-ON · One workload, three shapes Take a single realistic workload — say, a social feed with users, posts and follows. Implement it three times: relational in PostgreSQL, document-shaped in SQLite with JSON columns, and as a pure key-value store using only get and put.

Then ask each one the same four questions. Show one user's feed is easy everywhere. Show the ten most-followed users is trivial relationally and painful in key-value. Change a username is one update relationally and a fan-out rewrite in the denormalised document version. Find friends-of-friends three levels deep is where relational joins start to hurt and a graph model would win.

The realisation to reach: you do not choose a database, you choose which queries will be cheap and which will be expensive — and you are making that choice permanently, at modelling time, for questions you have not been asked yet. That is why N6 is the hardest node in this domain.

CONNECTS TO. Distributed Systems (CAP, replication, quorums) · Data Engineering (polyglot persistence) · Business (operational cost of each choice).
