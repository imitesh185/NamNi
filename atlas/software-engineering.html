Software Engineering

This is one of two domains in the Atlas set to genuine depth rather than commander-level. The subject is not how to write code that works — that is programming. It is how to reason about a system made of moving parts that outlives the day you wrote it, which is a different and much harder thing.

The single idea. Every concept in this domain exists because a simpler approach broke at a particular scale. The concept is never the lesson — the breakage is the lesson. Learn each one by reaching the breakage first, deliberately, in something small enough that you can see the whole failure.
#objects #references #concurrency #design

00 Why this domain exists

Programming is instructing a machine. Engineering is managing what happens next.

A program that runs once, for you, on your machine, needs almost none of this. Every idea below earns its place only when at least one of five things is true: the program is large, it lives a long time, it is touched by other people, it runs concurrently, or it must not lose data. That is the actual boundary between programming and engineering.

N1 Objects

Identity, type, value — and the contract between equality and hashing.

WHAT IT IS. An object has three properties: what it is (identity), what kind of thing it is (type), and what it holds (value). Two of those never change. Equality, hashing and ordering are protocols layered on top, and they have contracts you can violate.

WHY IT EXISTS. Because collections need to answer “have I seen this before?” — and that question is meaningless until you have decided whether you mean the same object or an equal one. Nearly every subtle bug involving sets, dicts and caches traces back to that choice.

DEPENDENCIES. Computing N5 (stack and heap).

SUBTOPICS. Identity vs equality · type as behaviour, not label · the eq/hash contract · ordering · immutability as a guarantee · value objects.

PRIMARY RESOURCE
Type: Official documentation · Title: The Python Language Reference §3, “Data model”
Why this one: free, precise, and the actual contract rather than someone's summary of it. Most confusion here comes from reading tutorials that paraphrase this document badly.

DEEPER (optional) — Composing Programs (Berkeley CS61A, free online), chapter 2, for the same ideas expressed as abstraction rather than as language rules.
HANDS-ON · The object that vanished Define a small class holding two fields. Give it an __eq__ and an __hash__ based on those fields. Put an instance into a set. Confirm it is there.

Now mutate one of the fields and look for the object again. It is gone. The set still contains it — len() proves that — but membership testing cannot find it, and iterating will yield an object the set claims not to contain.

Then find the second surprise: define __eq__ without __hash__ and watch the class become unhashable entirely. Ask why the language would do that to you rather than for you.

The realisation to reach: a hash-based container is not storing your object, it is storing it at an address computed from its value — so mutating the value without telling the container moves the door but not the house.

CONNECTS TO. Databases (primary keys are this exact contract) · Distributed Systems (consistent hashing) · Data Engineering (deduplication) · Mathematics (equivalence relations).

N2 References and aliasing

A name is a label, not a box — and containers hold labels too.

WHAT IT IS. Assignment binds a name to an object; it does not copy. Containers hold references, not values. Copying therefore has a depth, and mutability determines whether depth matters.

WHY IT EXISTS. Copying everything on every assignment would be unusably slow. Sharing is the default for performance reasons, and every aliasing bug is the price of that decision.

DEPENDENCIES. N1.

SUBTOPICS. Binding vs mutation · shallow and deep copy · argument passing · mutable default arguments · defensive copying · immutability as a design tool.

PRIMARY RESOURCE
Type: Your own existing note · Title: 1.3 References & aliasing
Why this one: you have already built it and marked it Evergreen. Re-deriving it from an external resource would be strictly worse than re-reading your own derivation.
HANDS-ON · The function with a memory Write a function that takes a list with a default value of [], appends to it, and returns it. Call it three times with no argument. The results accumulate across calls — the function has grown a memory it was never given.

Now build the more dangerous version: a “template” dictionary of configuration, copied into each of ten workers with a shallow copy, where one nested value is a list. Have one worker append to that list. Watch all ten change.

The realisation to reach: the default argument was evaluated once, at definition time — and a shallow copy duplicates the outer container while faithfully sharing everything inside it. Both bugs are the same bug: you assumed a copy where the language gave you a reference.

CONNECTS TO. Concurrency (shared mutable state is this problem with a timing dimension) · Functional programming · Distributed Systems (why messages are copied by value across a boundary).

N3 Data structures

Not a catalogue to memorise. A set of trade-offs to recognise.

WHAT IT IS. Arrays, hash maps, linked structures, trees, heaps and graphs — each one fast at some operations and slow at others, with the trade-off determined by physical layout.

WHY IT EXISTS. Because there is no structure that is good at everything. Choosing correctly means knowing which operation you will perform ten million times and which you will perform once.

DEPENDENCIES. N1, N2 · Computing N4 (the memory hierarchy is why arrays win more often than theory suggests).

SUBTOPICS. Dynamic arrays and amortised growth · hash maps, collisions, load factor · linked lists and pointer chasing · trees and balance · heaps and priority · graphs and traversal.

PRIMARY RESOURCE
Type: Free course · Title: MIT OCW 6.006, lectures on hashing, trees and heaps
Why this one: free, and it derives each structure from the problem it solves rather than presenting it as a fact to absorb.

DEEPER (optional) — Open Data Structures (opendatastructures.org, free) when you want the implementations in full.
HANDS-ON · Build a cache and get evicted Build a cache as a plain dictionary in front of a slow function. It works, and it is fast. Now let it run against a large key space until memory becomes a problem — and you have discovered that a cache without eviction is just a memory leak with good intentions.

Add a size limit. Immediately you face a real question with no obvious answer: which entry do you throw away? Try random eviction, then first-in-first-out, then least-recently-used. To implement LRU efficiently you will find that a dictionary alone cannot do it — you need ordering as well as lookup, and you will end up combining a hash map with a linked list because neither structure alone has both properties.

Measure hit rate for each policy on a realistic access pattern. Then try a workload where LRU is the worst possible policy — a sequential scan larger than the cache.

The realisation to reach: you did not choose a data structure, you composed two structures because your access pattern needed two different things. That is what real structure selection looks like.

CONNECTS TO. Databases (a B-tree is this node at disk scale) · Operating Systems (page replacement is literally cache eviction) · Distributed Systems (distributed caches) · Economics (inventory policy is the same problem).

N4 Recursion and the call stack

Processing something that contains smaller versions of itself.

WHAT IT IS. A technique for structures whose shape is self-similar, and the machine mechanism — the call stack — that makes it possible and also limits it.

WHY IT EXISTS. Some structures have no natural loop over them because their depth is unknown: a filesystem, a JSON document, an expression tree, an organisation chart. Recursion is how you write code whose shape matches the data's shape.

DEPENDENCIES. Computing N5.

SUBTOPICS. Base case and recursive case · the call stack and stack traces · depth limits · converting to iteration with an explicit stack · memoisation · cycle detection.

PRIMARY RESOURCE
Type: Free online textbook · Title: SICP (MIT Press, free online edition), §1.2 · Why this one: it distinguishes a recursive process from a recursive procedure, which is the distinction that makes tail calls and stack growth make sense.
HANDS-ON · Walk a filesystem until it bites Write a walker that computes the total size of a directory tree. It is naturally recursive because directories contain directories. Run it on your home directory.

Three things will go wrong, and each teaches a distinct concept. It may hit a symlink loop and recurse forever — forcing you to invent visited-set cycle detection, which is a graph concept arriving inside a tree problem. It may hit a permission error halfway through and lose all accumulated work — forcing you to think about partial failure. And on a deep-enough tree it may hit the recursion limit — forcing the iterative rewrite with an explicit stack.

The realisation to reach: the thing you thought was a tree was a graph. That single discovery is worth more than any number of recursion exercises, and it arrives on its own if you point the program at a real filesystem instead of a synthetic one.

CONNECTS TO. N3 (graphs) · Data Engineering (lineage graphs, DAG orchestration) · Distributed Systems (dependency cycles) · Mathematics (induction is the proof form of recursion).

N5 Memory management and garbage collection

Who decides when an object stops existing.

WHAT IT IS. The strategies by which a runtime determines that memory can be reclaimed: reference counting, tracing collectors, generational heuristics — and their failure modes.

WHY IT EXISTS. Manual freeing produces two catastrophic bug classes (use-after-free and leaks). Automatic collection removes one of them and makes the other quieter, at the cost of pauses and unpredictability.

DEPENDENCIES. N2 (references are exactly what a collector counts) · Computing N5.

SUBTOPICS. Reference counting · cycles · tracing and mark-sweep · generational collection · weak references · finalisers · what a “leak” means in a managed language.

PRIMARY RESOURCE
Type: Official documentation + tool · Title: Python's gc and tracemalloc modules, used as instruments
Why this one: free, installed, and this node is only convincing when you watch the numbers move on your own process.
HANDS-ON · Make an object immortal by accident Create two objects that refer to each other, drop every external name to both, and check whether they were freed. Under pure reference counting they cannot be — each holds the other's count above zero — so they are unreachable and alive at the same time. Disable the cycle collector and watch memory climb.

Then build the leak that actually happens in production: a cache keyed by object, a registry that appends every instance it has ever seen, or a closure that captured something large. Use tracemalloc to find it the way you would in a real incident, rather than by reading the code you already know is wrong.

The realisation to reach: a managed language does not prevent leaks. It only changes the question from “did I forget to free it?” to “what is still holding a reference I forgot about?”

CONNECTS TO. Operating Systems (virtual memory, RSS) · Databases (connection and buffer pools) · Infrastructure (why a service restarts nightly) · Biology (apoptosis is scheduled cleanup).

N6 Concurrency

More than one thing happening, and the loss of a single timeline.

WHAT IT IS. Structuring a program so that multiple activities overlap in time, plus the mechanisms — locks, queues, immutability, message passing — that keep shared state from being corrupted by that overlap.

WHY IT EXISTS. Because processors stopped getting faster and started getting wider, and because most programs spend their time waiting rather than computing. Both facts force overlap.

DEPENDENCIES. N2 (shared mutable state), N5 · Computing N3.

SUBTOPICS. Concurrency vs parallelism · threads and processes · race conditions · atomicity and the read-modify-write problem · locks, deadlock, livelock · queues as the safer default · async and event loops · immutability as a concurrency strategy.

PRIMARY RESOURCE
Type: Free book · Title: The Little Book of Semaphores (Allen Downey, free PDF)
Why this one: it is structured as a sequence of puzzles you attempt before seeing the answer, which is the only way synchronisation ever becomes intuitive rather than memorised.

DEEPER (optional) — OSTEP (free online), the concurrency section, once Operating Systems is on your map.
HANDS-ON · The counter that cannot count Two threads, each incrementing a shared counter one million times. Expected result: two million. Run it. You will get something less, and a different number every time.

The value of this exercise is entirely in the next step: explain precisely where the lost updates went, in terms of read-modify-write being three operations rather than one. Then fix it with a lock and measure the cost — the fixed version is often slower than a single thread, which is the second and more important surprise.

Then build a deliberate deadlock with two locks acquired in opposite orders, watch it hang, and fix it by imposing a global lock ordering. Finally, rewrite the whole thing with a queue and no shared state at all, and notice that the problem simply ceases to exist.

The realisation to reach: locks do not make concurrency safe; they make it slow enough to be safe. The structural fix is almost always to stop sharing, not to guard the sharing better.

CONNECTS TO. Operating Systems (scheduling, context switches) · Distributed Systems (the same problem with the added possibility that the other party has died) · Databases (isolation levels are concurrency control) · Human Behavior (coordination problems).

N7 Serialization and protocols

What happens when a value has to leave the process that created it.

WHAT IT IS. Converting in-memory structures to a byte sequence and back, plus the agreements — framing, schema, versioning — that let two programs interpret those bytes identically.

WHY IT EXISTS. Memory representations contain pointers, and a pointer is meaningless outside the process that made it. Anything crossing a process, machine or time boundary must be flattened.

DEPENDENCIES. N1, N2 · Computing N1 (encoding).

SUBTOPICS. Text vs binary formats · framing and message boundaries · schemas and evolution · backward and forward compatibility · endianness · the security risk of deserialising untrusted input.

PRIMARY RESOURCE
Type: Free book chapter · Title: Designing Data-Intensive Applications, chapter 4 — if you have library access; otherwise the free primary is the official documentation for JSON, Protocol Buffers and Apache Avro read side by side
Why this one: reading three schema systems together makes the trade-off visible in a way no single one does — self-describing versus compact, and flexible versus checked.
HANDS-ON · Send an object and watch it not arrive Open a socket between two processes and send an object across it. It will not work, and the reasons arrive in a useful order.

First the object cannot be sent at all — you must decide what its bytes are. Then the receiver gets half a message, or two messages stuck together, because TCP is a byte stream with no notion of where your message ends. You will invent length-prefixing, which is framing. Then you will change the sender's structure by adding a field and discover the receiver breaks — and you will have arrived at schema evolution.

Finally: send a float and a large integer, and check that what arrived is bit-for-bit what left.

The realisation to reach: a network gives you bytes, not messages. Every message boundary you have ever relied on was constructed by software, and you have now constructed one.

CONNECTS TO. Networking (framing is where these meet) · Data Engineering (Avro, Parquet, schema registries) · Distributed Systems (rolling upgrades demand compatibility in both directions) · Security (deserialisation is a classic remote code execution vector).

N8 Testing, debugging, observability

Three different answers to “what is this system actually doing?”

WHAT IT IS. Testing asks the question before deployment against cases you thought of. Debugging answers it after a failure you did not. Observability answers it continuously, in production, for questions you have not yet thought to ask.

WHY IT EXISTS. Because your mental model of the system diverges from the system immediately and permanently. These are the three instruments for measuring that divergence.

DEPENDENCIES. All previous nodes.

SUBTOPICS. Unit, integration and property-based testing · test doubles · the debugger versus print statements · bisection · structured logs, metrics, traces · cardinality · what makes a system “observable” rather than merely monitored.

PRIMARY RESOURCE
Type: Free course · Title: MIT The Missing Semester of Your CS Education — the debugging, profiling and testing lectures
Why this one: free, short, and it teaches the tools nobody teaches — debuggers, profilers, bisection — which are exactly the ones that separate hours of guessing from minutes of knowing.

DEEPER (optional) — the Hypothesis documentation for property-based testing, which will change what you think a test is.
HANDS-ON · Find a bug you did not plant Take any of the earlier hands-on systems, seed it with a subtle fault — an off-by-one in eviction, a lock released too early — and then leave it for a week. Come back and find it using only a debugger and bisection, without re-reading the diff.

Then do the harder version: write a property-based test that asserts something structural rather than specific — “the cache never exceeds its size limit, for any sequence of operations” — and let the framework generate thousands of sequences to try to break it. It will find inputs you would never have written by hand.

The realisation to reach: example-based tests check the cases you already imagined, which are exactly the cases you already handled. Properties check the space you did not imagine.

CONNECTS TO. Infrastructure (metrics, traces, incident response) · Probability (a flaky test is a probabilistic statement) · Psychology (confirmation bias is the main obstacle to debugging).

N9 Design

The only node with no correct answers — which is precisely why it is last.

WHAT IT IS. Deciding where the boundaries go: which things know about which other things, what is hidden behind an interface, and what has to change together.

WHY IT EXISTS. Because requirements change, and the cost of a change is determined almost entirely by how many places must be touched. Design is the discipline of arranging code so that likely changes are cheap and unlikely ones are merely possible.

DEPENDENCIES. Genuine experience of N1–N8. This node cannot be learned first, and attempting to is the most common way engineers waste years.

SUBTOPICS. Coupling and cohesion · interfaces and information hiding · abstraction and its leaks · composition over inheritance · when duplication is cheaper than the wrong abstraction · designing for deletion.

PRIMARY RESOURCE
Type: Free online textbook · Title: SICP (free online edition), chapters 1–2 on abstraction barriers
Why this one: it treats abstraction as something with a cost and a boundary rather than as a virtue, which is the mature version of the idea and rarely taught.

DEEPER (optional) — Parnas, “On the Criteria To Be Used in Decomposing Systems into Modules” (1972, free PDF). Fifty years old, still the clearest statement of why you hide what is likely to change.
HANDS-ON · Change the requirement and count the damage Take the cache from N3 and write down, before touching anything, how many files and functions you would have to modify to make each of these changes: eviction policy becomes pluggable; entries gain a time-to-live; the cache moves to another process; two threads use it.

Now actually make them, one at a time, and count what you really touched. The gap between your estimate and reality is your current design skill, measured.

Then do the thing nobody does: build the same cache twice, once with the eviction policy behind an interface and once inlined, and honestly assess which was better before the requirement changed. The inlined one usually wins on clarity — which is why premature abstraction is so tempting and so costly.

The realisation to reach: design quality is not a property of code, it is a relationship between code and the changes that actually arrive. You cannot evaluate it in the present tense.

CONNECTS TO. Systems Thinking (coupling is structure, and structure produces behaviour) · Business (Conway's law — architecture mirrors the organisation) · Economics (option value of deferred decisions).
