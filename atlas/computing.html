Computing

This domain answers one question: what is actually happening when a machine computes? Everything above it in the stack — software engineering, operating systems, databases, distributed systems — is an abstraction built to hide something in here. You cannot reason about the abstractions until you know what they are hiding.

The single idea. A computer is a machine that can only do two things: move bits between places, and combine bits according to fixed rules. Every other capability — text, images, money, intelligence — is a convention layered on top of those two operations. Most confusion in software comes from forgetting that the convention is a convention.

00 Why this domain exists, and what it is not

Not computer science. Not programming. The machine underneath both.

Programming teaches you to instruct a machine. Computing teaches you what the machine is, which is what lets you predict its behaviour instead of being surprised by it. The difference shows up the day a program is correct but 200× too slow, or produces 0.30000000000000004, or crashes at a recursion depth you did not know existed.

N1 Representation

How meaning is encoded in bits — and what leaks when the encoding is imperfect.

WHAT IT IS. A bit has no meaning. A group of bits means something only because a convention says so. Representation is the study of those conventions: how numbers, text, colours and times are encoded, and precisely where each encoding breaks.

WHY IT EXISTS. Hardware can only hold two states reliably. Everything humans care about must therefore be squeezed into finite sequences of two-state cells — and finite is the operative word. Every representation bug in history comes from the gap between an infinite idea and a finite encoding.

DEPENDENCIES. Positional notation. Nothing else.

SUBTOPICS. Binary and hex · two's complement · integer overflow · IEEE 754 floating point · ASCII, Unicode, UTF-8 and the difference between a character, a code point and a byte.

PRIMARY RESOURCE
Type: Free online textbook · Title: Dive Into Systems, chapters 1–4 · Creator: Matthews, Newhall, Webb
Why this one: it is genuinely free, written for people who program but have never looked underneath, and it treats representation as something you observe rather than memorise.

DEEPER (optional) — “What Every Computer Scientist Should Know About Floating-Point Arithmetic” (Goldberg, free PDF). Read only after the hands-on below makes you angry enough to want it.
HANDS-ON · The number that will not behave Open a Python REPL and evaluate 0.1 + 0.2. It is not 0.3. Now find out why — not by reading, by looking: print the exact stored value with Decimal(0.1), and print the raw bits of the float. Then answer three questions with experiments: which decimals are exact in binary and which are not; what 0.1 + 0.2 == 0.3 should be replaced with; and how big an integer can get before a float can no longer distinguish it from its neighbour.

Then find the real-world consequence: the Patriot missile timing failure of 1991, and the Vancouver Stock Exchange index that drifted downward for two years. Both are this bug, in production, with consequences.

The realisation to reach: floating point is not “imprecise maths”. It is an exact system for a different set of numbers than the one you assumed.

CONNECTS TO. Finance (never store money in a float) · Physics (measurement precision) · Databases (numeric types) · AI (why training uses reduced precision on purpose).

N2 From logic to a machine

The bridge from physics to arithmetic — the one layer that feels like magic until you build it.

WHAT IT IS. How switching elements combine into gates, gates into adders, adders into an arithmetic unit, and how feedback turns a circuit into something with memory.

WHY IT EXISTS. Because “the computer adds two numbers” has to be a physical event. This node is where you stop believing computing is magic, permanently. It is worth doing once, quickly, and never again.

DEPENDENCIES. Boolean logic. Basic electronics helps but is not required.

SUBTOPICS. Truth tables · AND/OR/NOT/XOR · half and full adders · multiplexers · latches and flip-flops · registers · the clock.

PRIMARY RESOURCE
Type: Project course · Title: Nand2Tetris, Part 1 (projects 1–3) · Creator: Nisan & Schocken · Cost: course materials, simulator and projects are free
Why this one: you build a working computer from a single NAND gate upward, in a simulator, with no hardware. This is the rare case where the doing is the learning and reading an equivalent chapter would teach you nothing.

DEEPER (optional) — Ben Eater's 8-bit breadboard computer series (free, YouTube). Watch if you want to see it in physical wire rather than simulation.
HANDS-ON · Build an adder, then discover memory In the Nand2Tetris simulator, build a half adder from NAND gates, then a full adder, then a 16-bit adder. You will notice something uncomfortable: everything you have built forgets instantly. Output depends only on present input. There is no yesterday.

Now wire the output of a gate back into its own input. Something new happens — the circuit holds a value after the input goes away. You have just built memory out of nothing but feedback. Sit with that for a moment; it is the same feedback loop that appears in Systems Thinking, biology and monetary policy.

The realisation to reach: state is not a thing you store. State is a loop.

CONNECTS TO. Electrical & Electronics (the physical switch) · Systems Thinking (feedback creates memory) · Operating Systems (registers are the machine's only true variables).

N3 Architecture

How a sequence of stored numbers becomes behaviour.

WHAT IT IS. The organisation of a processor: registers, the instruction set, and the cycle that fetches an instruction, decodes it, executes it, and moves on. Plus the uncomfortable modern truth that this cycle is no longer sequential.

WHY IT EXISTS. The stored-program idea — that instructions live in the same memory as data — is what makes a computer general rather than a fixed appliance. It is also why software can be a virus, why buffer overflows can execute code, and why a compiler can exist at all.

DEPENDENCIES. N1 (representation), N2 (registers and clocks).

SUBTOPICS. Fetch-decode-execute · the program counter · instruction sets and RISC vs CISC · pipelining · branch prediction · speculative execution and why it created security holes.

PRIMARY RESOURCE
Type: Free online textbook · Title: Dive Into Systems, chapters 5–8 · Creator: Matthews, Newhall, Webb
Why this one: it connects assembly to the C and Python you already write, so the machine stops being a separate subject and becomes an explanation of code you have already run.

DEEPER (optional) — MIT OCW 6.004 Computation Structures (free lecture materials), only if you want to design rather than understand.
HANDS-ON · Make the CPU guess wrong Write a program that sums the elements of a large array, but only those above a threshold — so there is an if inside the loop. Run it twice: once on a sorted array, once on a shuffled array with identical values. Same data, same total, same number of operations.

The sorted version will be several times faster. Nothing about your algorithm changed. Now find out what did: the processor was predicting which way the branch would go, and shuffling made it wrong half the time, throwing away work it had already speculatively started.

The realisation to reach: your instructions are a suggestion. The machine reorders, predicts and speculates — and its guesses are part of your program's performance.

CONNECTS TO. Software Engineering (why micro-optimising the wrong thing fails) · Operating Systems (interrupts, privilege levels) · Everyday Technology (the processor in every device).

N4 The memory hierarchy depth

The most useful node in this entire domain, and the most commonly skipped.

WHAT IT IS. Memory is not one thing. It is a stack of increasingly large, increasingly slow stores — registers, L1, L2, L3, RAM, SSD, network — where each level is roughly an order of magnitude slower than the one above. Performance is mostly determined by which level your data is actually in.

WHY IT EXISTS. Fast memory is expensive and physically small; large memory is far away and light takes time to travel. The hierarchy is the engineering compromise, and caching is how the compromise is hidden from you — until it isn't.

DEPENDENCIES. N3.

SUBTOPICS. Latency at each level · cache lines and why memory arrives in blocks · temporal and spatial locality · prefetching · row-major vs column-major · cache-friendly data layout · false sharing.

PRIMARY RESOURCE
Type: Free paper + interactive reference · Title: “What Every Programmer Should Know About Memory” (Ulrich Drepper, free PDF), read alongside the Latency Numbers Every Programmer Should Know interactive chart
Why this one: the paper is the definitive free treatment, and the latency chart converts abstract ratios into intuition you will use weekly for the rest of your career.

DEEPER (optional) — Dive Into Systems, chapter 11.
HANDS-ON · Find the cache cliff with your own hands Allocate a large array. Walk it with a stride — touch every element, then every 2nd, 4th, 8th, 16th, up to 4096 — and time each pass. Plot time-per-element against stride.

You will not get a smooth curve. You will get a cliff, then a plateau. The location of that cliff tells you your machine's cache line size, in bytes, and you will have measured a physical property of your own hardware without a datasheet.

Then the second experiment: sum a 2D matrix row-by-row, and again column-by-column. Identical arithmetic, identical element count. One is many times slower. Explain the gap in terms of what arrives in a cache line.

The realisation to reach: the layout of your data is often more important than the complexity of your algorithm. An O(n log n) algorithm with terrible locality routinely loses to an O(n²) one with good locality at real-world sizes.

CONNECTS TO. Databases (why columnar storage exists — the same experiment, at disk scale) · Data Engineering (Parquet is this node applied) · Distributed Systems (the hierarchy simply extends across the network) · Economics (caching as inventory near demand).

N5 Stack and heap

Where values actually live, and why that answer changes how you think about variables.

WHAT IT IS. Two regions with different rules. The stack is a fast, automatically managed region that grows and shrinks with function calls. The heap is a large, manually or garbage-collector-managed region where things live for as long as something refers to them.

WHY IT EXISTS. Function-local values have a known, nested lifetime — so they can be managed with a pointer that moves up and down. Values whose lifetime is unknown at compile time cannot, so they need a different region and a different discipline.

DEPENDENCIES. N3, N4.

SUBTOPICS. Stack frames · the call stack and stack traces · the heap and fragmentation · pointers and references · what a “variable” actually is in Python versus C.

PRIMARY RESOURCE
Type: Free online textbook · Title: Dive Into Systems, chapters 6 and 12 · Why this one: it shows the two regions with actual memory diagrams tied to code you run.

DEEPER (optional) — the Python Language Reference on the execution model, which will answer a question you already partly explored in your object-model track: what a name really is.
HANDS-ON · Find the floor of your own call stack Write a recursive function that does nothing but call itself with a depth counter, and run it until it dies. Record the depth. Now add a large local array inside the function and run it again — the depth drops sharply. You have just measured stack frame size experimentally.

Then take a recursive function that overflows, and convert it into an iterative one with an explicit list acting as the stack. It now handles depths thousands of times greater.

The realisation to reach: recursion is not a different kind of computation. It is a loop that borrows a data structure the machine already had — and that structure is small and finite. Once you see this, the entire recursion-versus-iteration debate becomes a memory question rather than a style question.

CONNECTS TO. Software Engineering (references, aliasing, mutability) · Operating Systems (memory layout of a process, virtual memory) · Distributed Systems (why deep call chains become the network's problem).

N6 Execution models

What actually runs when you run your source file.

WHAT IT IS. The spectrum from ahead-of-time compilation to pure interpretation, with bytecode virtual machines and just-in-time compilation in between — and the trade-offs each point makes between startup time, peak speed, portability and introspection.

WHY IT EXISTS. Source code is for humans. Something must translate it. When that translation happens is the whole design space, and it explains why Python is slow, why Java starts slowly but runs fast, and why C gives you speed and segfaults in the same breath.

DEPENDENCIES. N3, N5.

SUBTOPICS. Compilation vs interpretation · bytecode and VMs · JIT · static vs dynamic dispatch · what optimising compilers are permitted to do · undefined behaviour.

PRIMARY RESOURCE
Type: Official documentation + tool · Title: Python's dis module documentation, used as a laboratory rather than read as a reference
Why this one: free, already installed, and it lets you see the bytecode of code you wrote thirty seconds ago. Reading about execution models teaches far less than disassembling your own function.

DEEPER (optional) — Compiler Explorer (godbolt.org, free) to watch C become assembly, and to watch the optimiser delete code you thought mattered.
HANDS-ON · Watch the compiler delete your work Write the same trivial loop — sum 1 to 100 million — in Python and in C. Time both. The gap will be enormous, and the reason is not that “C is faster”: disassemble both and look.

Then, on Compiler Explorer, compile the C version with optimisation on. The loop disappears. The compiler solved it at compile time and emitted a constant. Now try to write a benchmark the compiler cannot optimise away, and notice how hard that is.

The realisation to reach: the machine does not execute your code. It executes a program that is observably equivalent to your code — and “observably” is a specification with edges you should know about.

CONNECTS TO. Software Engineering (why benchmarks lie) · AI (compilation to GPU kernels) · Operating Systems (loading, linking, the ELF format).

N7 Cost and complexity

Reasoning about scale — honestly, including the parts asymptotic notation hides.

WHAT IT IS. A vocabulary for how resource use grows with input size, plus the discipline of knowing when that vocabulary is the wrong tool.

WHY IT EXISTS. So you can predict whether something will survive a hundred times more data before you have a hundred times more data. This is the single most valuable predictive skill in software.

DEPENDENCIES. N4 (because constants come from the memory hierarchy) · basic algebra.

SUBTOPICS. Big-O, big-Θ and what each actually claims · constants and small-n reality · amortised analysis · space-time trade-offs · why measuring beats reasoning past a point.

PRIMARY RESOURCE
Type: Free course · Title: MIT OCW 6.006 Introduction to Algorithms, lectures 1–3 only · Why this one: free, rigorous, and the first three lectures give you the reasoning framework without committing you to a full algorithms course you do not need yet.

DEEPER (optional) — the rest of 6.006, when a real problem demands a real algorithm.
HANDS-ON · Predict the wall, then hit it Write a function with an obvious O(n²) shape — for example, checking for duplicates by comparing every pair. Before running anything, commit a written prediction: at what input size will this take more than ten seconds on your machine?

Now measure at increasing n and find the real wall. Most people are wrong by one to two orders of magnitude, in both directions, and the reason is instructive: constants and cache behaviour dominate until n gets large, and then they suddenly do not.

Then write the O(n) version with a hash set, and find the crossover n where it starts winning. It is higher than you expect — sometimes several thousand — because hashing has constants too.

The realisation to reach: asymptotic complexity tells you who wins eventually, never who wins today. Both questions matter, and only one of them is answerable from a whiteboard.

CONNECTS TO. Software Engineering (data structure choice) · Databases (query planning is automated complexity reasoning) · Probability (average vs worst case) · Economics (marginal cost).
