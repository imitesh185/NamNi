The substrate

Small on purpose. This branch contains only what genuinely gates something above it — and it earns its place because almost every question in it arrives disguised as a question about something else. A Spark tuning question is usually a Parquet layout question. A CDC question is usually a WAL question. An exactly-once question is usually an idempotency question.

The single idea. Nearly every performance and correctness property above this layer is decided by two things: how the bytes are laid out, and which single operation is atomic. Layout decides speed — columnar physical order, encoding, sorting, file size, partitioning. Atomicity decides correctness — table formats, commits, idempotency, exactly-once. The two labs in this branch are one for each half.
#columnar #parquet #atomic-commit #idempotency #wal

00 The one question this branch exists to answer

It sounds like a beginner question. The follow-up is not.

? “Why is Parquet faster than CSV?” Most answers are “it's columnar” or “it's compressed” — both true, both shallow. There are four independent mechanisms: column pruning, predicate pushdown from footer statistics, encoding that exploits a column's type homogeneity, and compression that works because the encoded data is redundant. Naming all four, and knowing which one is doing the work in a given case, is the whole difference.

And then the question that ends the conversation for most people: “when is Parquet slower than CSV?”

The second question belongs to the other half of the branch, and it is the one that separates people who use a lakehouse from people who understand one:

? “Object storage has no transactions. How does your table get ACID?” It does not get it from the storage. It gets it from exactly one atomic operation on exactly one pointer. Everything else — manifests, snapshots, time travel, schema evolution — is elaboration on that single swap. And the half nobody reaches: what operation, and atomic according to whom? The answer is the catalog, not the object store.
The failure mode of this branch Treating it as background reading. L0 is the branch most likely to be skimmed and least likely to be examined directly — which is exactly why it pays: it is the layer where a senior answer to an L2 or L5 question comes from. Both labs here run on a laptop with free tools and produce artifacts within a day. It is the highest ratio of insight to setup cost in the whole Forge.

Three habits to establish before the first lab Measure bytes scanned, not wall time. Wall time is confounded by page cache and by whatever else the machine is doing; bytes scanned is the honest metric, and it is also what cloud billing charges for. Test every format claim at three cardinalities and two sort orders. Encoding effectiveness is almost entirely a function of cardinality and clustering, so a single-dataset result is not a result. Separate planning time from scan time in every measurement. The small-files problem and the over-partitioning problem both live entirely in planning, and averaging them into one number hides them.

B1 Row versus columnar

One decision about physical byte order, and half of analytics performance follows from it.

WHAT IT IS. Whether the bytes of one record are contiguous on disk, or the bytes of one column are.

WHY IT EXISTS. Because storage and network are read in blocks, and the only question that matters is what fraction of each block you actually wanted. An analytical query touches 3 columns of 80; in row layout, every block you read contains 77 columns you are going to discard.

DEPENDENCIES. None.

The framing that makes the rest follow Columnar is not a compression trick. It is a selectivity trick applied to the other axis of the data. Row formats let you select rows cheaply; column formats let you select columns cheaply.

And the compression benefit is downstream of the layout benefit, not a separate one — a column stores values of one type, frequently with few distinct values, often in sorted order. That homogeneity is what makes encoding and compression suddenly effective. Reverse the causality in your head and every Parquet fact stops needing to be memorised.

SUBTOPICS. Physical layout and block-level read amplification · vectorised execution as the natural consequence of columnar storage · why OLTP stays row-oriented · hybrid layouts (PAX) and why Parquet is one · when row wins — point lookups, single-record writes, reading all columns of a narrow table, and any workload where the record is the unit.

PRIMARY RESOURCE
Type: Free paper · Title: "Dremel: Interactive Analysis of Web-Scale Datasets" (Google, 2010)
Why this one: free, short, and it is the direct ancestor of Parquet — the repetition and definition level scheme in section 4 is the answer to "how does a columnar format store a nested array", which is otherwise mysterious.

DEEPER — the C-Store paper (2005, free) for the original columnar database argument, including the parts about compression and late materialisation that Parquet did not adopt.
OBSERVATION · The ratio, measured Write the same table as CSV and as Parquet. Run SELECT one_column and then SELECT *, measuring bytes read for each.

For one column of eighty, the ratio is enormous. For SELECT * it collapses to roughly one — and with decode cost included, Parquet can lose. That is the answer to "when is Parquet slower", produced in ten minutes rather than argued about.

CONNECTS TO. B2 · Databases N3 · Computing N4 — the stride cliff is this same phenomenon at cache-line scale, and recognising them as one idea is the point of having an Atlas.

B2 Parquet, opened up spine

File → row groups → column chunks → pages → encoded values. Plus a footer that changes everything.

WHAT IT IS. A file is divided into row groups (a horizontal slice of rows), each containing one column chunk per column, each divided into pages which carry the encoding. The footer holds the schema and, per row group per column, the min, max and null count.

WHY IT EXISTS. Row groups make the file splittable across parallel tasks. Column chunks make pruning possible. Pages give a unit of decode. And the footer lets an engine decide not to read data at all — which is the only optimisation that beats reading data quickly.

DEPENDENCIES. B1.

MechanismWhat it savesWhat it requires to work
Column pruningReading columns you did not selectNothing. It is free and always on
Predicate pushdown via footer statsReading entire row groupsData clustered by the predicate column
Encoding — dictionary, RLE, bit-packing, deltaBytes, before compression even runsLow cardinality, or sortedness, or both
CompressionBytes, at a CPU cost paid on every readRedundancy — which encoding has usually already exploited
The most valuable Parquet fact, and almost nobody states it Footer statistics only prune if the data is sorted or clustered by the predicate column. On an unsorted column, every row group's min–max spans nearly the whole domain, so every row group matches every predicate and the statistics are present, correct, and completely decorative.

This is why "we converted to Parquet and it barely helped" is a common and entirely explicable complaint — and why sorting is a performance decision at least as large as format choice. Lab 01 experiment 5 exists to make you see the min–max ranges collapse.

SUBTOPICS. Row group sizing as the central knob — too small and metadata dominates and compression suffers, too large and pruning gets coarse · page size and page-level statistics · dictionary encoding and dictionary fallback when cardinality is too high · RLE and bit-packing · delta encoding for sorted integers and timestamps · definition and repetition levels for nested data · bloom filters in the footer · column indexes and page skipping.

PRIMARY RESOURCE
Type: Free specification · Title: the Apache Parquet format specification on GitHub, plus the encodings document
Why this one: free, and short enough to read completely. Reading a format specification rather than a tutorial is itself the transferable skill — it is how you will answer questions about formats that did not exist when you learned this.

DEEPER — the Dremel paper again for repetition and definition levels, which the specification states but does not motivate.
OBSERVATION · Watch the statistics become useful Dump a file's footer with parquet-cli meta. Note the row group count, the encoding chosen per column, and the min–max for your filter column in each row group. They will span almost the entire domain.

Now rewrite the file sorted by that column and dump it again. The ranges collapse into narrow, disjoint bands. Nothing about the format changed, nothing about the query changed — but the engine can now skip most of the file, and you watched the moment it became able to.

B3 Compression and splittability

A trade between bytes you store once and CPU you spend on every single read.

WHAT IT IS. The codec applied to pages inside a columnar file, or to the whole file in the case of raw text.

WHY IT EXISTS. Because storage is cheap and network is not, and because a smaller file is a faster read until the decode cost exceeds the transfer saving.

DEPENDENCIES. B2.

The classic, and it still happens weekly A gzipped CSV is not splittable. A 10 GB .csv.gz is exactly one task, on one core, regardless of how large your cluster is. You can add a hundred executors and the job will not get one second faster.

Inside Parquet this disappears entirely, because compression is applied per page and the row group boundaries remain visible in the footer. Which means splittability stops being a codec decision the moment you stop storing compressed text — and that reframing is the actual lesson.

SnappyModerateVery fastThe historical default, and still fine for hot data
Zstd (level 1–3)Better than gzipNear SnappyIncreasingly the correct default — better ratio at similar speed
GzipGoodSlowArchives read rarely. You pay the decode forever otherwise
LZ4WorstFastestIntermediate shuffle data, where it is written and read once

PRIMARY RESOURCE
Type: Free documentation + your own measurement · Title: the Parquet compression documentation, and then Lab 01 experiment 2
Why this way: published codec benchmarks are close to worthless for this decision because the ratio depends entirely on your data's cardinality and sortedness. The transferable skill is the measurement procedure, not the numbers.
OBSERVATION · Break-even read count For each codec record three numbers: file size, write time, and decode time per query. Then compute how many reads it takes for a better ratio to repay its extra CPU.

For a table read a thousand times a day the answer is "immediately"; for a landing zone read once it is "never". Same data, opposite correct answers — which is why the question "which codec should we use" has no answer without the read count.

CONNECTS TO. B4 · L2 S11 · L8 cost.

B4 Avro, ORC and format choice

Two formats, one rule, and a stack that correctly uses both.

WHAT IT IS. Avro is row-oriented with an embedded schema and first-class schema evolution — the natural format for records arriving one at a time. ORC is columnar, Parquet's closest peer, with stronger built-in indexes and native ACID inside Hive.

WHY IT EXISTS. Because the boundary of a data system has different requirements from its interior. At the edge, records arrive singly and schemas change; in the middle, queries read few columns of many rows.

DEPENDENCIES. B1.

The decision rule Row format where records arrive one at a time and the schema moves. Columnar format where queries read few columns of many rows. An Avro landing zone feeding a Parquet curated layer is not indecision — it is the correct answer, and being able to say why in one sentence is worth more than an opinion about which format is better.

SUBTOPICS. Avro's writer/reader schema resolution and what makes a change compatible · why Kafka Connect writes Avro · the Schema Registry's compatibility modes as the enforcement of this · ORC stripes, stripe footers and per-stripe bloom filters · where ORC genuinely wins · why Parquet won the ecosystem argument regardless.

PRIMARY RESOURCE
Type: Free specifications · Title: the Apache Avro specification, schema resolution section, and the ORC specification
Why this one: free, and Avro's schema resolution rules are the concrete definition of "compatible change" that L6 data contracts otherwise discusses in the abstract. Reading them here means L6 arrives as a policy question rather than a technical one.
OBSERVATION · Opposite winners Write the same data as Avro and as Parquet, then measure three things: total size, time to append a single record, and time to SELECT one column. Each format wins two of three, and loses the other by roughly the margin it won by. That symmetry is the whole of format selection, made concrete.

CONNECTS TO. L3 K11 Schema Registry · L6 data contracts · B5.

B5 Open table formats — the metadata tree

A table stops being a directory and becomes a data structure.

WHAT IT IS. Iceberg, Delta and Hudi. In Iceberg's shape: a catalog pointer → a metadata file → a manifest list (which is a snapshot) → manifests → data files, each entry carrying per-column statistics.

WHY IT EXISTS. Because "a table is a directory of Parquet files" fails four ways at once: no atomicity, no snapshot isolation, listing millions of objects is slow and was historically not even consistent, and any schema or partition change means rewriting everything.

DEPENDENCIES. B2 · B4.

The three tricks worth extracting 1. Statistics live in the manifest. Planning prunes files without opening a single one — a directory table must list, then open, then decide. This is why Iceberg planning scales and Hive-style partitioning does not.
2. Columns are tracked by ID, not by name or position. That single decision is what makes renaming a column free, and reordering safe, where a directory of Parquet would need a rewrite.
3. The partition spec is versioned. Old data keeps the spec it was written with, so partitioning can change without rewriting history — and hidden partitioning means a user filtering on ts gets the pruning automatically, which eliminates the single most common Hive-era bug: the accidental full scan caused by a forgotten dt= predicate.

SUBTOPICS. Snapshots, manifest lists and manifests · time travel as "keep the old manifest list", costing metadata rather than data · snapshot expiry and orphan file cleanup · schema evolution by column ID · partition evolution and hidden partitioning · copy-on-write versus merge-on-read and which read/write cost you would rather pay · Delta's transaction log and checkpoints as the same idea with different file names.

PRIMARY RESOURCE
Type: Free specification · Title: the Apache Iceberg table specification
Why this one: free, and unusually readable for a spec — it states the metadata tree, the commit protocol and the evolution rules precisely enough that you can reimplement a subset, which is exactly what Lab 02 asks you to do.

DEEPER — the Delta Lake VLDB paper (free). Reading both makes the shared mechanism obvious and the differences look like the implementation details they are.
OBSERVATION · Walk the tree by hand Create an Iceberg table, insert three times, then open the metadata directory and follow it manually: pointer → metadata JSON → manifest list → manifest → data file entries with column statistics.

Now delete a single row and look again. A new snapshot exists; no previously written file was modified. Every guarantee this format offers follows from that one observed fact.

CONNECTS TO. B6 · B7 · L6 governance — deletion in an immutable architecture is this node's consequence.

B6 Atomic commit on object storage spine

The single most reusable idea in the substrate, and it is one sentence long.

WHAT IT IS. Write all new data files where nothing points at them. Write the new metadata. Then atomically swap one pointer from the old metadata to the new. Readers who resolved the pointer before the swap see the old snapshot, consistently and completely. Readers after see the new one. Nobody, at any moment, sees a mixture.

WHY IT EXISTS. Because the storage layer offers no transaction, and none is needed — a single atomic operation on a single pointer is sufficient to build snapshot isolation over an arbitrarily large set of non-atomic writes.

DEPENDENCIES. B5 · B8.

The half that separates a real answer from a memorised one What is atomic depends on the catalog, not on the object store. S3 for most of its life had no compare-and-swap on an object, so the atomicity came from elsewhere: a Hive metastore transaction, a DynamoDB conditional put, a Glue update, a row in Postgres, or — more recently — conditional writes in S3 itself.

The commit is a compare-and-swap: “set the pointer to N+1 only if it is still N”. If it fails, the writer replans and retries. That is optimistic concurrency control, and it is the same mechanism as write-conflict detection in MVCC — arriving from a completely different direction.
One shape, four industries Write to a temporary location → flush → atomically rename.

That is a safe file write (the write path). It is a database commit — write the WAL, fsync, flip the commit record. It is an Iceberg snapshot. It is a blue-green deployment — build the new stack, flip the load balancer. Four industries, one idea, and recognising it is worth more than any individual fact in this branch.

SUBTOPICS. Optimistic concurrency and the retry loop · what the writer must re-plan on conflict, and why it is usually not a data rewrite · conflict granularity — file-level rather than table-level, which is why two writers to different partitions both succeed · orphan files after a crashed write, and why they are garbage rather than corruption · the reader's view and how long a snapshot stays valid · why this is snapshot isolation and not serialisability.

PRIMARY RESOURCE
Type: Free specification · Title: the Iceberg specification's commit and conflict-resolution sections, plus the Delta transaction protocol document
Why both: free, and they solve the identical problem with different vocabulary. Reading two independent solutions to one problem is how you learn the problem rather than the solution.

B7 Compaction and the small-files problem

Where partitioning strategy stops being a modelling question and becomes a cost line.

WHAT IT IS. The disproportionate cost of many small files. Each one costs a metadata entry, a request, an open, a footer read and usually a task — none of which scale with its size.

WHY IT EXISTS. Because streaming and micro-batch writers create at least one file per partition per batch. A job writing every five minutes into 200 partitions produces 57,600 files a day, all of them tiny, and every one of them costs the same fixed overhead as a good one.

DEPENDENCIES. B2 · B5.

The mirror-image mistake Over-partitioning. Partitioning on a high-cardinality column — a user ID, or a timestamp truncated to the minute — produces one small file per partition and turns query planning into a directory-listing exercise.

The rule has two conditions and people apply only the first: partition on a column that appears in most queries' predicates and whose cardinality is low enough that each partition holds a sensible amount of data. A column that satisfies one but not the other is a trap, and high-cardinality filter columns should be handled by sorting, not partitioning.

SUBTOPICS. Target file size and why 128 MB–1 GB is the usual band · compaction and rewrite maintenance jobs · write-side coalescing versus after-the-fact compaction · clustering, sorting and Z-ordering as the alternative to partitioning · why sorting is what makes footer statistics selective, which loops directly back to B2 · compaction's interaction with snapshot retention and time travel.

PRIMARY RESOURCE
Type: Free documentation · Title: the Iceberg maintenance documentation — rewrite data files, rewrite manifests, expire snapshots, remove orphan files
Why this one: free, and it enumerates the four maintenance operations every lakehouse needs. Knowing that a table format requires scheduled maintenance at all is a distinguishing piece of operational knowledge — plenty of people deploy one and never run any of it.
OBSERVATION · Separate planning from scanning Write identical data as 10,000 small files and as 100 right-sized ones. Same bytes, same rows, same query.

Measure planning time and scan time separately. Most of the difference is in planning — listing, opening and reading footers — before a single byte of actual data has been read. Averaging the two into one number is how this problem stays undiagnosed for years.

CONNECTS TO. L1 physical design · L2 S11 · L4 W12 — a streaming writer is the most common cause of this, and it is one more reason to ask whether streaming was needed.

B8 Partial failure and idempotency spine

The distributed-systems minimum for a data engineer, and it is smaller than people fear.

WHAT IT IS. A request that times out has three possible truths: it never arrived; it arrived and failed; it arrived, succeeded, and the response was lost. The caller cannot distinguish them.

WHY IT MATTERS. Because that is not an engineering gap to be closed — it is a proof. Therefore retrying is the only available action, therefore duplicates are guaranteed, therefore the only durable answer is to make the operation safe to repeat.

DEPENDENCIES. None.

The sentence this node exists to install Exactly-once delivery is impossible. Exactly-once effect is achievable — and the difference is where the work goes.

Delivery is the network's problem and the network cannot solve it. Effect is your problem, and you can. Every "exactly-once" claim in L3, L4 and L5 is an instance of this one sentence, which is why it belongs at the floor rather than in any of them.

SUBTOPICS. The undecidable timeout · at-most-once, at-least-once and effectively-once · the idempotency toolkit — natural keys, deterministic derived keys, overwrite-by-partition instead of append, upsert on a business key, absolute values instead of deltas, a dedup table with a bounded window · why coordination costs round trips · designing so that agreement is unnecessary, which is cheaper than making agreement fast · retry storms and why naive retries make outages worse.

PRIMARY RESOURCE
Type: Free lecture notes and videos · Title: Martin Kleppmann's Distributed Systems course (University of Cambridge) — full notes and lecture videos, free
Why this one: free, rigorous, and it covers exactly the parts a data engineer needs — failure models, time, ordering, replication — without descending into consensus implementation, which the Forge deliberately excludes.

DEEPER — "A Note on Distributed Computing" (Waldo et al., free). Thirty years old and still the clearest statement of why the network cannot be abstracted away.
OBSERVATION · Make the duplicates appear, then make them stop Write to a sink through a proxy that drops the response after the write has already succeeded. The client times out and retries, exactly as any correct client would. Count the rows.

Now add an idempotency key and an upsert, and repeat with the same fault injection. The row count stops changing while the network keeps failing. That is the entire idea, demonstrated in under an hour, and it is the foundation of three branches above this one.

CONNECTS TO. L3 K8 · L4 W9 · L5 backfills · Distributed Systems N7.

B9 Query planning, statistics and join algorithms

Learn the shape once here, and Catalyst becomes an instance rather than a subject.

WHAT IT IS. The pipeline every SQL engine runs: parse → resolve → logical plan → rule-based optimisation → cost-based optimisation → physical plan. Plus cardinality estimation, which is the input cost depends on.

WHY IT IS HERE. Because Catalyst, Trino's planner, Postgres's planner and DuckDB's planner are all the same shape. Learning it once at the floor turns L2 S5 into "the Spark version of a thing I know" rather than a new subject.

DEPENDENCIES. None.

The load-bearing fact about cost-based optimisation A cost model is only as good as its cardinality estimates, and cardinality estimates degrade catastrophically as joins are added — because errors compound multiplicatively down the plan.

This is why a plan that is excellent for three tables is frequently terrible for ten, and it is the actual reason hints, materialised intermediate results and adaptive execution exist at all. AQE is not a clever feature; it is an admission that the estimates were never going to be good enough.

PRIMARY RESOURCE
Type: Free documentation · Title: the PostgreSQL documentation on query planning and EXPLAIN
Why this one: free, and it is the best planner documentation that exists — it explains the cost model, the statistics it depends on and how to read the output, all against an engine you can run locally in a minute.

DEEPER — Selinger et al., 1979 (free). The origin of cost-based optimisation, and short enough to read in a sitting. Everything since is a refinement of it.
OBSERVATION · Watch the estimates fall apart EXPLAIN ANALYZE a three-table join in Postgres or DuckDB and compare estimated rows against actual rows at every node. Then add tables one at a time.

The divergence grows fast, and seeing it with your own eyes is the single most useful thing in this node — because it explains why optimisers fail, why they fail specifically on large joins, and why intervening is sometimes correct rather than a hack.

B10 B-tree, LSM, MVCC and the WAL

What the source system is doing, to the exact extent that it constrains you.

WHAT IT IS. The four database internals that determine what a data engineer can extract and which guarantees are inherited rather than chosen.

WHY IT IS HERE. Because CDC is not a query — it is a replication client, and understanding what it reads is the difference between operating one and hoping.

DEPENDENCIES. None.

01 Laboratory — Format Forensics

The same query, on the same data, ten times slower. Nothing changed but how the bytes were written.

PROBLEM. One benchmark query — filter on a timestamp, group by a low-cardinality column, aggregate two numeric ones — against roughly 10 GB of real data. Make it as fast as it can be, and know exactly which decision bought which fraction of the improvement.

INITIAL SYSTEM. The dataset as a single gzipped CSV. A fixed query. Measurement of bytes scanned, planning time and scan time as three separate numbers.
FAILURE TO INTRODUCE — four escalations 1. The query takes minutes and uses one core. Gzipped CSV is unsplittable — the whole file is a single task, and every byte of every column is read and parsed.
2. Convert to Parquet. Much faster — but check the footer: the statistics prune nothing, because the data is unsorted and every row group's min–max spans the domain.
3. Sort by the filter column. Row groups are now skipped and bytes scanned collapses. This is the biggest single win, and it is not a format change.
4. Partition by a high-cardinality column to "help". Planning time explodes and the total gets worse than step 2.

CONCEPTS THAT EMERGE. Splittability → columnar layout → column pruning → footer statistics → the clustering dependency that makes them useful → encoding as a function of cardinality → codec ratio versus decode cost → row group sizing → partition cardinality → planning cost as a distinct quantity from scan cost.

#ExperimentWhat it isolates
1CSV, JSON, Avro, Parquet, ORC — same data. Size, write time, bytes read for the queryThe format baseline, measured rather than assumed
2Codec sweep on Parquet: none, snappy, gzip, zstd(1), zstd(9), lz4. Size, write time, decode timeCompute the break-even read count

8Partition by a low-cardinality column, then a high-cardinality oneOver-partitioning, in file count and planning time

WHAT TO OBSERVE. Bytes scanned above everything else. Row groups skipped. Footer statistics before and after sorting. Planning time and scan time kept apart. The artifact is a layout decision table — format × codec × sort order × row group size → bytes scanned, query time, write time, storage size.

THE RESULT WORTH CARRYING. "Sorting by the predicate column reduced bytes scanned twelvefold. Changing the compression codec changed it by a factor of 1.3." Layout beats codec by an order of magnitude — and the codec is what everybody tunes.

REAL-WORLD CONNECTION. Every "our warehouse bill is too high" investigation, because the bill is bytes scanned. And every "we moved to Parquet and it barely helped" complaint, which this lab explains completely.

PORTFOLIO VALUE. High, and unusually cheap — a laptop, DuckDB and a public dataset. It is a measurement study, which reads very differently from a pipeline demo.

The data structure this lab forces A Parquet footer statistic is a zone map — a min–max index over a block — and its effectiveness is entirely a function of clustering. It is the same structure as a database's BRIN index, and it plays the same role that a bloom filter plays in an LSM read: cheap metadata consulted first so that expensive data can be skipped entirely.

02 Laboratory — Atomic Commit on Object Storage

A reader sees half the old files and half the new. Then you rebuild Iceberg from first principles.

PROBLEM. A table is being replaced while it is being read. The reader must never observe a mixture of old and new state.

INITIAL SYSTEM. A "table" that is a directory of Parquet files. A writer that deletes the old files and writes new ones. A reader in a loop that lists the directory, reads everything, and checks an invariant that must always hold — for instance, that the sum of all account balances equals a known constant.
FAILURE TO INTRODUCE The invariant fails during every write window. Not intermittently — reliably, and for a longer interval than anyone expects.

Nothing logs an error. Nothing is wrong from the file system's point of view. The query succeeded, returned rows, and the numbers were false. This is the exact failure mode that makes silent data corruption so much worse than a crash.

THEN BUILD THE FIX YOURSELF, in four versions, before touching Iceberg:

VersionWhat you addWhat it still gets wrong
v1Write new files under new names; swap a CURRENT pointer file. Readers resolve the pointer firstTwo concurrent writers overwrite each other's pointer — a lost update
v2Compare-and-swap on the pointer: set to N+1 only if still N. Loser replans and retriesOld data files accumulate forever
v3Retain old pointersYou have just built time travel, as a side effect of doing nothing
v4Delete data files only when no retained pointer references themNothing. You have derived snapshot expiry, and with it, Iceberg

CONCEPTS THAT EMERGE. Non-atomic multi-file writes → indirection through a pointer → compare-and-swap → optimistic concurrency and the retry loop → conflict granularity → snapshot isolation → time travel as retained metadata → garbage collection versus deletion → orphan files as garbage rather than corruption.

#ExperimentWhat it isolates
1Directory-as-table with a concurrent reader. Measure how often and for how long the invariant breaksQuantify the inconsistency window
2Add the CURRENT pointer. Measure the remaining windowIndirection alone gets you most of the way
3Two writers, plain pointer overwriteLost update, reproduced
4Compare-and-swap commit. One wins, one retries — show it in the logsOptimistic concurrency, built by hand
5Kill the writer between writing data files and swapping the pointerThe table is untouched; the orphans are invisible. Garbage, not corruption
6Retain old pointers; read pointer N−2Time travel, for free
7Expire snapshots and delete unreferenced files; then try to time travel past the expiryWhy retention is a policy with a hard edge
8Switch to real Iceberg. Repeat experiments 1, 4 and 5Identical behaviour — your model was right
9Walk Iceberg's metadata tree and map every file to the piece you builtRecognition rather than memorisation
10Two Iceberg writers committing to different partitions simultaneouslyBoth succeed — conflict detection is at file level, not table level

WHAT TO OBSERVE. The length of the inconsistency window in v0 — it is larger than intuition suggests. That the CAS retry re-plans rather than rewrites data. That a crashed writer leaves waste but never a wrong answer. The artifact is roughly two hundred lines of your own transactional table format, plus a mapping from each of its parts to Iceberg's.

REAL-WORLD CONNECTION. This is the mechanism underneath every lakehouse in production. And it is the same shape as a database commit and a blue-green deployment — write the new thing where nobody is looking, then flip one pointer.

PORTFOLIO VALUE. Very high, and rare. "I implemented ACID over object storage from first principles, then verified my model against Iceberg" is not a claim that can be produced by following a tutorial, and it is provable in a repository of a few hundred lines.
