The write path

These are not lecture notes. Every claim below was produced by writing a naive program, killing it two different ways, and reading what was left on the disk. Several of the claims contradicted what we predicted, and one contradicted what the guide asserted — that one was settled by checking the artifact, which is the only authority that counts here.

The whole thing in one sentence. A call that looks like one operation is really several, with different owners and different failure semantics. out.write(...) does not put anything on a disk. It puts bytes in a buffer that belongs to your process, and your process is the thing most likely to die.

00 Where this came from

No concept was introduced because it was next. Each one arrived because a program lied.

The setup

A ten-item loop. Each iteration writes one line to a file and prints processed item N. Twelve lines of code, deliberately naive — no error handling, no cleanup, the file opened once outside the loop.

The question

Kill it at item 5 — once with Ctrl-C, once with taskkill /F. The console said processed item 5 both times. Was the console telling the truth?

Method Predictions committed in writing before running, in a gate that refuses to execute the program until they are filled. An unpredicted result is a data point. A result that contradicts a written prediction is a finding.

01 A write is an intention, not a fact

The console was lying, and it was lying about something specific.

The instinct is that out.write(...) puts data on the disk, and that if the program said it happened, it happened. Both halves are false, and they are false for the same reason.

The finding Data survives a crash only if it has crossed out of the dying thing's control before the crash. A write still sitting inside your process is not a write — it is an intention. The print reported the intention, never the crossing.

Which reframes the whole problem. You cannot make a false statement verifiable by inspecting it afterwards — checking the file's size after the fact is checking too late, and from the wrong side. You reorder instead: force the crossing to happen before you make the claim, and the claim becomes incapable of being false.

02 Three stages, two boundaries

"On disk" is not one place. It is three, and they have different owners.

Why buffering exists at all Crossing into the kernel is a syscall — expensive. Batching thousands of small writes into one crossing is why writing a line at a time is not catastrophically slow. The buffer is not a bug; it is a bargain, and the price is the window in which your data exists only in a place that dies with you.

03 Which calls actually cross

The boundary is not "file operations". It runs between specific calls, and you have to know which.

You callWhat it really isReaches the kernel?
open(path, "a")a syscallImmediately. The directory entry is created right there.
out.write(s)a copy into your own bufferNo. Usually not until the buffer fills or is flushed.
out.flush()a syscallYes. Pushes stage 1 → stage 2.
os.fsync(out.fileno())a syscallYes, and forces stage 2 → stage 3 before returning.
out.close()flush, then releaseYes — but only if it is reached.
The asymmetry that surprised us A hard-killed run left behind a file that existed and was zero bytes. The prediction "the file will not exist at all" was wrong. Opening announced the file to the kernel instantly; the contents never crossed. Metadata and contents travel on different schedules.

Order matters between the two crossings, and it only works one way:

out.write(f"item {i} done\n")   # stage 1 only
out.flush()                       # stage 1 -> 2
os.fsync(out.fileno())         # stage 2 -> 3

Calling fsync without flushing first is useless: it orders the kernel to write out what it holds, and the kernel does not hold bytes that are still in your process. You cannot skip the first crossing to get to the second. Note also that fsync takes the file's integer OS handle, not the Python file object — the two live on opposite sides of the boundary, and the API says so.

04 The two deaths

The difference has nothing to do with threads, ports or process trees. We predicted that it did. It doesn't.

Ctrl-C — a death you can react to

Delivers an interrupt Python is allowed to handle. It raises KeyboardInterrupt, the exception propagates, and the interpreter shuts down in an orderly way. During shutdown the file object is finalized, and finalizing flushes it. The program got to execute more code on its way out.

taskkill /F — a death you cannot

The OS terminates the process outright. Zero Python code runs. No handler, no finally, no finalizer, no cleanup. Stage 1 was your process's own memory, and it is gone with the process. Stages 2 and 3 never heard about the item.

The question that unlocks it Not "which processes die". What is one kind of death allowing the program to do that the other isn't? Every cleanup mechanism in Python — finally, with, __del__, atexit — is code, and code needs a running process. A guarantee that depends on your own cleanup running is not a guarantee against a hard kill.

Same program, same kill, three write policies. Real numbers from real runs.

And separately, the naive program interrupted with Ctrl-C at item 5 kept items 0–5 — the same policy that lost everything under a hard kill. The write policy did not change. The kind of death did.

Prediction ledger naive → empty: predicted, correct.  flush → survives: predicted, correct — this is the core result.  flush vs sync: not predicted; recorded honestly as "unable to say", which is a better entry than a guess dressed as an answer.

06 Which disaster each call covers

Identical files are not evidence that fsync does nothing. They are evidence we simulated the wrong disaster.

taskkill /F kills your process. It does not scratch the kernel — the kernel keeps running, still holding your bytes, and writes them out when it feels like it. So once flush() pushed the bytes across the first boundary, your process became irrelevant to their survival. Forcing the second crossing changes nothing unless the thing that dies is the kernel itself.

CallProtects againstDoes nothing aboutCost
flush()process death — kill, crash, exception, bugpower loss, kernel paniccheap: one syscall
fsync()machine death — power cut, panic, VM destroyednothing further; this is the strong oneexpensive: waits for hardware
Honest limit of this experiment flush is genuinely testable — you can kill a process. fsync is not testable this way; proving it would require cutting power to the machine mid-write. Knowing which disaster your test actually simulates is worth more than the result of the test.

This is why "make it durable" is a throughput decision, not a correctness checkbox. Syncing per record means waiting on hardware per record. Every serious system exposes this as a knob rather than choosing for you.

07 Empty is worse than absent

The hard kill produced the expensive kind of failure, not the cheap kind.

LOUD No file

Downstream asks "is the output there?" → no → fails immediately. Someone is paged, the run is retried. Annoying, cheap, contained.

QUIET Empty file

Downstream asks "is the output there?" → yes → proceeds with zero rows, computes a total of zero, and reports success. No error anywhere. This is the kind that reaches production and stays there.

The check that fails "The output path exists, therefore the job succeeded" is a real check that real pipelines really make, and a zero-byte file defeats it. Existence of an artifact and validity of an artifact are separate claims, and nothing about a filename tells you the second one.

08 The thirteenth byte

A small one, found by dividing file sizes and getting a non-integer.

item 0 done\n is 12 characters. The file measured 13 bytes per line. On Windows, a file opened in text mode translates \n into \r\n on the way out. The runtime silently rewrote the data.

Why it matters beyond trivia It is the reason CSV files get mangled crossing between Windows and Linux, and why the csv module tells you to open files with newline="". Your program's idea of what it wrote and the disk's idea of what it holds are not the same thing — the same lesson as the rest of this page, arriving from a different direction.

09 Traps we actually hit

Three mistakes, all made for real. The first inverted a correct result into a wrong conclusion.

T1 · Stale state read as fresh output — cost: a wrong conclusion

The file was opened in append mode and not deleted between runs. After the hard kill wrote nothing, reading the file showed the previous run's data — so the hard kill looked like it had preserved everything, the exact reverse of the truth. The prediction had been correct all along.

Detected by arithmetic, not by intuition: two surviving runs would have left twelve lines. There were six. Exactly one run had ever flushed, and a hard-killed process cannot be the one that did.

The lesson is the project "Is this output from this run or the last one?" is not a testing-hygiene footnote here — it is the central question of the whole project, reproduced by accident in its own harness. Every mode now writes to its own file.

T2 · out.fsync() does not exist — cost: one dead run

Written by pattern-matching the out.flush() line above it, despite the instruction stating it was a function in os that takes the integer handle, not a method on the file object. The run died with AttributeError at item 0.

Three signals said so and all three were initially missed: the Python command exited with code 1; the follow-up taskkill also exited 1 because the process was already gone; and the file held exactly one line, written by the flush immediately before the crash. Those bytes were not a result. They were wreckage.

T3 · Comparing runs killed at different points — cost: an invalid comparison

One mode was killed at item 1, another at item 0. Different byte counts, no conclusion available — the variable under test was not the only thing that varied. Re-run with the kill at a fixed item, the two modes came out identical, and only then did the comparison mean anything.

10 The model, restated

Everything above, compressed to the seven statements worth carrying away.

#What is now settled
1There are three stages — Python's buffer (yours), the OS page cache (the kernel's), the disk. Only stage 1 dies with your process.
2The hard-killed file existed because open() is a syscall and created the directory entry at once. It was empty because write() only filled a buffer inside the process, and that buffer died with it.
3Ctrl-C raises an exception the program is allowed to handle, so shutdown code runs and the file is flushed during finalization. taskkill /F runs no Python at all. The difference is whether the dying program gets to execute anything.
4flush and fsync came out identical because the kill destroyed only the process, and flush had already handed the bytes to the kernel. Separating them would require killing the kernel — a power cut.
5fsync without a prior flush is useless: the kernel can only write out what it holds, and unflushed bytes are still sitting in your process.
6A zero-byte file defeats the check "does the output exist?" — it answers yes, so downstream proceeds with no rows and reports success. A missing file would have failed loudly and cheaply.
7The ordering rule: make it true before you say it. A claim cannot be verified after it has been published — force the crossing first, then print.

11 Where this shows up in real work

Five things that look unrelated and are one model.

Kafka acks

acks=0 / 1 / all is a producer choosing which stage counts as written. It is the same axis as write / flush / fsync, spelled with brokers instead of buffers. send() returning is not delivery.

Spark's commit protocol

Tasks write to a temporary location and commit by atomic rename, then drop a separate _SUCCESS marker. Spark does not trust the output directory either — because existence is not validity, exactly as §07 found.

Database group commit

Syncing per transaction means waiting on hardware per transaction. Databases batch many commits into one fsync for the reason in §06: the strong crossing is expensive, so you amortise it rather than skip it.

Write-ahead logging

Record the intention durably before performing the change, so a crash leaves something that can be replayed. It is §01's rule turned into a storage design: never claim before the crossing.

The interview version "How does Spark guarantee exactly-once output when a task dies mid-write?" is answerable from this page without having memorised anything about Spark — stages, owners, crossings, atomic rename, marker file. One model, generating the answer on demand, beats five remembered facts.

If the program's word is worthless, the artifact has to carry the truth. That forces a self-describing record format: markers, and a way for a reader to tell a complete record from a truncated one without trusting anything external.

A second run reads the log and resumes where the first died. That requires holding "what have I already done" across calls — state with an owner and a lifetime. That pressure, and not a syllabus, is what will introduce classes.
