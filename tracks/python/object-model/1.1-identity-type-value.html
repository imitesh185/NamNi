Objects: Identity, Type, Value

Python does not manipulate variables. It manipulates objects, and it reaches them through names. Almost every confusing behaviour you will ever meet in this language — aliasing, mutability, hashability, the is/== split, why len(x) is a function and not a method — resolves cleanly once you hold a precise model of what an object is. This drill installs that model, and nothing else.

Scope discipline. This is one concept, drilled to the bottom. Not five. You will finish it able to state, for any expression in any Python program, exactly what objects exist and which of their three properties can change. Everything after this stage is a consequence of this stage.

01 The one claim

Six words from the language reference that the whole stage unpacks.

“ “Every object has an identity, a type and a value.” The Python Language Reference, §3.1 — Objects, values and types. That sentence is not a friendly summary. It is a closed enumeration: there are three properties, there is no fourth, and each behaves differently under change.
PropertyHow you observe itCan it change?What "no" buys you
Identity id(x), compared by is Never — for the object's entire lifetime You can hold a reference and know it still means the same thing later.
Type type(x) Effectively never; treat as fixed Every operation on the object can be dispatched without re-checking anything.
Value no universal accessor Sometimes. That is the definition of mutable. —

Read the third row again. There is id() for identity and type() for type, and then there is nothing for value. That absence is not an oversight; it is the single most important design fact in this document, and §04 is about it.

02 Identity — and the qualifier everyone skips

Four words in the docs turn a "unique id" into a landmine.

LANGUAGE id(x) returns an integer "guaranteed to be unique and constant for this object during its lifetime."

Read the qualifier During its lifetime. The docs continue: "Two objects with non-overlapping lifetimes may have the same id() value." Ids are not globally unique and never were. An id is only meaningful while you are holding a reference to the object — which means the act of asking for an id and then dropping the object destroys the answer's validity.
CPython detail In CPython, id(x) is the memory address of the object. That is why freed addresses get handed straight back to the next allocation, which is what produces the trap above. PyPy does not do this — objects can move, so PyPy synthesises a stable fake id on demand. Code that treats an id as an address is CPython-only code.

The practical rule this generates

is asks "same object?". == asks "same value?", and it asks the object's type to decide. They answer different questions, so they are not interchangeable, and the choice is a semantic one:

if x is None:      # correct — None is a singleton; identity IS the question
if x == None:      # works, but asks the wrong question and invokes __eq__
if n is 257:       # a bug. You meant ==. It may even pass in testing.
Why the third line is genuinely dangerous It is a bug that passes its own test. Depending on how the literals reach the interpreter, the two 257 objects may or may not be the same object — so the code works in the REPL and fails in production, or vice versa. You will reproduce this in D2. That divergence is your first direct encounter with the language/implementation boundary, and it is not academic.

03 Type — a slot, not an opinion

type(x) and x.__class__ are not the same mechanism. Knowing which one is authoritative is the drill.

type(x)
Reads a fixed slot on the object. Not overridable from Python.
x.__class__
An attribute lookup. Attribute lookup is user-controllable, therefore so is this.

They agree for every normal object, which is why most people never learn they are distinct. Then you meet a mock, a proxy, or an ORM lazy-loader — all of which work precisely by making them disagree — and the distinction becomes load-bearing.

The consequence isinstance() consults __class__ as well as the real type. So an object can make isinstance(obj, int) return True while being incapable of a single integer operation. isinstance tells you what an object claims; the real type slot decides what it can do. D3 makes you build one of these liars and then watch it fail.

Types are themselves objects

Not a slogan — a checkable fact with consequences. int is an object: it has an id, it has a type (type), and it has a value. type(type) is type — the chain terminates by pointing at itself rather than continuing forever.

This matters because it is what makes the next two stages possible. If types were not objects, they could not hold attributes; if they could not hold attributes, there would be nowhere to put __len__ and __eq__; and the entire data model would have no home. You are looking at the foundation of protocol dispatch three stages early.

The type object is not the instance object

The single most common way to misread “int is an object” is to picture one int box that all integers live inside. That is wrong, and the correction is the whole of this subsection: there is one type object, and one separate instance object per value. x = 100 binds x to an instance. It never touches the type.

If you know Java, you already know this Java has both models side by side, and Python only kept one of them:
  • int x = 100; — a primitive. The name is a 32-bit slot. No object, no header, no type tag at runtime.
  • Integer x = 100; — a reference to a heap object with a header and a class pointer. This is the only model Python has.
And the famous Java gotcha is literally the same phenomenon as CPython's small-int cache: Integer a=127, b=127; a==b → true (cached), but Integer a=128, b=128; a==b → false (not cached). If that surprised you in Java, Python's is behaviour on integers will not surprise you at all — it is the same cache, the same reason.

04 Value — the deliberate absence

There is no value() builtin. This is the most instructive missing feature in Python.

Identity has an accessor. Type has an accessor. Value has none, and could not have one. Ask yourself what value(x) would even return for a socket, a generator, a class, a file handle, or a running thread.

The design decision Value is not a slot you read. It is an interface the type exposes. Python never asks an object "what is your value" — it asks the object's type to perform an operation, and the answer is whatever that operation returns:
  • "are these two values equal?" → the type's __eq__
  • "render this value" → the type's __repr__
  • "how big is this value?" → the type's __len__
  • "can this value index a dict?" → the type's __hash__

Precisely stated, so this is not misread: every object does have a value, and that value is real data stored inside the object. What does not exist is a generic, type-independent way to ask for it — because the value is laid out in a type-specific format that only the type knows how to interpret.

Why a value() builtin is not merely missing — it is impossible Suppose value() existed. It would have to return a Python object. Now apply it to x = 100. The only correct answer is the int object 100 — which is x itself. value() would be the identity function. There is no inner primitive to unwrap, because the object is the value. In C, int x is a box and the bits inside are the value. In Python there is no box: x is a name, and the thing it names is already the value.

So the three-property model resolves into something sharper: identity and type are properties you can query directly; value is data you reach only through operations the type provides. That is the seam between Stage 1 and Stage 3, and you have now seen it before meeting a single dunder method.

Mutability, defined properly You can now define it without hand-waving. An object is mutable if operations exist that change its value while its identity and type stay fixed. Mutability is a property of the type, not of the variable, and never of the name. "Mutating a variable" is a sentence with no meaning in Python — and D1 will make you say it correctly.

05 The object header CPYTHON

Where identity, type and the bookkeeping physically live. Everything in this section is implementation, not language.

Every CPython object begins with the same fixed header. Simplified from Include/object.h:

struct _object {
    Py_ssize_t      ob_refcnt;   /* offset 0  — how many references point here */
    PyTypeObject   *ob_type;     /* offset 8  — pointer to the type object      */
};

/* variable-sized objects (list, tuple, str, int, bytes) add: */
    Py_ssize_t      ob_size;     /* offset 16 — number of items                 */
Do not memorise this layout — verify it The layout above is true for standard CPython builds, but free-threaded builds (3.13+) use a completely different header struct, and fields have shifted between minor versions. The drill file therefore ships layout_is_sane(), which checks that offset 8 really does hold id(type(obj)) before you trust any reading. If it returns False, that is not a failure — it is the lesson.

The trade this header represents

Python buysPython pays
Total uniformity — every value, from None to a class to a coroutine, is the same shape, so any of them can be put in any list, passed to any function, or made a dict key with no special-casing anywhere. No unboxed values. An int costs ~28 bytes instead of 8. A million-element list of ints is a million separate heap objects plus a million pointers.
Type dispatch is one pointer dereference, so it is O(1) and every object knows what it is without any external table. Every object carries that pointer forever, even the billionth identical one.
Lifetime management is uniform — one refcount field, one rule, no per-type bookkeeping. Every reference operation touches memory. This is a direct cause of the GIL's stubbornness and of NumPy's existence.

When someone says "Python is slow", this table is most of the actual answer — and notice that every row is a deliberate purchase, not an accident.

06 Immortal objects CPYTHON 3.12+

Read this before D6 or your refcount readings will look like corruption.

PEP 683 made a small set of objects immortal: None, True, False, small integers, and some interned strings. Their refcount field is set to a saturated sentinel value and then never touched again.

>>> import sys
>>> sys.getrefcount(None)
4294967295        # not a leak, not a bug — saturated
What problem this solves Refcounts are writes. Every time a shared object like None was passed around, CPython wrote to its header. Two costs follow: (1) in a fork()ed process, those writes dirty copy-on-write pages, so child processes stop sharing memory with the parent — a real cost for every pre-fork server; (2) under free-threading, every one of those writes is contended between threads. Freezing the count for objects that can never die removes both.

The exact sentinel constant has changed across 3.12 / 3.13 / 3.14, so do not memorise the number — report whatever yours prints. And note the second-order fact you should extract from D6: immortality is only worth engineering because ordinary objects pay that cost constantly. That is your on-ramp to drill 1.4.

08 Worked examples

Code with what it actually produced, and the conclusion each one forces.

The three properties, and the two kinds of change

x = [1, 2, 3]
id(x)              # 0x1f3a...

x.append(4)       # value changed
id(x)              # 0x1f3a...  SAME

x = [1,2,3,4]     # value looks identical
id(x)              # 0x2c81...  DIFFERENT
Stated without "mutation", "assignment" or "variable" The first changed the object a name reaches. The second changed which object the name reaches. In one, identity survives and value moves; in the other, a second object is created and the name is re-pointed at it. The original is untouched — and if nothing else reaches it, it stops existing.

The identity trap — three cases that do not agree

# (a) no names involved
id([1,2,3]) == id([4,5,6])   # True   (!)

# (b) both held by names
a = [1,2,3]; b = [4,5,6]
id(a) == id(b)                 # False

# (c) no names again
class C: pass
id(C()) == id(C())             # True   (!)

In (a) and (c) nothing holds the first object, so its lifetime ends the moment id() returns. The address is immediately free, and the second object is built right where the first one was. In (b) both objects are alive at the same time, so they cannot share an address.

Would you test against (a)? No. The language only guarantees that ids are unique among objects alive at the same time. The True in (a) is an address-reuse artifact of CPython's allocator, not a fact about Python. Never cache an id, and never compare ids across time.

An object that lies about its type

class Liar:
    @property
    def __class__(self): return int

l = Liar()
type(l)              # <class 'Liar'>   the truth
l.__class__          # <class 'int'>    the lie
isinstance(l, int)   # True             the lie is believed
l + 1                # TypeError: unsupported operand type(s)

Line 4 settles it. isinstance() deliberately consults __class__, so it can be fooled. type() is authoritative about what the object can do, because behaviour dispatches through the real type — and the real type has no __add__ for integers.

Why the hole exists on purpose Mocking libraries, lazy proxies and ORM row objects all need to pass an isinstance check without being the real class. If isinstance consulted only type(), none of them could work.

Types are objects, and the recursion terminates

type(3)                      # <class 'int'>
type(int)                    # <class 'type'>
type(type)                   # <class 'type'>
type(type) is type            # True
isinstance(int, object)       # True
isinstance(object, type)      # True

int is an object, so it has all three properties: its identity is its address, id(int); its type is type; and its value is the set of attributes and behaviours it carries — the methods that define what its instances can do.

Why type(type) must be type If type had a distinct metatype, that metatype would itself need a type, and so on without end. Making type its own type is what bottoms the recursion out — the same trick as a directory that contains itself as ..

Reading the object header out of live memory CPYTHON

layout_is_sane()            # True  — verify before trusting anything below

x = [1, 2, 3]
header(x, "x")
# x    id=0x1f3a...  refcnt=1  ob_type=0x7ff8... (list)
hex(id(list))                # '0x7ff8...'  — the same address

for obj in ([], (), "s", 3.5):
    raw_type_ptr(obj) == id(type(obj))   # True, all four

Every object stores a pointer to its type, and every list in the process points at the same list type object. Two consequences:

  • The per-object cost of knowing your own type is one pointer — 8 bytes on 64-bit. The type is shared, never copied.
  • type(x) is O(1) regardless of inheritance depth, because it is a single read at a fixed offset. Depth affects attribute lookup, which walks the MRO — not type(), which never searches anything.

Immortal objects, and where the boundary sits CPYTHON

sys.getrefcount(None)    # an absurd constant
sys.getrefcount(True)    # an absurd constant
sys.getrefcount(1)       # an absurd constant
sys.getrefcount(1000)    # an ordinary small number

raw_refcount(256)         # immortal    <- boundary
raw_refcount(257)         # ordinary    <- boundary

Small integers (-5…256), None, True and False are cached and immortal. The exact sentinel constant differs across 3.12 / 3.13 / 3.14, so read yours rather than memorising one.

The second-order fact — this is the real payload Immortality is an optimisation, so it removes a cost. The cost is that every single reference to a shared object like None would otherwise require incrementing and decrementing a counter written into memory shared by the whole program.
Which forces the inference: ordinary objects are paying that write constantly — on every name binding, every argument passed, every container insertion, every scope exit. That is the on-ramp to object lifetime.

Identity across mutation vs rebinding

a = [1, 2, 3]
before = id(a)

a.append(4)
after_mutate = id(a)      # == before

a = a + [5]
after_rebind = id(a)      # != before

The first two match; the third differs. Two lists were created — the original, and the one + built. append created none; a + [5] created one and the name was moved onto it.

The liveness trap Is the object from line 1 still alive at the end? No — no name reaches it any more, so it was freed. And you cannot check with before: that is an integer, not a reference, and the address may already have been handed to something else. The only honest way to ask is to hold a weakref to it before rebinding and see whether it is dead afterwards.

The cost of being an object

sys.getsizeof([1,2]) - sys.getsizeof([1])    # 8 on 64-bit

That 8 is one pointer — the size of the extra slot in the list's array. It is not the size of the integer 2, and one line proves it:

sys.getsizeof([10**100]) == sys.getsizeof([1])   # True

A hundred-digit integer is far larger than a small one, yet the containing list is exactly the same size. The list holds references, not values.

Why getsizeof understates a big list It measures the container and nothing it points at. A list of a million distinct ints reports roughly 8 MB of pointers while the ints themselves consume tens of MB more, unseen. Every "small" container in Python is a table of addresses, and the real memory is somewhere else — which is exactly why aliasing and copy depth matter in 1.3.

09 What these settle

The conclusions worth carrying out of this page.

#Settled
1Two kinds of change: one alters the object a name reaches (identity survives), the other alters which object the name reaches (a new object exists). Neither needs the word "variable" to describe.
2Ids are unique only among objects alive at the same time. Unnamed temporaries die immediately, so their addresses get reused — which is why id(C()) == id(C()) can be True. Never cache or compare ids across time.
3isinstance() consults __class__ and can be fooled; type() reports the real type and is authoritative about what the object can do. The hole is deliberate — mocks and proxies depend on it.
4int is an object: identity = its address, type = type, value = the attributes and behaviours it carries. type(type) is type because the chain has to bottom out somewhere.
5Every object stores one pointer to a shared type object. That makes type(x) O(1) at any inheritance depth — depth costs you attribute lookup, not type().
6Immortality removes a memory write per reference for the most-shared objects. Its existence proves ordinary objects pay that write constantly — on every binding, call, insertion and scope exit.
7append creates no object; a + [5] creates one. After rebinding, the original is unreachable and freed — and the saved id cannot tell you, because it is an integer, not a reference.
8getsizeof measures the container only. The 8-byte delta is a pointer slot, proven by getsizeof([10**100]) == getsizeof([1]). Containers hold addresses; the memory lives elsewhere.
The sentence that compresses the page id() is guaranteed unique only during an object's lifetime, because it names a location rather than an object — which means identity is a fact about now, and any code that stores one and compares it later is asking a question the language never agreed to answer.

10 Ledger — language vs CPython

Everything asserted in this document, sorted. Learn the split, not just the facts.

BadgeClaimConsequence for your code
LANGUAGEEvery object has identity, type, value.Universally true. Reason with it everywhere.
LANGUAGEIdentity never changes during an object's lifetime.Safe to rely on.
LANGUAGEObjects with non-overlapping lifetimes may share an id.Never cache or compare ids across time.
LANGUAGEis compares identity; == asks the type.Choose deliberately; they answer different questions.
LANGUAGETypes are objects; type(type) is type.Foundation of the whole data model.
CPYTHONid() returns the memory address.False on PyPy. Never write code assuming it.
CPYTHONHeader is ob_refcnt then ob_type.Differs in free-threaded builds. Verify, never assume.
CPYTHONFreed addresses are reused immediately.Cause of the D2 trap. Not portable behaviour.

CPYTHONReference counting exists at all.Other implementations use tracing GC only. Drill 1.4.
The skill this table is really teaching Most engineers who "know Python deeply" actually know CPython deeply and cannot tell which is which. That confusion is invisible until it costs you — a subtle bug on an alternative runtime, a wrong answer in a design review, an optimisation that assumes semantics the language never promised. Maintaining this split is the difference between senior and principal-level knowledge of a language.

11 What this unlocks

Forward references. Do not chase them yet — just notice the wires you have already laid.

Immediate — drill 1.2

The arrow in §01's figure. A name is a key in a mapping; binding a name never copies and never moves an object. Everything about aliasing follows mechanically from that plus today's model.

Immediate — drills 1.4 & 1.5

ob_refcnt is already on your screen. Once you know what increments it, the identity-reuse trap from D2 stops being folklore and becomes arithmetic.

Later — the data model

"Value is an interface the type exposes" (§04) is the entire thesis of special methods. len(x) is not a method call on x; it is a request routed to x's type. You have already met the reason why.

Later — dict and set

Hashability is a rule about value stability over an object's lifetime — which is a sentence you can only parse because of today. Every "unhashable type" error traces back to §04.

The standard for finishing 1.1 You are done when you can take any line of Python and answer, without running it: which objects exist, which are new, which of their three properties changed, and which name or container is still reaching them. Not "lists are mutable". That is a memorised fact. The goal is a model that generates the facts.
