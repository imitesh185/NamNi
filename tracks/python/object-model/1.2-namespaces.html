Namespaces: the name → object mapping

Drill 1.1 established the object. This drill establishes the arrow — the thing that connects a name to it. The single claim is small and its consequences are enormous: a name is not storage, it is a key in a mapping. Once that is real to you, aliasing, del, scope, closures, shadowing and the entire "does Python pass by value or by reference" argument collapse into one mechanism you can reason about directly.

The 1.1 → 1.2 hinge. In 1.1 you saw that an object exists independently of any name. Now: a name exists independently of any object. They are two separate populations joined by a mapping — and almost every Python surprise lives in that join.

00 Where this sits

One line of recap, one line of new claim, and the boundary.

Settled in 1.1

An object is identity + type + value. Identity is fixed for its lifetime. Value is data inside the object, reachable only through operations the type provides. The type object and the instance object are different objects.

The claim of 1.2

A namespace is a mapping from names (strings) to object references. Binding a name inserts or replaces a key. Binding never copies, never moves, and never creates storage for a value.

The consequence is immediate and it is the whole drill: an operation either rebinds a name or mutates an object — never both by accident, and never neither. Sorting Python statements into those two buckets is the skill 1.2 installs.

Protocol for this drill There is exactly one checkpoint, in §08, and it is a fixed finite list. No follow-up round. If a question in the drill body is one you do not want to chase, skip it — say "banked" and it will not be re-raised.

01 A name is a key, not a box

The claim, and the two-line proof.

“ “A namespace is a mapping from names to objects.” The Python Tutorial, §9.2. Not a metaphor and not a simplification — at module level it is literally a dict you can inspect and modify. 
x = 100
globals()['x'] is x          # True  — the name lives in a real mapping

globals()['y'] = 7
y                             # 7     — you created a variable by inserting a key

del globals()['y']
y                             # NameError — you deleted a key, nothing else

That second block is worth sitting with. You produced a working module-level variable without an assignment statement, by writing to a dictionary. Assignment is not a primitive operation on memory — it is a convenient syntax for a mapping update.

This kills the "pass by value / by reference" question Neither term fits, because both assume the C model where a name is storage. Python passes references to objects, by value — the callee gets its own name (a new key in a new namespace) bound to the same object. So rebinding the parameter is invisible to the caller, while mutating the object is visible. Both facts, one mechanism, no special rule.

03 globals() is live. locals() is not.

The asymmetry that reveals what a function frame really is.

CallReturnsWriting to it
globals()The actual module namespace dictWorks. It is the real mapping.
locals() at module levelThe same dict — locals() is globals()Works, same reason.
locals() inside a functionA snapshot built on demandSilently does nothing.
 
def f():
    a = 1
    locals()['a'] = 999
    return a

f()      # 1  — the write went into a throwaway dict
CPython 3.13+ · PEP 667 Before 3.13, locals() in a function returned a dict cached on the frame and refreshed on each call — so a write could appear to stick until the next refresh silently wiped it. PEP 667 (landed in 3.13) made it return an independent snapshot every call, so the failure is now honest and immediate. You are on 3.13/3.14, so you get the clean behaviour — and D3 has you prove which one you have.

Ask the obvious question: why is the module namespace a real dict but the function namespace not? The answer is §04, and it is the single best piece of evidence in Stage 1 that "a namespace is a mapping" is a language-level model, not a description of storage.

04 Why function locals can't be a dict CPYTHON

Implementation, clearly labelled. It explains the §03 asymmetry and nothing else.

Inside a function, CPython's compiler can see every local name at compile time. So it does not build a dict — it assigns each local an integer slot in an array on the frame, and compiles name access into a direct index. That is why function-local access is fast and why there is no live mapping to hand you.

import dis

def uses_local():
    v = 1
    return v

dis.dis(uses_local)     # STORE_FAST / LOAD_FAST   → array index

def uses_global():
    return SOME_GLOBAL

dis.dis(uses_global)    # LOAD_GLOBAL              → dict lookup by key
The two-layer reading Language layer: a function's local namespace is a mapping from names to objects. True, and the only thing you need to reason about semantics.
CPython layer: that mapping is realised as an array of slots, because the compiler knew the keys in advance. The dict was optimised away; the model was not. Holding both statements at once, without confusing them, is the skill §11 of drill 1.1 was training.

Most people know two of these. There are eleven.

If you can recite this list, you can look at any block of Python and say exactly which names come into existence and where.

06 del, shadowing, and the three scope traps

All three are consequences of "a name is a key". None of them are special cases.

del removes a binding, not an object

a = [1,2,3]
b = a
del a
b            # [1, 2, 3] — the object never noticed
a            # NameError — the key is gone

del a is del globals()['a']. Whether the object dies is a separate question, answered by drills 1.4 and 1.5.

Trap 1 — the class body is not an enclosing scope

class C:
    y = 1
    def m(self):
        return y        # NameError — not 1

A class body runs in its own namespace, but that namespace is not in the LEGB chain of methods defined inside it. The E in LEGB means enclosing function scopes only. Methods must go through self.y or C.y.

Trap 2 — comprehensions have their own scope

x = 'outer'
[x for x in range(3)]
x                     # 'outer' — untouched

for x in range(3): pass
x                     # 2 — the loop variable leaked

A comprehension gets its own namespace; a for statement does not. Same-looking syntax, different binding behaviour.

Trap 3 — except … as unbinds on exit

try:
    1/0
except ZeroDivisionError as err:
    pass
err                   # NameError

LANGUAGE The reference specifies this as an implicit del err in a finally. The motive is lifetime: the exception holds a traceback, the traceback holds the frame, and the frame holds err — a cycle that would keep the whole frame alive. A language rule introduced purely to protect object lifetime — which is your bridge into 1.4 and 1.5.

10 What this unlocks

Wires laid. Do not chase them.

Next — drill 1.3

References and aliasing. You have already built it: two keys holding the same reference. 1.3 extends the mapping model from namespaces to containers — a list is also a collection of references, just keyed by integer instead of by name.

Then — drills 1.4 / 1.5

Every binding you made in this drill incremented a refcount. Every del decremented one. The except … as rule exists because of a reference cycle. 1.2 is where the counting starts being visible.

Later — closures and decorators

The E in LEGB is the entire mechanism behind closures. There is no additional concept — only a namespace that outlives the call that created it.

Later — attribute lookup

D7 showed module.attr is a lookup in module.__dict__. Instances and classes work the same way. When Stage 2 arrives, attribute access will be a namespace search you already understand.
