References & aliasing

1.2 gave you one mechanism: a namespace maps names to object references. This page does something cheap and enormously powerful with it — it points out that containers work exactly the same way. A list is a mapping from integers to references. A dict is a mapping from hashable keys to references. Once you see that, aliasing, shallow copy, nested mutation, argument passing and the += paradox all stop being separate rules.

The whole page in one sentence. A list does not contain objects. It contains references to objects. Everything below is that sentence, applied until it hurts.
#references #aliasing #shallow-vs-deep #argument-passing #iadd

00 Where this sits

One generalisation, four consequences, zero new machinery.

Settled in 1.2

A namespace maps names to object references. Binding inserts a key. Rebinding replaces a key's value. Mutation changes an object and is visible through every key that reaches it.

The claim of 1.3

Containers are the same structure with different keys. list keys by integer, dict keys by hashable object. Nothing new is introduced — only the key type changes.

01 A container holds references, not objects

The sentence people nod at and then reason as if it were false.

Everyone agrees with the claim in the abstract. The test of whether you actually believe it is this expression:

rows = [[]] * 3
rows[0].append("x")
rows                    # [['x'], ['x'], ['x']]

If that looks like a bug in Python, you are still reasoning as though the list held three objects. It held three copies of one reference. * repeats the contents of the list — and the contents are references. It never had any reason to create a second list.

Generalisation Same for every container. A dict's values are references. A tuple's slots are references. An instance's __dict__ is a namespace, so attributes are references too. Python has exactly one storage concept: a slot holding a reference. Names, list indices, dict keys and attributes are four spellings of the same idea.

02 Aliasing, generalised

Two references to one object, regardless of where the references live.

1.2 showed two names reaching one object. The general statement drops the word "name":

Both references live in…Example
two namesb = a
a name and a list slotbox = [a]
two list slots[a, a], or [x] * 3
a list slot and a dict valued['k'] = lst[0]
a name and an attributeobj.data = a
a container and itselfa.append(a)

All six are the same situation and mutation propagates identically through all of them. There is no "aliasing feature" to learn — aliasing is the absence of copying, and Python never copies unless you ask.

The self-reference case is not a curiosity a = [1,2]; a.append(a) is legal and prints [1, 2, [...]]. The [...] is repr detecting a cycle it would otherwise recurse into forever. This object cannot be freed by reference counting alone — it references itself, so its count never reaches zero. You have just constructed the exact problem that drill 1.4's garbage collector exists to solve.

03 The three depths of copying

Most "copy" bugs are someone using depth 2 while believing they used depth 3.

DepthHowWhat is duplicated
0 — aliasb = aNothing. One object, one more reference.
1 — shallowa[:] · list(a) · copy.copy(a)The outer container only. The references inside are copied, so the inner objects are shared.
2 — deepcopy.deepcopy(a)The container and, recursively, everything reachable from it.
Why shallow is the default Deep copying is expensive, often wrong (would you deep-copy a database connection?), and not always possible (cycles, sockets, file handles). Python's design position is that the programmer knows the object graph and should say when to go deep. deepcopy does handle cycles via a memo of already-copied objects — but it cannot know that copying your connection pool is a mistake.

04 Argument passing needs no new rule

The most argued-about topic in Python has no dedicated mechanism at all.

A call creates a new namespace (the frame) and binds parameter names in it to the argument objects. That is the whole story. f(data) is seq = data executed inside a fresh namespace.

def rebind_vs_mutate(seq):
    seq.append("mutated")     # mutates the shared object   → caller sees it
    seq = ["rebound"]         # rebinds the local key       → caller sees nothing
    seq.append("invisible")   # mutates the NEW object      → caller sees nothing
    return seq
The correct formulation Not "pass by value", not "pass by reference". Python passes references to objects, by value — the reference is copied into a new binding; the object never is. Both observed behaviours fall out of that single sentence, with no special case for mutable types.

Why the mutable default argument bug exists

def leaky(item, bucket=[]):
    bucket.append(item)
    return bucket

Default values are evaluated once, when the def statement executes — not per call. So one list object is created at definition time and stored on the function object. Every call that omits bucket binds to that same object.

leaky.__defaults__          # the object is right there, inspectable

This is not a wart bolted on. It follows from def being a binding operation (§05 of drill 1.2) whose default expressions are evaluated at binding time. The fix — bucket=None and build inside — works because it moves object creation into the call.

05 The += paradox

One statement that both raises an exception and succeeds. The best test of this drill.

t = ([1, 2], 3)
t[0] += [9]

# TypeError: 'tuple' object does not support item assignment

t
# ([1, 2, 9], 3)      ← the mutation happened anyway

Both are true. The exception is real and the mutation is real. The reason is that x[i] += v is not one operation — it is three:

  1. Load t[0] — you now have the inner list object.
  2. In-place add — list.__iadd__ mutates that object and returns it. The mutation is now permanent and irreversible.
  3. Store back — t[0] = <result>. Tuples reject item assignment. TypeError.

Step 2 already committed. Step 3 fails afterwards. Nothing rolls back, because Python has no transaction concept for expressions.

Why += is not just sugar for + a = a + b always builds a new object and rebinds. a += b tries __iadd__ first, which for mutable types mutates in place and returns self — so the rebinding is a no-op onto the same object. That is why += on a list is visible to every alias, while + is visible to none of them. Immutable types have no __iadd__, so for them += genuinely does fall back to +.

06 Worked examples

Code with what it actually produced. Companion: python-model/d13_references.py.

The * operator repeats a reference, not an object

rows = [[]] * 3
rows[0].append("x")
rows                        # [['x'], ['x'], ['x']]  — one list, three slots

nums = [0] * 3
nums[0] = 9
nums                        # [9, 0, 0]  — no repetition

Both lines built three slots pointing at one object. The difference is not the type — it is the statement. rows[0].append(...) mutates the object all three slots point at. nums[0] = 9 rebinds one slot and leaves the other two alone.

Say it without the word "immutable" [0]*3 is not safer than [[]]*3. The two examples were never doing the same thing: one mutates a shared object, the other replaces a reference. The immutability of int is not required to explain either.

Copy depth is two booleans, not a spectrum

orig[0].append("BOOM")   # mutate an INNER object of the original

Four spellings of the shallow copy, one behaviour. The single test that tells you the depth is c[0] is orig[0] — the inner identity. The outer one is never shared by any real copy, so it distinguishes nothing.

The practical version Handing config = {"hosts": ["a","b"]} to untrusted code needs deepcopy. A shallow copy hands over the same inner list, so copy["hosts"].append(...) is visible in your original — the copy protected the outer dict and nothing that mattered.

Argument passing introduces no new rule

def rebind_vs_mutate(items):
    items.append("mutated")   # caller sees this
    items = ["rebound"]       # caller does NOT see this
    return items

data = ["start"]
returned = rebind_vs_mutate(data)
data                        # ['start', 'mutated']
returned                    # ['rebound']
data is returned            # False

The parameter is just another name bound to the same object. Mutation reaches the caller; rebinding the local name does not. Nothing about functions is involved.

A mutable default is evaluated once, at definition

def leaky_default(x, acc=[]):     # the list is created ONCE
    acc.append(x); return acc

leaky_default(1)                 # [1]
leaky_default(2)                 # [1, 2]      <- not a fresh list
leaky_default(3)                 # [1, 2, 3]
leaky_default.__defaults__      # ([1, 2, 3],)  the evidence

def safe_default(x, acc=None):
    if acc is None: acc = []
    acc.append(x); return acc     # [1] then [2]

__defaults__ is the whole explanation: the default is an attribute of the function object, bound when def executed, not when the call happens.

The += paradox — it raises and succeeds

t = (1, [2])
t[1] += [3]              # TypeError: 'tuple' object does not
                            #            support item assignment
t                           # (1, [2, 3])   <- the mutation HAPPENED

Three steps, and the exception lands on the last one:

  1. t[1] is fetched — a reference to the inner list.
  2. list.__iadd__([3]) runs and mutates that list in place. This step commits.
  3. Python then attempts t[1] = <result> to complete the +=, and the tuple refuses. This step fails.
a = [1,2]
a.__iadd__([3]) is a     # True  — in-place ops return self
(1,2).__iadd__              # AttributeError — tuples have none

Which is exactly why += on a list is visible to every alias while + is visible to none: the first mutates and rebinds onto the same object, the second builds a new one.

A container can hold a reference to itself

a = [1, 2]
a.append(a)
a                           # [1, 2, [...]]  — repr refuses to recurse
a[2] is a                  # True
a[2][2][2][2] is a         # True, at any depth

sys.getrefcount(a) comes back higher than the number of names you created, because one of the references is held by the list itself. A cycle like this cannot be freed by counting references alone — which is the entire reason a cycle collector exists.

Aliasing is not a list feature

shared = [1, 2]
registry = {"a": shared, "b": shared}

class Holder: pass
h = Holder(); h.data = shared

shared.append(3)
registry                    # {'a': [1, 2, 3], 'b': [1, 2, 3]}
h.data                      # [1, 2, 3]
h.__dict__                  # {'data': [1, 2, 3]}
registry["a"] is h.data is shared   # True
What h.__dict__ reveals It is an ordinary dict. Which makes attribute access a dictionary lookup keyed by a string — not a distinct language feature. Names, list slots, dict values and attributes are four spellings of one idea: a slot holding a reference.

07 What these settle

The five conclusions worth carrying out of this page.

#Settled
1[0]*3 is not "safer" than [[]]*3. Both share one object across three slots. Rebinding a slot affects one slot; mutating the object affects all of them. Type never entered the explanation.
2Every shallow copy — .copy(), [:], list(), copy.copy() — shares inner objects. The one test that tells you the depth is c[0] is orig[0].
3t[1] += [3] on a tuple: the mutation commits (step 2, __iadd__) and the rebind fails (step 3, item assignment). One statement, two outcomes, both real.
4h.__dict__ is a plain dict, so attribute access is a string-keyed dictionary lookup — the same mechanism as a namespace, wearing different syntax.
5A safe copy for untrusted code is deepcopy. A shallow copy hands over the same inner objects, so it protects the outer container and nothing else.
The one that matters most Explaining [0]*3 without saying "immutable" forces it to be a fact about references and rebinding, not a fact about types. nums[0] = 9 replaces a reference in a slot; rows[0].append("x") mutates the object a reference points at. The two statements were never doing the same thing.

09 What this unlocks

Two wires laid, both load-bearing.

Next — drill 1.4

D5 built an object whose reference count can never reach zero. That single object is the entire justification for CPython having a cycle-detecting garbage collector in addition to reference counting. You built the problem before meeting the solution.

Then — drill 1.5

§05 showed __iadd__ exists on list and not on tuple. That asymmetry is not a quirk — it is the mutability boundary, and it is what makes tuples usable as dict keys. 1.5 turns that into the hashability contract.

Later — the data model

__iadd__ was your first special method. Stage 2's claim is that every operator, every builtin and every syntax form resolves to one of these. You have already seen the mechanism work.

Later — attribute lookup

D6 exposed h.__dict__ as a plain namespace. Attribute access is a mapping lookup, exactly like a name lookup — which is why __slots__, descriptors and properties can intervene in it at all.
