Stage 2 · Data Model · Drill 2.1

Special methods as protocol hooks

Stage 1 answered what an object is — identity, a type, a value, reached through references living in namespaces. Stage 2 answers the other half: how the language talks to it. The answer is smaller than it looks. There is no privileged set of built-in behaviours that Python knows how to perform on your object. There is only a naming convention: the interpreter reaches for a method with a specific name, on the object's type, and calls it.

The whole drill in one sentence. Syntax and builtins are sugar for calling a named method on the type. len(x) is type(x).__len__(x). Everything below is that sentence, applied until it stops being surprising.

00 Where this sits

You have already used one special method. This drill turns it into a system.

Settled in Stage 1

An object is identity + type + value. Names, list slots, dict values and attributes are four spellings of one idea: a slot holding a reference. Mutation changes an object; rebinding changes a slot.

The claim of 2.1

1.3 §05 found that list has __iadd__ and tuple does not, and that this asymmetry is the behaviour of +=. Generalise it: every operator, builtin and syntax form resolves this way.

This is the payoff of Stage 1 being boring. Because you already accept that behaviour lives on the type and not on the instance, the data model needs no new machinery — it is an index of method names plus the rule for when each one is consulted.

01 Syntax is a method call

Not "similar to". Not "implemented using". It is one.

Read the left column as what you type and the right column as what the interpreter actually performs. There is nothing in between.

You writeThe interpreter callsProtocol
len(x)type(x).__len__(x)sized
x[k]type(x).__getitem__(x, k)subscriptable
x + ytype(x).__add__(x, y)numeric

The last row is worth pausing on. Even the dot is a special method. There is no layer underneath this one — attribute access itself is implemented by a method that Python looks up as an attribute of the type, and the recursion bottoms out in C.

Why this design Because it makes the language open. If len() contained a hardcoded list of types it understood, only the core developers could write a sized object. Because it dispatches to a method name instead, your class is a first-class citizen of the syntax — the same status as list, with no registration step and no inheritance requirement.
You do not call these yourself Write len(x), not x.__len__(). The builtin is faster (it takes a direct slot on the C type object), it applies the fallback rules described in §05, and it reads as the operation rather than the mechanism. The only normal reason to write a dunder explicitly is when you are implementing one and delegating to another.

02 Lookup happens on the type, not the instance

The one rule that makes special methods behave unlike every other attribute.

Ordinary attribute access checks the instance first, then the type. Implicit special-method invocation skips the instance entirely. This is not an optimisation detail you can ignore — it produces visibly different results:

s = Sneaky()             # its class defines __len__ returning 1
s.__len__ = lambda: 99

len(s)                    # 1  — implicit: type lookup, instance ignored
s.__len__()              # 99 — explicit: ordinary attribute lookup
Consequence you will hit You cannot give one object a protocol. Monkey-patching obj.__iter__, obj.__enter__ or obj.__eq__ does nothing to for, with or ==. Patch the class, or build a subclass. Mocking libraries know this — it is why they patch types.
Why it works this way Every type is a C struct with fixed slots — tp_as_sequence->sq_length and friends — filled in once when the class is created. len() reads the slot; it never performs a dictionary lookup at all. Skipping the instance is not a rule bolted on top, it is a description of what the fast path physically does.

03 The two string protocols

One is for you at 3am. The other is for the user. Only one has a fallback.

Two methods, two audiences, and an asymmetric fallback that decides which one you should always write first.

MethodAudienceGoalIf missing
__repr__the developerunambiguous — ideally valid Python that recreates the object<Class object at 0x…>
__str__the end userreadable — may drop detailfalls back to __repr__

The fallback runs one way only. Define __repr__ and you get sensible output from both. Define only __str__ and your debugging output, your log lines and every collection containing your object stay useless:

[OnlyStr()]     # [<OnlyStr object at 0x7f...>]  — containers use repr
[OnlyRepr()]    # [OnlyRepr(unambiguous)]
Rule that pays for itself Write __repr__ on every class you define. Write __str__ only when a non-developer will read it. Containers, the REPL, logging, pdb and pytest failure output all use repr. A dataclass gives you a good one for free; that is most of why people reach for dataclasses.

Where each one is actually used

ExpressionUses
print(x), str(x), f"{x}"__str__ → falls back to __repr__
repr(x), f"{x!r}", REPL echo__repr__
[x], {"k": x}, any container__repr__ of the elements
f"{x:>10.2f}"__format__ → default delegates to __str__
The container detail people miss str(some_list) does not call str on the elements. A container's __str__ is its __repr__, and that builds itself from the repr of each element. So a class with only __str__ prints beautifully alone and unreadably inside a list — which is exactly where you need it during debugging.

04 One method, several powers

Why protocols beat inheritance: you implement a piece, and the rest arrives.

Define __getitem__ — nothing else, no base class — and count what already works:

class Countdown:
    def __init__(self, start): self.start = start
    def __getitem__(self, i):
        if i >= self.start: raise IndexError(i)
        return self.start - i

c = Countdown(4)
list(c)              # [4, 3, 2, 1]
for v in c: ...      # works
2 in c              # True
a, b, *rest = c     # works
hasattr(type(c), "__iter__")   # False (!)

It iterates without an __iter__. When iter() finds no __iter__, it falls back to the legacy sequence protocol: call __getitem__ with 0, 1, 2, … until IndexError is raised. Everything built on iteration then works, because it is all built on iter().

This is what duck typing means, precisely Not "Python doesn't check types". It means membership in a protocol is decided by which methods your type defines, evaluated at the moment of use — not by what you inherited from. Countdown is a sequence to for, to in, and to unpacking, while being a subclass of nothing.

The fallback chains worth memorising

OperationTries, in order
iter(x)__iter__ → __getitem__ from 0 → TypeError
k in x__contains__ → __iter__ and scan → __getitem__ and scan
bool(x)__bool__ → __len__ → True
str(x)__str__ → __repr__ → default repr
The cost of the free lunch in falling back to a full scan is correct and O(n). A class that looks like a set but only defines __getitem__ will pass every test and quietly turn a membership check into a linear scan inside a loop. Protocol satisfaction says nothing about complexity.

05 Truthiness and its fallbacks

Three-step chain. Every object in Python has a truth value; almost none define one.

The last box is the one that bites. if result: on a custom object with neither hook is always true — including when the object represents nothing at all:

class Response:
    def __init__(self, rows): self.rows = rows

r = Response([])
if r: ...           # True — there is no hook, so the default wins
if r.rows: ...      # False — you meant this
Design rule If "empty" is a meaningful state for your class, give it __len__ and truthiness follows for free. Reach for __bool__ only when emptiness and falsiness are different questions — a Flag that is present but off, for example.

06 Operators, NotImplemented, and the __eq__ trap

A two-round negotiation, and the one place defining a method silently deletes another.

Binary operators are not a single dispatch. a + b asks the left operand first; if it declines, it asks the right operand's reflected method:

  1. type(a).__add__(a, b) — if this returns anything other than NotImplemented, done.
  2. type(b).__radd__(b, a) — the right operand's turn.
  3. Both declined → TypeError: unsupported operand type(s).
Return it, do not raise it NotImplemented is a value you return to say "not my problem, try the other operand". NotImplementedError is an exception you raise for an unfinished abstract method. Returning the wrong one, or raising TypeError yourself, kills the negotiation and breaks interoperability with types that would have handled it. Note also that NotImplemented is truthy — if x == y: on a broken __eq__ can silently take the wrong branch.

Defining __eq__ removes __hash__

This is the sharpest edge in the data model, and it follows directly from Stage 1. By default __eq__ is identity and __hash__ is derived from identity, so the hash invariant holds trivially. The moment you redefine equality, Python cannot assume the invariant still holds — so it sets __hash__ = None and your class becomes unhashable:

class Money:
    def __eq__(self, other): ...

Money(5) == Money(5)     # True
hash(Money(5))            # TypeError: unhashable type: 'Money'
{Money(5)}                # TypeError — no sets, no dict keys, no lru_cache
Money.__hash__            # None — not missing. Explicitly None.
The invariant being protected If a == b then hash(a) must equal hash(b). Break it and a dict will store two "equal" keys in different buckets and fail to find one you just inserted. Python refuses to let you break it by accident — silently keeping the identity-based hash would produce a corrupt dict, so it removes hashing instead.

Restore it deliberately, and only if the fields you hash cannot change while the object is in a set or dict:

def __hash__(self): return hash(self.rupees)

This is why immutability and hashability travel together, and why @dataclass(frozen=True) gives you __hash__ while a plain @dataclass with eq=True does not.

10 What this unlocks

Everything in Stage 2 from here is the same rule with a different method name.

Next — 2.2 containers & sequences

D4 satisfied the sequence protocol by accident. 2.2 makes it deliberate: slicing, __len__ plus __getitem__ together, negative indices, and why collections.abc exists when duck typing already works.

Then — iteration properly

The __getitem__ fallback is the legacy path. The real protocol is __iter__ returning an iterator with __next__, which is what makes generators, lazy pipelines and itertools possible.

Then — context managers

with was one row in the §01 table. Two methods and an exception-safety guarantee is the entire feature, and it is how every connection, file handle and Spark session should be managed.

Later — attribute access

1.3 D6 exposed h.__dict__; §01 showed the dot is itself a special method. Together they open __getattr__, __slots__, descriptors and property — the machinery behind every ORM and settings object you have used.

Where this shows up in real work Every library you rely on is an exercise in this drill. pandas overloads __getitem__ so df[...] means four different things. PySpark's Column overloads __eq__ to build an expression tree rather than compare — which is exactly why if col == 5: silently misbehaves and df.filter(col == 5) is correct. You cannot read that library's behaviour without this drill.
