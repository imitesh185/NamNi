Pipelines & Orchestration

A pipeline is not merely a program that runs. It is a program that will be run again, over data that may have changed, after code and schemas may also have changed.

The reconstruction test. For any rerun, identify the input version, code version, target grain, write semantics, recovery position, and whether repeating every side effect converges.
#idempotency#backfill#cdc#reconciliation

P1 ETL versus ELT

The choice moves transformation ownership, compute, and replay across the load boundary.

ETL
source -> external transform -> modeled output -> warehouse
          |
          `-- raw source may never reach target

ELT
source -> raw target layer -> SQL/model transform -> served tables
    |                       |
    +-- replayable input    +-- versioned readable logic

ELT pressure:
analytical engine already owns scalable compute
+ SQL is reviewable by data consumers
+ retained input permits model replay
ChoiceGivesCosts / boundary
ETLFilter/redact before target; specialized runtimeExternal bottleneck and weaker raw replay if input is discarded
ELTRaw retention, visible SQL, target computeSensitive/noisy data and compute cost move into target

P2 Orchestration

A schedule says when to consider work; a dependency says what must be true first.

WRONG
A scheduled 01:00
B scheduled 02:00
assumption: A completed before B
        |
        X A runs late
        v
B reads partial or stale output

EXPLICIT DAG
A success + interval ready ----> B
external dataset/sensor -------> B
retry + timeout + ownership ---> task state

logical data interval != task start time != completion time

P4 Idempotency and write semantics

Retries are inevitable; target semantics decide whether repetition duplicates, replaces, or converges.

same input interval, run twice

APPEND                         UPSERT
run 1 -> A,B                   key = declared grain
run 2 -> A,B,A,B               apply A,B again -> same keyed state
duplicate by design            only if key/version rule is correct

PARTITION REPLACE              SNAPSHOT COMMIT
compute full partition         write immutable files + metadata
atomically replace target      atomically publish new snapshot

DELETE then INSERT without atomic boundary
delete -> reader sees empty -> insert -> full
   ^ exposed failure window
Write modeSafe replay conditionFailure
AppendStable event identity plus downstream dedupDuplicate effects
UpsertKey equals grain; source version is validCollapsed facts or stale overwrite
Partition replacePartition deterministic and replacement atomicPartial/empty visibility
Snapshot publishReaders resolve committed metadataWriter conflicts and orphan files remain
VerifyKill the task at each write boundary, rerun twice, and compare target keys, counts, and checksum to a clean oracle.

P5 Incremental models and change detection

Incremental work needs a reliable definition of what changed since a durable position.

TIMESTAMP WATERMARK
SELECT ... WHERE updated_at > last_seen
          |
          +-- equal timestamp tie may be skipped
          +-- late commit may carry old timestamp
          +-- hard delete emits no row
          `-- clock/transaction boundary is ambiguous

LOG POSITION
WAL/LSN 120 ---- committed changes ----> checkpoint 150
ordered transaction records, including delete

SNAPSHOT DIFF
state T1 vs state T2 -> insert/update/delete set
cost: scan and compare whole or hashed key space
MethodGivesFailure boundary
TimestampSimple query-based incrementTies, late commits, deletes, clock semantics
Log CDCOrdered committed changes and deletesRetention, connector/schema failure, source burden
Snapshot diffIndependent state reconciliationExpensive; intermediate changes disappear
Row hashCompact equality signalStill needs candidate discovery and normalization

P6 Backfills

A backfill runs old intervals under today's code, source availability, and shared capacity.

REQUEST: recompute two years
  +-- CODE: which historical logic?
  +-- SOURCE: do old values/schemas remain?
  +-- ORDER: can intervals run independently?
  +-- WRITE: replace or duplicate?
  +-- COST: can production coexist?
  `-- VALIDATE: what independent oracle?

SAFE SHAPE
pin code + input snapshot
 -> write shadow output
 -> compare counts/checksums/business totals
 -> atomically publish
 -> retain rollback snapshot

production pool != backfill pool
quota prevents history replay from starving current data
RiskControlResidual cost
Logic driftVersion code and metric contractChoose whether history should restate
Source driftSnapshot and temporal dimensionsOld source may no longer exist
Production starvationPool, quota, rate limitLonger completion
Partial publicationShadow, validate, atomic publishTemporary duplicate storage

P7 CDC: log-based versus query-based

Query capture samples current state; log capture consumes the database's ordered commit record.

QUERY-BASED
T1: SELECT rows after marker
T2: SELECT rows after marker

row inserted, updated, deleted between T1 and T2
 -> no current row remains to reveal the delete/intermediate state

LOG-BASED
transaction -> WAL: BEGIN, INSERT, UPDATE, DELETE, COMMIT
          |
          v
connector decodes committed changes + source positions

consumer stalls -> retained WAL grows -> source disk fills -> outage
MethodGivesCosts / failures
Query-basedSimple current-state extractionSource scans, invisible deletes, marker gaps
Log-basedDeletes, transaction order, low query loadPrivileges, decoding, schema changes, slot/retention risk
CorrectionLog-based CDC closes several query-marker gaps; it is not failure-free. Logs age out, replication slots retain disk, connectors stop, and schema changes can break decoding.

P8 Snapshot and stream stitching

Bootstrap joins finite state to an ongoing log without a gap or stale overlap winning.

SOURCE LOG ---- 100 ---- 120 ---- 140 ---->
          |
      agreed boundary B=120

1. reserve/record B
2. take snapshot associated with B
3. retain changes after B
4. load snapshot
5. apply post-B changes by key + source version
6. continue streaming

snapshot K@118 arrives after stream K@125
unconditional upsert -> target becomes stale 118
conditional upsert   -> 118 rejected; target remains 125
InvariantWhy
No source-position gapEvery commit belongs to snapshot or stream
Overlap toleratedRepeated changes converge
Source version beats arrival timeBootstrap and network reorder delivery

P9 Deletes, tombstones, and out-of-order updates

Three silent failures can all leave plausible current state.

1. HARD DELETE INVISIBLE
query current rows -> key absent, but old target row remains

2. TOMBSTONE EXPIRES TOO EARLY
delete K@v8 removed before slow consumer reads it
consumer retains K@v7 forever

3. UPDATE REORDERED
K@v12 arrives -> target=v12
K@v11 arrives later -> naive target=v11 WRONG

DEFENCE
store source_version with target
apply only when incoming_version > stored_version
delete is a versioned transition, not "no row"
ControlGuaranteeBoundary
Versioned tombstoneDelete competes in update orderRetention must exceed outage/replay horizon
Conditional upsertOld arrival cannot overwrite new source stateVersion must be authoritative
ReconciliationDetects drift outside streaming assumptionsDelayed and resource-consuming

P10 Materialization strategies

Visibility strategy decides update cost, read cost, and crash behavior.

VIEW
query -> recompute every read

MATERIALIZED TABLE
scheduled changes -> stored result -> cheap read

COPY-ON-WRITE
update -> rewrite affected files -> publish snapshot
read -> simple base files

MERGE-ON-READ
update -> append delta/delete files
read -> merge base + deltas
later compaction pays accumulated write debt

IMMUTABLE FACT
correction -> compensating/versioned event, not erased history
ChoiceGivesCosts
ViewCurrent logicRepeated compute and unstable upstream
Materialized tableFast stable readsRefresh, storage, staleness
Copy-on-writeSimple readsWrite amplification
Merge-on-readCheap frequent changesRead amplification and compaction

P12 When a pipeline should not exist

Every copy creates another owner, latency boundary, cost center, and place for truth to diverge.

REQUEST: "send this data somewhere"
  +-- governed source/read replica is queryable? -> no copy
  +-- existing view/model can serve it? ---------> no new pipeline
  +-- event delivery already exists? ------------> subscribe
  +-- low latency earns continuous operation? ---> maybe stream
  `-- independent retention/shape/scale needed? -> pipeline justified

NEW PIPELINE TAX
schedule + retry + storage + lineage + contract
+ monitoring + backfill + ownership + on-call
Build whenDecline when
A real boundary requires independent storage, compute, retention, security, or latencyAn existing query, view, export, or contract already satisfies the need
