Apache Kafka

The partition is the unit of ordering, parallelism, assignment, replication, offset, and lag. Most surprising Kafka behavior is the result of expecting a topic-wide property from a partition-scoped mechanism.

The reconstruction test. For any Kafka incident, name the partition, its leader and ISR, the producer acknowledgment path, the consumer position, and the committed group offset.
#partition#consumer-group#isr#delivery

00 One-screen mental model

A topic is several independent ordered logs; clients and replicas coordinate around each one.

PRODUCERS
 key=A | key=B | key=A
   |       |       |
   +--- partitioner + batching ---+
                    |
          +---------+---------+
          v                   v
TOPIC PARTITION 0         TOPIC PARTITION 1
leader: B1                leader: B2
[0][1][2][3][4]           [0][1][2]
 | replicated to ISR       | replicated to ISR
 v                          v
followers B2,B3            followers B1,B3

CONSUMER GROUP G

consumer C2 <- assigned P1 -> position 3 -> committed offset 3

ordering: within one partition
parallelism ceiling: partition count
lag: log-end offset - consumer/group position, per partition

K1 Architecture

Pressure: retain an ordered event history while distributing throughput and surviving broker loss.

CLUSTER
+-- controller quorum: metadata leadership and broker/partition state
+-- broker 1
|   +-- P0 leader
|   `-- P1 follower
+-- broker 2
|   +-- P1 leader
|   `-- P0 follower
`-- broker 3
    +-- P0 follower
    `-- P1 follower

TOPIC = named collection of partitions
PARTITION = ordered append-only sequence with offsets
REPLICA = copy of one partition
LEADER = replica serving reads/writes for that partition
ScopePropertyNot implied
PartitionTotal order by offset for appended recordsOrder across other partitions
TopicAggregate capacity across partitionsOne global cursor or transaction history
ClusterPlacement and replication across brokersApplication-level exactly-once effect
BoundaryOffsets identify positions, not event time, business sequence, or globally comparable order.

K2 The storage engine

Append sequentially, index sparsely, and let the operating-system page cache serve hot data.

PARTITION DIRECTORY
00000000000000000000.log     records 0 ... 999
00000000000000000000.index   sparse offset -> byte positions
00000000000000000000.timeindex
00000000000000001000.log     active segment, records 1000 ...

FETCH offset 742
  -> choose segment by base offset
  -> sparse index finds nearby byte position
  -> scan forward to exact record
  -> page cache may satisfy read
  -> file region transferred to socket with minimal copying

segment roll -> old segment immutable -> retention/deletion manageable

Compaction is not an LSM tree

log compaction by key:
K1=v1, K2=v1, K1=v2, K2=tombstone
                    |
                    v
retain latest K1=v2; eventually remove superseded K1 and deleted K2

records remain in offset order; Kafka does not maintain sorted levels for key lookup
MechanismGainCost / boundary
SegmentsRetention and indexes operate on bounded immutable filesDeletion occurs by segment, not individual record
Sparse indexSmall index with short sequential scanNot direct key lookup
Page cache / zero-copy pathReuse OS cache and reduce user-space copiesCold reads and cache contention still hit storage
Tiered storageLong retention without local disk for all historyRemote fetch latency and operational complexity

K3 Producers

A producer trades latency, throughput, durability, and ordering through a partition-scoped send path.

record(key, value)
      |
      v
serialize -> choose partition -> append to per-partition batch
                               |
                     linger.ms / batch.size reached
                               |
                               v
                         compress batch
                               |
                               v
                    send to partition leader
                               |
              +----------------+----------------+
              v                v                v
           acks=0           acks=1           acks=all
        no broker ack    leader appends     leader waits for
                                          current ISR replicas

retry after ambiguous response -> idempotent producer sequence numbers
                                let broker reject duplicate append
LeverGainCost / boundary
linger.msMore records per batch, better compression/throughputIntentional queueing latency
batch.sizeLarger efficient requests when traffic fills themMemory; does not force sparse traffic to wait until full
acksSelects acknowledgment durability pathHigher waiting and availability constraints
max.in.flightMore pipeline concurrencyWithout idempotence/config safeguards, retries can reorder
VerifyRecord batch size, request rate, compression ratio, record queue time, request latency, retries, and error rate while changing one producer lever.

K4 Consumers

Processing position and committed recovery position are separate state.

partition log:  [40][41][42][43][44][45]
                         ^           ^
                  committed=42   position=46 after poll

poll -> receive 43,44,45 -> process -> side effect -> commit 46

CRASH WINDOWS
commit before effect:
  commit 46 -> crash -> restart at 46 -> effects 43..45 LOST

effect before commit:
  effects 43..45 -> crash -> restart at 43 -> effects DUPLICATED

atomic/idempotent sink boundary decides whether replay is safe
ChoiceBehaviorMain risk
Auto commitLibrary periodically advances group offsetCommit may not correspond to completed business effect
Sync manual commitCaller waits for coordinator responseLatency and still an external-sink gap
Async manual commitCaller continues while commit is in flightCallbacks/reordering and uncertain final commit on shutdown
Seek/replayReset position to chosen offsetSide effects must tolerate repeated records
Poll contractIf processing prevents another poll longer than max.poll.interval.ms, the group may evict the member even while its process is alive.

K5 Consumer groups

A group divides partitions; it does not divide individual records from one partition concurrently.

TOPIC: P0 P1 P2 P3

GROUP G with 2 consumers       GROUP G with 6 consumers
C1 <- P0,P1                    C1 <- P0   C2 <- P1
C2 <- P2,P3                    C3 <- P2   C4 <- P3
                               C5 <- idle C6 <- idle

GROUP H is independent
H1 <- P0,P1,P2,P3

parallelism within one group <= partition count
each group maintains its own committed offsets

Assignment protocol

members join -> coordinator identifies generation
             -> assignment strategy maps partitions to members
             -> members sync assignment
             -> consumption resumes

membership or partition change -> new assignment required
Guarantee boundary"One consumer per partition" is a group assignment invariant for active members, not a guarantee that business effects occur once. A revoked consumer may still have in-flight work.

K6 Rebalancing

Membership change requires ownership transfer; transfer strategy determines pause and duplicate-risk shape.

EAGER REBALANCE
C1 owns P0,P1     C2 owns P2,P3
      |
      v
all members revoke all partitions ---- consumption stops
      |
      v
new complete assignment ---- consumption restarts

COOPERATIVE INCREMENTAL
C1 keeps P0; revokes P1 -> new C3 acquires P1
C2 keeps P2,P3
only moving partitions pause across coordinated rounds

Rebalance storm loop

slow processing
   -> poll interval exceeded
   -> member removed
   -> rebalance pauses/moves work
   -> backlog and processing pressure rise
   -> replacement also misses poll
   `--------------------------------> repeats
MitigationMechanismCost
Cooperative assignorMoves ownership incrementallyProtocol takes coordinated rounds; clients must support it
Static membershipStable instance identity tolerates brief restartStale identity must be fenced correctly
Bound poll workKeep group liveness separate from long processingRequires internal queue/backpressure and offset discipline
VerifyRecord rebalance count/rate, assignment duration, records-lag-max, poll interval, processing time, and revoked/assigned partitions on one timeline.

K7 Replication

Durability comes from replica state at acknowledgment time and the election rules used after failure.

PARTITION P0
leader B1:    [0][1][2][3][4][5]
follower B2:  [0][1][2][3][4][5]  in ISR
follower B3:  [0][1][2][3]        lagging, may leave ISR
                         ^
                  high watermark
          records at/below committed boundary visible to consumers

acks=1:
leader appends -> ACK; leader may fail before followers copy

acks=all:
leader appends -> wait for every replica currently in ISR -> ACK

min.insync.replicas:
minimum ISR size required to accept an acks=all write
Precise interactionacks=all and min.insync.replicas do different jobs. With ISR size 3 and minimum 1, acks=all still waits for the current ISR and is stronger than acks=1. The danger is availability after ISR shrinks: minimum 1 permits writes with only the leader in sync, so the redundancy guarantee has degraded without rejecting writes.
Failure choiceGainCost / loss mode
Higher minimum ISRReject writes before redundancy falls below policyLower write availability during replica loss
Unclean leader election allowedPartition may recover availability from out-of-sync replicaAcknowledged records can disappear
Unclean election disabledPreserves committed historyPartition can remain unavailable until valid replica returns
VerifyTrack ISR membership and high watermark. Stop followers, observe when ISR shrinks, then attempt acks=all writes under different minimum ISR settings.

K8 Delivery semantics

The end-to-end outcome is the composition of producer retry, broker durability, consumer commit, and sink behavior.

PRODUCER              KAFKA              CONSUMER              SINK
retry/idempotence -> replication -> poll/offset commit -> write semantics
       |                 |                 |                    |
       +-----------------+-----------------+--------------------+
                                 |
                                 v
                         END-TO-END EFFECT

AT-MOST-ONCE: commit/advance before effect -> loss possible, no replay duplicate
AT-LEAST-ONCE: effect before commit         -> replay duplicate possible, no loss if source retained
EFFECTIVELY-ONCE: replay occurs, sink dedup/upsert makes repeated effect converge
TRANSACTIONAL EOS: coordinated Kafka read-process-write within supported transaction boundary
ClaimWhere it stops
Idempotent producerPrevents duplicate appends from that producer session/path; does not deduplicate sink effects
Kafka transactionCoordinates supported Kafka records and consumed offsets; external systems need their own cooperation
read_committedHides aborted transactional records; does not validate business correctness
Exactly onceMust name source, state, sink, identity, and failure window; otherwise it is not a complete claim

K9 Performance and lag

Lag is a symptom measured per partition; its distribution distinguishes capacity from skew.

lag(P) = log_end_offset(P) - consumed_or_committed_offset(P)

PATTERN A                         PATTERN B
P0: 1,000                        P0: 100,000
P1: 1,200                        P1: 20
P2:   900                        P2: 15
P3: 1,100                        P3: 18
    |                                |
    v                                v
all partitions behind            one hot/stuck partition
capacity / downstream issue      key skew / owner / data issue

drain condition:
consumer service rate > arrival rate
backlog drain rate = service rate - arrival rate
LeverImprovesCost / boundary
More consumersParallel service until partition ceilingNo help to one hot partition already owned by one member
More partitionsPotential write/read parallelismMetadata, files, replication work; key-to-partition mapping changes
Larger batches/compressionThroughput per request/byteLatency, CPU, memory
Better keyDistributionMay sacrifice required per-key ordering

K10 Failure modes

A useful incident model ties each failure to an observable transition and a guarantee boundary.

FailureState transitionObservable signalRisk
Leader broker diesEligible ISR follower electedLeader-election errors, temporary request failuresUnclean election policy decides loss vs outage
Consumer crashes after effectPartition reassigned from last committed offsetRebalance + replayDuplicate external effect
Consumer stallsLag rises; poll interval may expireLag slope, poll metrics, rebalanceFeedback loop into storm
ISR shrinksReplica removed from acknowledgment setUnder-replicated partitions, ISR changesDurability policy may silently degrade if minimum is low
Retention passes unread offsetRequired segment deletedOffset out of rangeReplay source is gone
FAILURE QUESTION
  -> which partition?
  -> what was leader/ISR/high watermark?
  -> what was produced and acknowledged?
  -> what side effect completed?
  -> what offset was committed?
  -> what data still exists under retention?

K12 When not to use Kafka

A replicated replayable log is expensive when the requirement is only a queue, request, or current value.

REQUIREMENT
  |
  +-- replayable ordered history + many independent consumers? -> Kafka may fit
  +-- simple task dispatch with per-message ack? --------------> work queue
  +-- request/response with tight tail latency? ---------------> RPC/service
  +-- current state / key lookup? ------------------------------> database/KV
  +-- one producer, one consumer, low volume? ------------------> file/DB/simple queue
  `-- global ordering across all events? -----------------------> partitioned Kafka conflicts with it
Kafka givesYou pay
Retention, replay, partitioned scale, consumer independence, replicationBroker operations, partition planning, rebalances, schema/retention discipline, eventual cross-partition reasoning
