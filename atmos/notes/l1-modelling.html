Data Architecture & Modelling

A model is a set of decisions about what can still be answered. The load-bearing decision is grain: once an event was never captured at the required grain, no later SQL can reconstruct it.

The reconstruction test. For every table, complete one sentence: "one row represents exactly..." Then prove that every measure, key, history rule, and metric definition is compatible with it.

M1 The data lifecycle

Pressure: the system that records a fact is rarely the system that analyzes it.

GENERATION -> INGESTION -> STORAGE -> TRANSFORMATION -> SERVING
    |            |           |              |             |
 business     loss/order   retention      meaning       latency
 semantics    contracts    + layout       + quality     + access

UNDERCURRENTS CROSS EVERY STAGE
security | orchestration | metadata | ownership | observability

Why a pipeline-only view fails

"move rows from A to B"
   -> ignores where meaning entered
   -> ignores who may see it
   -> ignores how it changes
   -> ignores how consumers detect staleness
   -> successful copy can still be a failed data product
BoundaryQuestion that must cross itSilent failure
Generate -> ingestWhat event and version does this record mean?Schema-valid record with changed semantics
Store -> transformWhich snapshot and corrections are included?Repeat run reads a different past
Transform -> serveWhich grain, freshness, and metric version?Plausible dashboard using incompatible definitions

M2 OLTP versus OLAP

Opposing workloads create opposing physical and logical designs.

OLTP                                      OLAP
"update order 42"                        "revenue by region for 3 years"
      |                                            |
      v                                            v
few rows + many concurrent writes          many rows + few columns
      |                                            |
      v                                            v
row locality + indexes + constraints       columnar scans + compression
      |                                            |
      v                                            v
normalized current state                   historical analytical model

run OLAP scan on OLTP -> buffer churn + lock/contention + production risk
AxisOLTP pressureOLAP pressure
AccessPoint lookup and short rangeLarge scan and aggregation
MutationFrequent row-level insert/updateAppend or bulk rewrite
ConcurrencyMany small transactionsFewer expensive queries
ShapeNormalized to protect writesDenormalized to simplify and accelerate reads
VerifyProfile one aggregate against normalized row storage and an analytical copy. Record rows/bytes scanned, index use, locks, and impact on transactional latency.

M4 Batch, streaming, and hybrid

The distinction is boundedness and correction behavior, not whether a tool runs every minute.

BOUNDED INPUT                       UNBOUNDED INPUT
known end                          no final record
   |                                  |
   v                                  v
run complete computation           maintain result over time
   |                                  |
   v                                  v
easy replay from source            windows + state + lateness policy

LAMBDA                              KAPPA
batch truth + speed layer           one streaming path + replay log
      |                                         |
      v                                         v
two implementations can diverge     replay may be operationally expensive

COMMON REALITY: stream for freshness + batch reconciliation/backfill
Decision pressureChoose from required staleness, correction semantics, replay cost, and source boundedness. "Real time" without a number is not a requirement.

M5 Grain

The one irreversible modelling decision: what one row asserts about reality.

ORDER 9
header discount = 30
lines:
  product A, qty 1, amount 100
  product B, qty 2, amount 200

MIXED-GRAIN TABLE
order_id | product | line_amount | header_discount
9        | A       | 100         | 30
9        | B       | 200         | 30
                                  |
SUM(discount) --------------------+--> 60  WRONG, no error

DECLARED GRAINS
order_fact:      one row per order
order_line_fact: one row per order line
      |
      v
header discount stored once; line amounts remain additive

Grain sentence

ONE ROW PER
  [business event or state]
  x [entity/key scope]
  x [time resolution]

Example:
one row per account per calendar day per currency
TestQuestionFailure if unanswered
UniquenessWhich columns identify exactly one assertion?Merge key deletes or duplicates legitimate facts
AdditivityAcross which dimensions may this measure be summed?Ratios, balances, and headers silently double-count
ResolutionWhat detail was discarded before storage?Future question cannot be reconstructed
VerifyWrite the grain sentence before schema design. Construct two records that should coexist; test the proposed key and every aggregate across each dimension.

M8 Star versus snowflake

The modern tradeoff is query simplicity and joins versus centralized dimension maintenance.

STAR                               SNOWFLAKE
             product                         product
                |                               |
customer -- sales_fact -- date         subcategory <- product
                |                               |
              store                         category

fewer joins                         normalized hierarchy
easy for consumers                  updates centralized
repeated attributes compress well   more joins + more semantic paths
ChoiceGivesCosts
StarPredictable joins, comprehensible query surfaceRepeated dimension attributes and update pipelines
SnowflakeNormalized hierarchy and reduced update duplicationJoin count, optimizer dependence, consumer confusion
Correction to an old argumentIn columnar stores, repeated low-cardinality dimension values often compress extremely well. Storage duplication alone is no longer a decisive reason to snowflake.

M9 Slowly changing dimensions, types 1-6

The real choice is which temporal question the model must answer.

CUSTOMER 7 MOVES: WEST -> NORTH at t2

TYPE 1: overwrite
[7, NORTH]                  answers current only

TYPE 2: add version
[surrogate 70, 7, WEST,  t0..t2)
[surrogate 71, 7, NORTH, t2..open)  answers as-was by valid time

TYPE 3: add previous column
[7, current=NORTH, previous=WEST]   one prior value only

TYPE 4: current + separate history table
current[7,NORTH] + history[7,WEST,t0,t2]

TYPE 5: mini-dimension + current-profile reference
historical profile on fact; current profile also reachable

TYPE 6: 1 + 2 + 3 hybrid
version rows + current value propagated + prior value
QuestionRequired behaviorLikely patternCost
What is true now?Latest value onlyType 1History destroyed
What was true when event occurred?Versioned valid intervalsType 2Row growth and interval joins
Restate history using current organizationCurrent attribute reachable from old factsType 5/6 or explicit dual modelMore columns/joins and update logic
What did system believe at reporting time?Record system time as well as valid timeBi-temporal extensionTwo time axes and correction semantics
BoundaryType 2 captures changing business validity only if effective times are trustworthy. It does not by itself preserve when the warehouse learned or corrected that history.

M11 Physical design

Logical truth stays constant while layout changes the amount of work required to retrieve it.

TABLE: 10 TB, common predicate date + tenant_id

PARTITION by date
year/month/day directories
   -> eliminate whole partitions
   -> too-fine key creates small files and metadata load

CLUSTER within partition by tenant_id
similar tenant ids colocated
   -> narrower file/row-group min-max ranges
   -> more selective pruning

FILE SIZE
too small -> open/list/plan overhead
too large -> weak parallelism + coarse rewrite/pruning unit

Causal chain

query predicate aligns with partition/cluster key
   -> metadata rejects physical units
   -> fewer bytes scanned
   -> lower latency and billed scan cost

wrong key / high-cardinality partition
   -> many tiny partitions
   -> metadata and file overhead dominate
VerifyHold rows and query fixed. Rewrite with two layouts; compare files opened, row groups skipped, bytes scanned, elapsed time, and rewrite cost.

GainMechanismBoundary
Consistent metricsCentral versioned definition compiled into consumer queriesConsumers can still bypass it
Change impactMetric lineage to physical columns and modelsOnly as complete as instrumentation
Temporal correctnessDefinition version and effective intervalRestating old reports is a product decision, not just recomputation
FailureTwo dashboards can use the same formula over different grains and both look reasonable. The semantic layer cannot repair missing source grain; it only governs meaning over data that exists.
