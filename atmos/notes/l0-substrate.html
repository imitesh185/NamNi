The Substrate

Most performance and correctness properties above this layer are inherited from two decisions below it: how bytes are arranged, and which state transition is atomic.

The reconstruction test. Given a slow scan or a half-visible table update, trace the behavior downward until you can point to the bytes read, metadata consulted, or single commit operation. A tool name is not an explanation.

B1 Row versus columnar layout

Pressure: analytical queries touch many records but only a few attributes.

DATA
id | city | fare
1  | BLR  | 120
2  | DEL  | 250
3  | BLR  | 180

ROW LAYOUT                         COLUMN LAYOUT
[1,BLR,120][2,DEL,250][3,BLR,180] [1,2,3][BLR,DEL,BLR][120,250,180]

SELECT SUM(fare)                   SELECT SUM(fare)
        |                                  |
        v                                  v
read id + city + fare              read fare bytes only
discard two fields                 contiguous values, same type

Why the simple thing fails

store complete records together
        -> excellent point lookup / whole-row update
        -> scan 1 column across 100 columns
        -> read roughly 99 unwanted columns
        -> I/O and decode work dominate
LayoutGivesCostsBreaks down when
RowWhole record in one locality unit; cheap inserts and point readsAnalytical projection reads unwanted fieldsQueries scan few columns across many rows
ColumnarColumn pruning, type-local encoding, vectorized processingReconstructing one row touches several streams; updates are awkwardWorkload is dominated by point writes or full-record lookup
VerifyWrite the same wide dataset as a row-oriented file and Parquet. Query one column, then all columns. Record bytes read, elapsed time, and CPU. The mechanism predicts the gap should collapse as projection width approaches the full schema.

B2 Parquet, opened up

Core idea: package columnar data into independently skippable and decodable units.

PARQUET FILE
|
+-- ROW GROUP 0 -----------------------------+
|   +-- column chunk: id                     |
|   |   +-- page: values + encoding metadata |
|   +-- column chunk: city                   |
|   |   +-- page: dictionary + encoded ids   |
|   `-- column chunk: fare                   |
|       `-- page: encoded values             |
|
+-- ROW GROUP 1 -----------------------------+
|   `-- same column-chunk structure          |
|
`-- FOOTER
    +-- schema
    +-- row-group locations
    +-- column offsets and codecs
    `-- statistics: null_count, min, max ...

READ WHERE fare > 500
        |
        v
read footer -> reject row groups with max(fare) <= 500
            -> fetch only requested column chunks
            -> decode selected pages

Causal chain

footer statistics selective
   -> row groups rejected before data fetch
   -> fewer compressed bytes transferred
   -> fewer values decompressed and decoded
   -> lower I/O + CPU

projection requests 2 of 100 columns
   -> only 2 column chunks fetched per surviving row group
   -> column pruning removes about 98% of column payload
UnitJobMain tuning consequence
Row groupHorizontal partition with one chunk per columnLarger groups improve sequential I/O; smaller groups improve pruning and parallelism
Column chunkAll values for one column inside one row groupProjection can skip every unrequested chunk
PageEncoding/compression unit inside a chunkSmaller recovery/read unit, but more metadata overhead
FooterMap from logical schema to physical locations and statisticsA final range read is required before selective access
BoundaryMin/max statistics are not magic indexes. If values are randomly distributed, nearly every row group may have the same broad range and none can be pruned. Sorting or clustering makes the metadata selective.
VerifyInspect the footer, record row-group min/max, and compare the same predicate on randomly ordered versus sorted data. Confirm skipped row groups in the query profile rather than inferring pruning from elapsed time.

B3 Compression and splittability

Compression saves I/O by spending CPU; block boundaries decide whether readers can work independently.

WHOLE-FILE COMPRESSION
file bytes -> [ one compression stream ------------------- ]
                                  ^
reader cannot begin here without earlier stream state

BLOCK / PAGE COMPRESSION
file bytes -> [block 0][block 1][block 2][block 3]
                 ^        ^        ^        ^
              worker 0 worker 1 worker 2 worker 3

COLUMNAR ENCODING PIPELINE
similar typed values
      -> encode structure (dictionary / RLE / delta)
      -> compress remaining bytes (Snappy / ZSTD / ...)
      -> store block metadata

Why the benefit exists

fewer stored bytes
   -> fewer bytes read from disk/object storage
   -> less network transfer
   -> more data fits in cache
   -> decode CPU may be repaid many times

but:
high compression level -> more write CPU + more read CPU
whole-file stream       -> weak split parallelism
tiny blocks             -> metadata and call overhead
PriorityLikely choiceReasonCost
Fast repeated analyticsFast block codecDecode latency matters on every scanLarger files than maximum-ratio codec
Cold archivalDenser codecStorage saved for long retentionMore CPU when eventually read
Parallel distributed readsIndependent blocks/pagesWorkers seek directly to assigned rangesPer-block framing and metadata
VerifyHold data and layout fixed. Change only codec, then record file size, write time, read time, CPU, and bytes fetched. A codec cannot be called "better" without naming which column wins.

             conversion boundary

  row                 columnar
FormatOptimizesCore mechanismMain mismatch
AvroRecord transport and schema evolutionWriter and reader schemas resolve fields during decodeAnalytical projection still traverses records

Decision ruleAsk four questions: Is the unit of work one record or many? Which columns are read? Must old and new schemas interoperate? Which engines must read the file? The answer is a workload fit, not a format reputation.

B5 Open table formats and the metadata tree

A directory of immutable data files becomes a table when metadata defines one coherent snapshot.

CATALOG POINTER
      |
      v
TABLE METADATA v42
      |
      +-- schema + partition specification
      +-- current snapshot id
      `-- snapshot history
              |
              v
        MANIFEST LIST
          /       \
         v         v
   MANIFEST A   MANIFEST B
      |            |
      v            v
 data files     data files
+ stats         + stats

QUERY category = 'books'
      -> metadata prunes irrelevant manifests
      -> manifest stats prune irrelevant data files
      -> Parquet footer prunes row groups
      -> pages are decoded

Why a file list is insufficient

list object prefix
   -> thousands / millions of objects
   -> no single declaration of "the table at time T"
   -> concurrent writes expose ambiguous membership
   -> schema and partition evolution have no versioned home

versioned metadata tree
   -> immutable snapshot names exact file set
   -> readers pin one snapshot
   -> metadata pruning avoids listing and opening everything
GainMechanismCost / boundary
Snapshot isolationReader follows one immutable snapshotOld metadata/files remain until expiration
Time travelRetained snapshot historyRetention raises storage and metadata cost
Partition evolutionSnapshot records the active specificationReaders must understand multiple specs
File pruningManifest-level statisticsMetadata itself can become large and need maintenance

B6 Atomic commit on object storage

Construct new state privately; publish it by changing one authoritative pointer.

BEFORE
catalog -> metadata v41 -> snapshot S41 -> {A.parquet, B.parquet}

WRITER BUILDS OFF TO THE SIDE
                         write C.parquet
                               |
                               v
                    snapshot S42 = {A, B, C}
                               |
                               v
                         metadata v42

COMMIT
compare catalog pointer == v41 ?
       | yes                         | no
       v                             v
catalog: v41 -> v42              CONFLICT: retry/rebase

READERS
resolved before commit -> follow v41 -> complete old state
resolved after commit  -> follow v42 -> complete new state
                         never a mixed file set

State machine

OLD_VISIBLE
    |
    | create immutable files + metadata
    v
NEW_PRIVATE -------------------X crash
    |                            |
    | conditional pointer update| old pointer unchanged
    v                            v
NEW_VISIBLE                  OLD_VISIBLE + orphan files
                                  |
                                  v
                           later orphan cleanup
PrecisionObject storage does not generally provide a filesystem-style atomic directory rename. The atomic boundary is supplied by a catalog transaction, conditional metadata update, or equivalent compare-and-swap. Data files are immutable; one authoritative reference changes.
GuaranteeRequiresDoes not guarantee
Readers see old or new snapshotAll readers resolve through the authoritative metadata pointerTwo writers will both commit; one may lose the compare-and-swap race
Crash before commit is invisibleNew files are not discoverable as table state without committed metadataNo orphan files; cleanup is separate
Optimistic concurrencyCommit validates the base versionAutomatic semantic merge of conflicting changes
VerifyRun one reader pinned to the old snapshot while a writer creates a new snapshot. Kill the writer before and after pointer update. Record the catalog pointer and exact file set each reader resolves.

B7 Compaction

Frequent small writes optimize arrival; analytical readers pay the accumulated file-open tax.

INGEST-OPTIMIZED STATE
[2 MB][1 MB][3 MB][2 MB][1 MB] ... x 10,000 files
   |      per-file request + metadata + footer + planning
   v
high fixed overhead before useful scan work

COMPACTION
read small files -> sort/cluster if useful -> write large files
                                          -> commit new snapshot
                                          -> expire old files later

READ-OPTIMIZED STATE
[256 MB][256 MB][256 MB] ... fewer files
   |
   v
fewer opens + larger sequential reads + more useful statistics
Compaction givesCompaction costsBoundary
Lower planning/file-open overhead; better clustering; larger scan unitsRead + rewrite I/O, compute, temporary duplicate storage, write amplificationCompact files read often enough for future savings to repay rewrite cost

Decision equation

compact when:

future_read_savings_over_retention
    > rewrite_compute + rewrite_I/O + operational risk

not merely when:

small_files_exist
VerifyHold total bytes fixed while varying file count. Plot planning time, first-row latency, total scan time, and request count. Compact once; measure how many future reads are needed to repay it.

B8 Partial failure and idempotency

A timeout cannot tell the caller whether an operation failed or merely lost its reply.

CLIENT                         SERVICE                         SINK
  |                              |                              |
  | write item 42, key=K42       |                              |
  |----------------------------->| apply write                  |
  |                              |----------------------------->|
  |                              |                  COMMITTED   |
  |                X reply lost  |                              |
  |<-----------------------------X                              |
  | timeout: outcome UNKNOWN                                    |
  | retry K42                                                   |
  |----------------------------->|                              |

NAIVE APPEND                    IDEMPOTENT EFFECT
retry -> second row             retry same key/version
      -> duplicate                   -> same final state

Core pressure

partial failure
   -> caller cannot distinguish "not done" from "done, reply lost"
   -> retry is required for availability
   -> retry may duplicate effects
   -> operation needs a stable identity or replaceable target
   -> repeated execution converges to one state
PatternIdempotency mechanismBoundary
RequestDeduplication key stored with resultKey retention must exceed retry horizon
Table loadOverwrite a deterministic partition or merge on true grainWrong grain turns legitimate rows into collisions
Versioned stateApply only if incoming source version is newerRequires a trustworthy monotonic version
Snapshot commitPublish immutable state through one conditional pointer changeOrphan cleanup and writer conflicts remain
BoundaryIdempotent delivery is not exactly-once execution. Work may execute several times; only its externally visible effect converges. Every side effect must participate, or the guarantee stops at the first non-idempotent boundary.

B10 LSM, MVCC, and the WAL

Three different mechanisms answer three different pressures; vocabulary overlap does not make them one design.

WRITE-AHEAD LOG (durability / recovery)
transaction change -> append WAL -> flush required record -> acknowledge
                              |
                              +-> replay after crash
                              `-> CDC reads ordered changes

MVCC (concurrent visibility)
row key -> version 7 [visible to snapshot T1]
        -> version 8 [visible to snapshot T2]
readers choose versions; writers need not overwrite readers' view

LSM TREE (write-optimized indexing)
write -> memory table -> immutable sorted run -> level 0
                                      |
                                      v
                                  compaction
                                      |
                                      v
                               larger sorted levels
MechanismPressure solvedBenefitCost / failure boundary
WALCrash between logical change and durable page updateSequential durable record supports redo/recovery and replicationRetention and replication-slot lag can exhaust disk
MVCCReaders and writers need concurrent, stable viewsSnapshot reads without blocking every writerOld versions accumulate; vacuum/garbage collection is required
LSMRandom writes are expensiveTurns writes into memory updates and sequential runsRead and write amplification; compaction consumes I/O
Category correctionKafka stores append-only partition segments with sparse indexes and may compact records by key. It is not an LSM tree: it does not maintain sorted runs across levels for key lookup. RocksDB, Cassandra, and many streaming state stores are LSM-based.
