Apache Spark

Most slow Spark jobs are paying to move data. The central reconstruction is: logical operation -> stage boundary -> shuffle files -> network fetch -> partition-level work.

The reconstruction test. Do not propose a configuration first. Point to the slow stage, identify its dependency, compare task distributions, and name the bytes or records that moved.

BoundaryCluster manager placement is not data execution. It allocates processes; Spark's driver decides stages and tasks.

S2 Lazy execution and stages

Laziness preserves a whole computation long enough for the engine to rewrite and schedule it.

df = read(...)
df2 = df.filter(...).select(...).groupBy(...).sum(...)
                |
                v
          PLAN OBJECT ONLY
          no source scanned

df2.write(...)  ACTION
       |
       v
analyze complete plan -> optimize -> choose operators -> create stages -> tasks

NARROW DEPENDENCY                 WIDE DEPENDENCY
parent partition -> one child     records from many parents -> child partition
map/filter/project                groupBy/join/repartition/orderBy
same stage                         shuffle boundary -> next stage

Causal chain

defer execution
   -> optimizer sees filter + projection + join together
   -> push filter/projection toward source
   -> reduce rows/columns before expensive operators
   -> less downstream work and movement
VerifyCall transformations without an action and inspect source access. Then compare parsed, analyzed, optimized, and physical plans after an action is defined.

S3 The shuffle

A global key operation requires records with the same destination key to meet in one partition.

MAP SIDE                                      REDUCE SIDE
input p0: A B A C                            target p0: all A
input p1: B C A B                            target p1: all B
     |                                             ^
     | hash/range partition                        |
     v                                             |
per-destination buffers                            |
     | memory full                                 |
     v                                             |
spill sorted runs -> merge -> shuffle files -------+ network fetch
                                                   |
                                                   v
                                            merge/sort/aggregate

COST = serialize + memory copies + spill I/O + network + merge + straggler

Why one stage waits

reduce task needs outputs from every relevant map task
      -> map stage must materialize shuffle outputs
      -> failed/lost output must be recomputed or refetched
      -> shuffle boundary becomes synchronization + recovery boundary
SignalMechanism suggestedDo not conclude yet
High shuffle writeWide dependency repartitioned many recordsThat shuffle is avoidable
High spillSorter/aggregate exceeded execution memoryMore executor memory is the best fix
Long fetch waitRemote blocks unavailable/slow or network constrainedCPU is slow
One long reduce taskSkew or anomalous executorAll partitions are too large
VerifyRecord shuffle read/write bytes, records, spill, fetch wait, and task-duration distribution for the exact stage. Compare to input/output size.

S4 Partitioning

A partition is simultaneously a scheduling unit, memory unit, and data-movement decision.

1 TB / 10 partitions  = ~100 GB per task -> little parallelism, likely spill/OOM
1 TB / 10,000 parts   = ~100 MB per task -> more scheduling/file overhead

repartition(200)
old partitions -- full redistribution --> 200 balanced partitions
                 costs a shuffle

coalesce(1)
old partitions -- narrow merge --> one output partition
                 avoids shuffle, but one downstream task
                 may pull a narrow upstream chain into one bottleneck
ChoiceGivesCosts / boundary
Hash partitionSame key colocated; good equality joins/aggregatesHot key remains indivisible
Range partitionOrdered ranges and range-query localitySampling and boundary skew
repartitionExplicit redistribution and potential rebalanceFull shuffle
coalesceCheap reduction without full redistributionCan preserve imbalance and collapse parallelism

S5 Catalyst

The optimizer can only transform semantics it can see.

SQL / DATAFRAME EXPRESSIONS
          |
          v
PARSE: unresolved syntax tree
          |
          v
ANALYZE: bind tables, columns, types
          |
          v
LOGICAL OPTIMIZE: push filters, prune columns, fold constants
          |
          v
PHYSICAL PLANNING: enumerate joins/exchanges/scans using statistics
          |
          v
CODE GENERATION: fuse compatible operators

OPAQUE UDF
input row -> [unknown Python/JVM function] -> output
             optimizer cannot reason through it
             pushdown/folding/codegen may stop at boundary

Mechanism to consequence

declarative expression visible
  -> Catalyst proves equivalent rewrite
  -> filter and projection move before scan/join
  -> fewer rows/columns enter expensive path

stale statistics
  -> wrong cardinality estimate
  -> wrong physical join may still be logically correct
  -> performance failure, not answer failure
VerifyChange one built-in expression to an equivalent UDF. Diff optimized and physical plans, pushed filters, whole-stage codegen regions, and runtime metrics.

S6 Tungsten

Remove per-row object overhead and interpreter/virtual-call work from the hot loop.

OBJECT PATH
row object -> field objects -> pointers -> virtual operators -> GC pressure
   |             |              |
 scattered memory, weak cache locality, many allocations

BINARY / VECTORIZED PATH
[null bits | fixed-width fields | offsets -> variable bytes]
                  |
                  v
contiguous batches -> generated tight loop -> CPU-friendly operations

WHOLE-STAGE CODEGEN
scan -> filter -> project
  three logical operators become one generated loop
  intermediate rows need not be materialized between each operator
MechanismGainBoundary
Binary row formatCompact predictable layout and fewer JVM objectsVariable-width data still needs offsets/storage
Whole-stage codegenOperator fusion and fewer virtual callsUnsupported/opaque operators split codegen stages
Vectorized readerDecode batches into column vectorsPer-row UDF or conversion can erase the benefit

S8 Memory and spill

"Spark OOM" names several different processes and pressure paths; each demands a different fix.

EXECUTOR CONTAINER LIMIT
|
+-- JVM HEAP
|   +-- execution memory: sort / aggregate / join
|   +-- storage memory: cache
|   `-- user objects and metadata
|
+-- MEMORY OVERHEAD / OFF-HEAP
|   +-- native buffers, direct memory, JVM overhead
|   `-- Python worker processes (PySpark)
|
`-- OS-visible process memory

execution pressure -> evict storage if possible -> spill -> continue slower
single object/partition cannot spill safely -> OOM
container total exceeds limit -> external kill, even if JVM heap looks fine
FailureDiagnostic clueMechanism-first response
Driver result/metadata OOMDriver dies around collect, plan, task metadata, or broadcast creationKeep data distributed; reduce result/metadata; inspect driver path
Executor heap OOMJVM heap error in a task/operatorFind operator and per-task partition size; reduce or repartition work
Python worker OOMWorker/container failure; JVM metrics look incompleteBound Python materialization; vectorize; inspect process memory
Container/overhead killExit code / scheduler kill without Java heap errorMeasure off-heap/native/Python overhead; adjust path or limit
One skewed task OOMSingle task input/spill far above medianFix key distribution; more total executor memory may only delay it
VerifyFor the failed attempt, collect executor lost reason, container exit, heap/GC, process RSS, input bytes, shuffle bytes, spill, and task percentile distribution before changing memory settings.

S9 Join strategies

Join selection is a decision about which side moves, which side becomes state, and whether that state fits.

BROADCAST HASH JOIN
small B ----broadcast----> every executor
large A partitions local -> probe hash(B)
gain: no shuffle of A
risk: B expanded/deserialized in each executor; driver may collect broadcast

SORT-MERGE JOIN
A --shuffle by key-- sort --\
                           merge -> output
B --shuffle by key-- sort --/
gain: bounded streaming merge
cost: move + sort both sides

SHUFFLE HASH JOIN
A and B shuffled by key -> build smaller side per partition -> probe
gain: avoids global sort
risk: per-partition build must fit; skew breaks average estimate
QuestionWhy it controls the choice
Bytes after filters, not source size?Join sees the post-filter relation
Can build side fit with concurrency?Several tasks share executor memory
Are inputs already partitioned/sorted?Existing layout can remove exchange/sort cost
What is key distribution?Median size does not protect the hottest partition

S11 I/O and caching

The cheapest byte is the byte rejected by metadata before it crosses storage or serialization boundaries.

QUERY
  |
  +-- partition pruning ----> directories/files never considered
  +-- predicate pushdown ---> row groups rejected by statistics
  +-- column pruning -------> chunks never fetched
  `-- vectorized decode ----> selected bytes decoded in batches

CACHE PATH
first use: source -> decode/compute -> cache block -> consumer
next use : cache block ---------------------------> consumer

cache helps only when:
reuse savings > materialize + memory pressure + eviction/recompute cost

Input records vs outputCould filter move earlier?Add executors before reducing work

S13 When not to use Spark

Distributed scheduling and shuffle are fixed costs; some workloads never earn them back.

WORKLOAD
  |
  +-- fits comfortably on one machine? ----> DuckDB / Polars / database
  +-- needs millisecond request latency? ---> serving DB / cache / stream processor
  +-- per-record network side effects? -----> bounded concurrency service/worker
  +-- tiny periodic transform? -------------> SQL / script / warehouse task
  `-- large parallel scan + shuffle? -------> Spark may fit

Spark adds:
startup + serialization + scheduling + network + shuffle + operational surface
Use Spark whenAvoid it when
Data/work exceeds one node, work is parallelizable, latency is batch-scale, ecosystem integration mattersOne node is sufficient, response latency is tight, work is inherently sequential, or coordination dominates useful compute
