Data Platform Engineering

A platform turns one solution into a promise used by teams the builders may never meet. The discipline is therefore as much about what not to promise as what to ship.

The reconstruction test. For every capability, name the user, alternative path, time to first success, metadata contract, isolation boundary, unit cost, migration owner, and withdrawal plan.

Product boundaryA mandate can force compliance but cannot create usability. Workarounds, copied data, and shadow systems are evidence that the offered path does not solve the user job.

         |
         v

team-based pool alone:
one team's backfill and production still compete inside same boundary

QuotaCaps one workload's shareUnused capacity may strand without borrowing

E5 Storage and table-format standardization

One widely adopted contract creates more leverage than a technically superior format used by half the estate.

WITHOUT STANDARD
team A: Parquet folders + custom commits
team B: Delta conventions
team C: Iceberg, different names/retention
     |
     v
every engine/tool implements N combinations

STANDARD TABLE CONTRACT
+ one table format and catalog integration
+ file-size/layout defaults
+ naming and ownership
+ schema/partition evolution rules
+ retention, snapshot expiry, compaction
+ interoperability test suite
     |
     v
engine x reads every governed table
quality/lineage/access/cost attach once
GainCausal mechanismCost
InteroperabilityShared metadata and behavior contractFeature choice constrained to common support
Operational leverageOne compaction/retention/tooling pathMigration and central ownership
Governance coveragePolicy hooks at standard boundaryNonstandard data needs explicit quarantine/exception
Adoption thresholdStandardization compounds only when teams actually use it. Compatibility tests and migration support matter more than declaring a preferred format.

E9 Cost management and chargeback

Cost control starts by making consumption attributable and understandable, not by imposing limits blindly.

RESOURCE EVENTS
compute seconds | bytes scanned | storage | network | licenses
    |
    v
CATALOG + JOB/QUERY TAGS
owner | workload | dataset | tenant | environment
    |
    v
ATTRIBUTED UNIT COST
per pipeline run | TB processed | query | tenant | product
    |
    v
SHOWBACK -> budget/forecast alerts -> quota/optimization -> optional chargeback

visibility first: team can remove waste without gaming a billing rule
StageBehavior createdRisk
ShowbackOwners see cost consequencesNo incentive when ownership lacks budget
Budget/alertIntervene on rate change before month endStatic budget ignores growth/value
QuotaBounds shared-resource harmCan block valuable work
ChargebackStrong local incentiveAllocation disputes and optimization of accounting rather than system
Decision unitCompare cost with value or SLO at the same unit. "This table costs 10" is incomplete; "this certified report costs 10 per day and prevents 100 of manual/incident cost" can be defended.

E10 Migration and deprecation

An adopted interface cannot simply disappear; migration is part of the original feature cost.

OLD API / FORMAT / PATH v1
       |
       | EXPAND
       +-- introduce v2 alongside v1
       +-- dual read/write or compatibility adapter
       +-- publish migration tooling and deadline
       |
       | MIGRATE
       +-- lineage finds consumers
       +-- owners move and compare behavior
       +-- usage telemetry proves traffic leaves v1
       |
       | CONTRACT
       +-- block new v1 adoption
       +-- remove remaining dependency by explicit exception
       `-- retire v1 and operational burden

"no queries seen" without complete telemetry != no consumers
MechanismGivesCost / boundary
Expand-migrate-contractCompatibility during transitionTemporary dual systems and longer support
Lineage + usageConsumer inventory and progressExports/offline readers may be invisible
Automated adapter/toolReduces consumer migration effortAdapter can preserve old semantics indefinitely
Deprecation budget at launchLifecycle cost recognized earlyReduces apparent initial delivery speed
Promise accountingEvery new capability incurs future compatibility, support, and withdrawal work. A feature without an owner and deprecation path is permanent accidental infrastructure.

E11 When not to build a platform

Platform investment pays only when repeated problems, real users, and adoption can amortize the control plane.

PROPOSED PLATFORM
      |
      +-- repeated problem across several teams? -------- no -> solve locally
      +-- users and alternatives observed directly? ----- no -> discovery first
      +-- stable common path dominates variation? ------- no -> abstractions premature
      +-- team can own support/migration for years? ------ no -> do not promise
      +-- adoption value exceeds switching friction? ---- no -> improve path
      `-- measurable leverage over bespoke solutions? --- yes -> build smallest path

START
one real user + one end-to-end golden path + one reliability promise
      |
      v
measure repeat use before generalizing
BuildBuy/use managed serviceKeep local
Unique repeated requirement creates strategic leverage and ownership existsCapability is commodity and vendor boundary is acceptableOne/few workloads, high variation, or no adoption evidence
FalsifierIf a representative team cannot complete the supported job faster and more safely than its existing path, the platform has not yet earned expansion.
