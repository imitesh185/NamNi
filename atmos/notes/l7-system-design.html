Data System Design

The task is not to name the best architecture. It is to discover the requirements that control the architecture, compare viable options, and state what the selected design trades away.

The reconstruction test. Start with a consumer decision and estimated data shape. Every box in the design must answer a requirement; every arrow must name data, ordering, and a failure boundary.

Seven characteristics

VOLUME       bytes/day and total retained bytes
VELOCITY     events/sec, bytes/sec, burst shape
CARDINALITY  distinct keys and state/aggregate explosion
SKEW         hottest key/tenant versus median
LATENESS     event-to-arrival delay distribution
MUTABILITY   append, update, delete, correction frequency
RETENTION    online, replay, audit, and deletion horizons

Six tradeoff axes

AxisQuantifying questionMechanism it pressures
ThroughputAverage/peak events or bytes per second?Partition count, batching, parallelism
LatencyHow stale may the answer be?Batch interval, serving store, state
CorrectnessWhat is cost of loss, duplicate, or wrong value?Replication, idempotency, reconciliation
EvolutionHow do old/new producers and consumers coexist?Contracts, versions, expand-migrate-contract
CostStorage, compute, network, and staffing?Retention, tiers, managed versus self-run
RecoveryHow much may be lost, and how fast must backlog drain?Replay source, spare capacity, checkpoints

Numbers before products

500,000 events/s x 1 KB = 500 MB/s
500 MB/s x 86,400 s   ~= 43.2 TB/day before replication/compression

30 days x 43.2 TB/day ~= 1.30 PB logical input

BACKLOG RECOVERY
arrival rate             = r
processing capacity      = c x r, where c > 1
net backlog drain rate   = (c - 1) x r
outage duration          = T
backlog                  = r x T
catch-up time            = T / (c - 1)

At total capacity 2r: catch-up = T, not T/2.
At total capacity 3r: catch-up = T/2.
Arithmetic correctionProcessing at twice the ongoing arrival rate leaves only one arrival-rate of spare capacity. A 24-hour backlog therefore takes 24 hours to drain while new data continues arriving.

D7 Multi-tenant SaaS data architecture

Tenant size follows a power law; one uniform physical strategy is wrong for both the long tail and the largest tenants.

TENANTS BY DATA / TRAFFIC
many tiny tenants -------------------------- few whales
|..............................................####|

LONG TAIL                         LARGE TENANT
shared tables/compute             isolated partition/pool or dedicated path
tenant_id in key/filter           explicit quota and capacity
low unit cost                     noisy-neighbor containment

CONTROL PLANE
tenant catalog -> tier, region, retention, encryption, quota, owner
        |
        v
route ingest / compute / storage / serving by policy

GLOBAL VIEW requires federation/aggregation across placement tiers
ChoiceGivesCosts / boundary
Fully sharedHigh utilization and simple fleetNoisy neighbors, large scans, isolation risk
Database/schema per tenantStronger isolation and lifecycleOperational explosion for long tail
Tiered hybridShared economics plus whale isolationRouting, migration, and cross-tier query complexity
Tenant-based partitioningPruning and localityTiny partitions for small tenants, giant partitions for whales

Failure reconstruction

one whale launches backfill
 -> shared pool saturated
 -> long-tail freshness SLO fails
 -> average utilization appears efficient

signal: cost/bytes/slots/latency by tenant percentile, not only cluster average
response: workload-class pool + tenant quota + isolated whale path
