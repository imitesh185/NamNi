Reliability & Governance

A broken service often returns an error. A broken data pipeline can return a plausible number that is believed and acted on. Reliability is the machinery that shortens that silent interval.

The reconstruction test. For any wrong dataset, identify when corruption began, which invariant could have detected it, who consumed it, which columns propagated, and how long the wrong answer remained trusted.

R2 Five quality dimensions

Each dimension is a falsifiable property, not a generic quality score.

TABLE RUN t
      +-- FRESHNESS:    max(event_time), source lag
      +-- VOLUME:       row count, bytes, input/output ratio
      +-- DISTRIBUTION: nulls, quantiles, categories, cardinality
      +-- SCHEMA:       fields, types, required/optional, meaning version
      `-- UNIQUENESS:   one row per declared grain

example: rows=1,000,000 and task green
      freshness: 2 days old       -> stale success
      volume:     expected 10 M    -> partial load
      uniqueness: 990k keys       -> duplicated grain
      all are different failures
DimensionCheap first signalBlind spot
FreshnessMaximum source/event timestampFresh duplicate or corrupt rows
VolumeCount against historical/expected boundsEqual-count substitutions
DistributionNull/category/quantile/cardinality shiftsLegitimate business change
SchemaContract diffSame field with changed meaning
UniquenessDuplicate count on grain columnsWrong grain declaration
VerifyInject one deterministic fault per dimension and measure whether the check fires, detection delay, and false positives on known-valid runs.

R4 Anomaly detection and false-positive economics

A detector consumes attention; repeated false alarms destroy the channel that carries real incidents.

metric: daily transactions
normal weekday 100k
sale day        400k  <- legitimate structural change
broken load      80k  <- incident

NAIVE fixed band 90k..110k
      -> pages on every sale/weekend/holiday
      -> responders learn to ignore channel
      -> true 80k incident waits

detector value
      ~= incidents caught x avoided impact
       - false alerts x investigation cost
       - missed incidents x residual impact
MethodGivesFailure
Static thresholdSimple auditable invariantCannot follow seasonality/growth
Seasonal baselineCompares like time periodsRegime change invalidates history
Peer/ratio checkControls for shared business movementShared corruption can cancel signal
Human suppressionHandles known eventManual exceptions become permanent blind spots
CalibrationMeasure precision, recall where labels exist, alert rate, acknowledgment time, and actionability. A statistically unusual point is not automatically an incident.

R6 Compatibility, precisely defined

Compatibility names which reader/writer version pair must continue to work.

OLD DATA written by W1       NEW DATA written by W2
                              |                            |
                              v                            v
             NEW READER R2                OLD READER R1

BACKWARD COMPATIBLE: R2 reads W1 data
FORWARD COMPATIBLE:  R1 reads W2 data
FULL COMPATIBLE:     both directions

adding optional field with default
      -> old data supplies default to new reader
      -> old reader can ignore unknown new field if format permits

renaming/removing required field
      -> identity is lost unless alias/migration protocol exists
ChangePotentially safe whenHidden semantic risk
Add optional fieldDefault/absence is definedConsumers interpret missing differently
Widen numeric typeReaders support promotionDownstream storage may not
Rename fieldStable field identity/alias and migrationOften appears as delete + add
Change meaning onlyNew version/name and explicit transitionSchema checker sees no break

R8 Data SLAs and SLOs

An objective becomes operational only when its indicator, window, owner, and response are explicit.

SLI: measurable signal
      freshness lag = now - max(source_commit_time represented)

SLO: internal target
      99% of hourly partitions available within 20 minutes over 30 days

SLA: external commitment
      defined consequence when commitment is missed

ERROR BUDGET
allowed bad events/time in window
                  |
                  +-- budget healthy -> ship/change
                  `-- budget exhausted -> reliability work / restriction
Weak statementOperational form
"Data should be fresh"Named timestamp, lag threshold, percentile/window, owner
"Pipeline is 99.9% reliable"Define successful data outcome, denominator, and exclusions
"SLA is 30 minutes"Name consumer, clock start/end, consequence, and response
