Stream Processing Semantics

A stream has no end, so completeness cannot be observed directly. Windows, watermarks, lateness policies, state, and checkpoints decide when to act despite an unfinished world.

The reconstruction test. Given one output, state its event-time interval, the watermark that triggered it, which late events can still change it, what state was retained, and how that state and the sink recover together.
#event-time#watermark#state#exactly-once

00 One-screen mental model

Events arrive out of order; estimated progress bounds waiting and retained state.

W1 Event, ingestion, and processing time

One event can occupy three clocks; confusing them turns transport delay into business behavior.

action occurs              broker receives             operator handles
event=10:00:00             ingestion=10:07:12          processing=10:07:14
      |                          |                            |
      +--- offline/network -----+--- queue/scheduling -------+

EVENT TIME       when represented event happened
INGESTION TIME   when it crossed a controlled system edge
PROCESSING TIME  when this operator saw it

group by processing hour -> delayed event joins the wrong business interval
group by event hour      -> correct interval, but needs lateness policy
ClockGivesBoundary
EventDomain-time answersSource clock may be wrong or absent
IngestionStable edge timestampAlready includes source/network delay
ProcessingSimple immediate executionChanges with load, outage, and retry

W3 Watermarks

A watermark is a configured estimate of event-time progress, not proof of completeness.

P0 observed through 10:14 -> watermark 10:09
P1 observed through 10:11 -> watermark 10:06
P2 idle since 09:40       -> watermark 09:35
                                  |
operator watermark = minimum active input watermark = 09:35

window [10:00,10:05) waits although P0 and P1 advanced
idle-input policy may eventually exclude P2

watermark passes window end
   -> on-time trigger may fire
   -> earlier arrivals are classified late
   -> state survives until allowed-lateness cleanup
aggressive watermark -> earlier result + less state + more correction/loss
conservative watermark -> later result + more state + greater first-result completeness
BoundaryWatermark definitions differ by engine. Treat one as a monotonic progress signal under a policy, never as certainty that no earlier event can arrive.
VerifyRecord delay distribution, watermark per partition/operator, idle status, firing time, and late-event count on one timeline.

W4 Late data

Once output is published, later truth requires an explicit correction contract.

window [10:00,11:00) published count=100
at 13:00, event_time=10:42 arrives
                 |
        +--------+---------+
        v                  v
      DROP               ACCEPT
count remains 100          +-- restate count=101
known loss                 |   consumers update/retract
                           `-- side output
                               repair path owns reconciliation
PolicyGivesCosts
DropStable low-latency output, bounded stateMeasured incompleteness
Restate/retractConverges toward event-time truthEvery consumer must accept changing history
Side outputSeparates fast path from repairSecond path can lag, fail, or be ignored
DecisionThe lateness horizon prices latency against correction. It is a business contract disguised as an engine setting.

W6 Checkpointing and recovery

Recovery needs source positions, operator state, and sink intent from one compatible cut.

SOURCE A: records -- barrier C7 -------- records -->
SOURCE B: records -------- barrier C7 -- records -->
                              |
                              v
OPERATOR aligns or captures C7 boundary
state before C7 -> durable snapshot
records after C7 -> post-checkpoint work
                              |
                              v
COORDINATOR marks checkpoint complete

CRASH
 -> restore C7 operator state
 -> reset sources to C7 positions
 -> replay post-C7 records
 -> sink must abort or deduplicate repeated effects
ChoiceGainCost / boundary
Aligned barriersClear consistent cutSlow input delays checkpoint
Capture in-flight dataProgress under backpressureLarger, more complex snapshot
Frequent checkpointLess replay after failureMore I/O and runtime interference
BoundaryInternal state consistency does not make an arbitrary external side effect exactly once.

W7 State growth and TTL

Stable throughput can hide state that grows until recovery or memory fails.

state bytes ~= active keys x bytes/key/window x retained windows

constant 10k events/s + new keys never expire
       |
       v
hour 1: 1 GB -> hour 6: 6 GB -> day 2: OOM / huge checkpoint

TTL / window cleanup
state -- inactive past horizon H --> delete
                          |
                          v
bounded resources, but later recurrence loses prior context
ControlGainSemantic cost
TTLBounds inactive-key lifetimeLate recurrence becomes new state
Lateness cleanupReleases closed-window stateLater events drop or enter repair path

W9 End-to-end exactly-once

The claim is composed across source, state, identity, and externally visible effect.

CHECKPOINT C9
+ source offsets: P0=500, P1=620
+ operator state snapshot
` sink transaction / stable result identity
              |
              v
coordinated completion

FAIL AFTER SINK WRITE, BEFORE C9 COMPLETES
restore C8 -> replay records
     +-- transaction aborts uncommitted C9 effect
     `-- idempotent sink recognizes key/version and converges

non-idempotent email / charge / append
replay -> second effect -> guarantee ended at that boundary
Required pieceWhy
Replayable sourceRecovery can revisit recorded input position
Consistent checkpointState and offsets describe one prefix
Stable identityRepeated logical effect can be recognized
Transactional/idempotent sinkReplay does not duplicate visibility
Honest phraseRecords may execute again during recovery. "Effectively once" often names the externally visible convergence more precisely.

W10 Backpressure

When service rate falls below arrival rate, the deficit becomes delay, queue, loss, or upstream slowdown.

arrival 10k/s -> A 10k/s -> B 6k/s -> sink 6k/s
                              |
                              v
                         backlog +4k/s
                    +---------+---------+
                    v         v         v
                buffer     block      shed
                    |         |         |
                    v         v         v
                exhaustion  source lag explicit loss

backlog -> larger state/checkpoints -> slower processing -> more backlog
ResponseGivesCost
BufferAbsorbs finite burstMemory/disk and latency; no cure for sustained deficit
PropagateBounds internal queueSource lag or lower ingestion
Scale/optimizeRaises service rate if partitionableCost; hot key/sink may remain fixed
Shed/degradeProtects essential pathExplicit correctness/product loss

W12 When not to stream

Continuous state and correction machinery are waste when consumers do not value the latency.

REQUIREMENT
  +-- decision can wait for bounded hourly/daily data? --> batch
  +-- source bounded and replay cheap? -----------------> batch
  +-- consumers cannot accept correction? -------------> wait/finalize
  +-- low latency changes a valuable action? ----------> streaming may fit
  `-- continuous control over unbounded input? --------> streaming likely fits

streaming tax:
24x7 operation + state + checkpoints + lateness + replay + sink contract
Use streaming whenPrefer batch when
Latency changes action, input is continuous, and correction semantics are ownedFreshness has weak value, bounded recomputation is cheap, or simplicity dominates
